# 원작 초기 상태·난수·저장

2026-11-23. 공통 기반의 다음 묶음이다. 원본 ROM의 함수 경계를 C로 옮기고 같은 입력에서 원작 6502 실행과 GBC 실행의 결과를 비교했다. **이름 입력/새 게임 화면, 정상 진행의 전투 진입, 저장 메뉴 UI까지 완성한 단계는 아니다.** 사운드/필드 부하 ROM에는 원작 초기 상태와 새 코드 은행 왕복 검사를 연결했다.

## 상태와 원작 근거

기준 자료는 [everything8215/ff3 고정 리비전](https://github.com/everything8215/ff3/tree/1acef8117120ff891003de249b1a74bc8d94d674)의 디스어셈블리/RAM 지도다. 빌드 입력은 지원 원본 ROM이며 자료 파일을 제품에 포함하거나 빌드 때 다운로드하지 않는다. 주소와 소비자를 `tools/state-source.mjs`에 기록하고, 로컬 보고서에 각 추출 구간의 해시를 남긴다.

| 원작 상태 | 보존 계약 |
|---|---|
| `$6000..63FF` | 고정 WRAM의 1,024바이트 원형 레이아웃. 알려지지 않은 바이트도 저장·복원 |
| `$6000..601F` | 월드/차량/좌표/메시지 속도/저장 횟수/CP/24비트 돈 등 |
| `$6019/$601A` | 초기화 표식 `$5A` / 8비트 체크섬 |
| `$6020..602F` | 이벤트 플래그 128비트. `$6030..603F`도 원형 유지 |
| `$6040..607F`, `$6080..60BF` | 보물상자/NPC 스위치 각각 512비트 |
| `$60C0..60DF`, `$60E0..60FF` | 32칸 가방의 아이템 ID와 수량 |
| `$6100..61FF`, `$6200..62FF` | 4명 × 64바이트 × 2블록. 이름/24비트 경험치/HP/MP/장비/22직업 숙련도 등의 바이트 폭 유지 |
| `$6300..63FF` | 뚱보 초코보 보관 수량 |
| `$6400..67FF`, `$6800..6BFF`, `$6C00..6FFF` | 원작 저장 슬롯 1/2/3, 각 1,024바이트 |

`ff3_state_init`은 `3A/8E76..8F3F`를 옮겼다. 전체 상태를 지운 뒤 초기 월드 좌표, `FF` 보물 비트, ROM의 NPC 비트·첫 직업 능력치·MP·HP·초기 수치·장비를 적용하고 첫 캐릭터의 두 블록을 다른 세 명에게 복사한다. 이름 여섯 바이트는 `FF`다. ROM의 사용되지 않는 초기 돈 표를 임의로 적용하지 않는다. 이름 입력과 메시지 속도 설정 전 경계이며, `3D/BAD3..BAD8` 및 `3E/C0CD..C0EA`가 수행할 후속 처리는 아직 연결하지 않았다.

전체 1,024바이트의 원작 초기 상태 SHA-256은 `e35249b5d06f77392397722deb06dca851ee684deef068b0c8571f63a43fe42c`이다. 제품 ROM에는 비교 정답 상태를 복사해 넣지 않는다. C 초기화기가 원본에서 추출한 개별 입력 표로 상태를 구성한다.

## 저장 계약

- `3D/AE5C..AE96`: 현재 필드의 월드/차량/X/Y를 상태에 반영하고 표식을 설정한 뒤 체크섬 바이트를 0으로 놓아 1,024바이트를 합한다. 각 덧셈의 캐리는 버리며, **8비트 합을 XOR FF**하여 저장한다.
- `3D/AE97..AEC2`: 표식이 `5A`이며 체크섬까지 포함한 8비트 합이 `FF`여야 유효하다. 주석의 `FFFF`는 실제 연산 폭과 다르다. 서로 상쇄되는 두 바이트 변경은 원작처럼 통과한다. CRC로 바꾸지 않았다.
- `3D/A897..A8BA`: 메뉴 진입 시 `$7F38/$7F39`가 `55/AA`인지 확인하고, 유효하지 않으면 저장 횟수를 1로 초기화한다. 현재 횟수를 `$6014`에 복사하고 체크섬을 갱신한다.
- `3D/A93D..A949`: 저장 확정 뒤에만 작업용 횟수를 증가시킨다. 100 이상은 1로 되돌린다. 8비트 래핑도 유지하므로 비정상 입력 255의 다음 값은 0이다. 취소와 확정 처리를 합치지 않았다.
- `3D/A94C..A971`, `3D/A9F9..AA17`: 저장/복원은 1,024바이트 전체 복사다. 원작 로드 메뉴는 복사 후 `$6010`을 선택한 메시지 속도로 다시 설정한다(`3D/BABF..BAC1`). 저장 어댑터는 이 UI 동작까지 수행하지 않는다.

GBC는 MBC5+RAM+battery, 32KiB SRAM을 선언한다. **은행 0의 `$A000..A3FF`, `$A400..A7FF`, `$A800..ABFF`**를 슬롯 1/2/3으로 사용한다. 헤더를 추가하지 않은 원작 바이트 형식이다. 접근할 때 RAM을 켜고 은행 0을 선택하며, 끝에는 RAM을 끈다. [Pan Docs MBC5](https://github.com/gbdev/pandocs/blob/master/src/MBC5.md)의 RAM enable/bank 계약을 따른다. 남은 SRAM을 쓰거나 초기화하지 않는다.

`ff3_save_write/read`는 슬롯 1..3만 허용한다. 쓰기는 봉인된 유효 상태만 받아 원작 메뉴의 `갱신 → 복사` 계약 밖의 오용을 거부한다. 읽기는 검사를 통과하기 전 활성 상태에 한 바이트도 복사하지 않는다. 포인터는 WRAM 버퍼여야 하며 IRQ에서 호출하지 않는다. 전원 차단 중 원자성, 새 저장 UI, 한글 이름 확장, 자동 저장은 이번 범위에 추가하지 않았다.

## 두 난수 경로

| 함수 | 원작 경계 | 보존한 동작 |
|---|---|---|
| `ff3_field_random` | `3E/C711..C72B` | `$F5` 인덱스와 `$F6` 방향, `3F/FE00` 256바이트 표. 결과 인덱스가 0일 때 방향에 `A0`를 더함 |
| `ff3_battle_seed` | `3F/FC27..FC91` | 진입 A/C와 가상 NES 제로페이지 256바이트를 ADC 캐리 체인으로 합산. 3개 카운터 초기화 및 동적 256바이트 표 생성 |
| `ff3_battle_random` | `3F/FBEF..FC26` | 카운터 선택/증가 시점, 반올림, 하한/상한의 8비트 연산, 조기 반환 |

필드 난수의 역방향에서 `0 → FF`는 방향 전환이 아니며 `1 → 0`이 전환이다. 전투 카운터 선택은 주석의 `$1A`가 아니라 실제 명령이 읽는 `$21`이다. 하한 FF, 상한 0, 상·하한 동일일 때 원작 순서로 조기 반환하고 카운터를 소비하지 않는다. 역전 범위도 원작의 8비트 차를 유지한다. 선택자 0..2 밖은 공개 C API에서 명시적으로 실패시키고 출력/카운터를 보존한다.

전투 표 생성의 16비트 곱셈/나눗셈과 범위 산정의 32비트 곱셈은 이 호출 경계에서 동등한 정수식으로 옮겼다. 원작의 범용 수학 함수 전체를 이식했다고 세지 않는다. 실제 전투/컷신 진입의 제로페이지 상태와 난수 소비 순서는 이후 소비자 연결 시 추적해야 한다. **GBC의 현재 RAM이나 임의 시각을 난수 시드로 대신하지 않았다.** 아직 같은 입력 타이밍으로 정상 플레이했을 때 같은 전투 결과가 나온다는 주장은 하지 않는다.

## 검증과 재현

`tools/state-source.mjs`가 사용자의 ROM을 기존 `Driver6502`로 실행해 비교 정답을 만든다. 원작 코드 수정/성공 스텁 없이 실제 함수 또는 명시된 명령 구간을 실행한다. 저장 메뉴의 화면 처리 직전에서 멈추는 경계는 문서화했고, 별도의 GBC 테스트 ROM이 제품용 C 함수로 실제 결과를 만든다. 필드/전투 난수, 초기화, 저장 함수 코드는 은행 10을 공유한다.

| GBC 비교 | 사례 수 |
|---|---:|
| 초기화 전 메모리 패턴 3종, 상태 전체 비교 | 3 |
| 필드 좌표 반영/체크섬 생성 | 32 |
| 유효 슬롯·손상·표식·상쇄 변경 | 197 |
| 필드 인덱스 × 방향의 모든 바이트 조합 | 65,536 |
| 전투 시드: 가능한 합산 결과/진입 carry 및 혼합 제로페이지 | 528 |
| 전투 상·하한 모든 조합 + 잘못된 선택자 2종 | 65,538 |
| 저장 메뉴 횟수 256 × 표식 4종 | 1,024 |
| 저장 확정 후 횟수 256종 | 256 |
| **합계** | **133,114** |

모두 실제 GBC C 실행에서 통과했다. 전투 범위 검사는 3개 선택자와 여러 카운터를 분산 적용한 전수 상·하한 검사이며, 모든 256바이트 난수표 × 모든 카운터 × 모든 범위를 전수 조합한 것은 아니다. 최초 기대 바이트를 일부러 훼손한 별도 ROM은 사례 0/바이트 0에서 오류 1로 실패했다.

SRAM 검사는 실제 GBC 명령 실행으로 71개 요청을 처리했다. 슬롯별 전체 바이트, 슬롯 0/4/255 거부, 잘못된 입력 저장 거부, 각 슬롯의 표식/체크섬/마지막 바이트 손상 시 활성 상태 보존, 다른 SRAM 29,696바이트 보존을 검사했다. 이어 프로세스를 완전히 종료하고 새 프로세스로 같은 저장 파일을 읽어 슬롯 3개와 나머지 영역을 다시 확인했다. 매번 새 `.local/mesen-state-*` 홈을 사용하므로 기존 플레이어 저장을 덮어쓰지 않는다. 테스트 전용 SRAM 패턴 채우기/손상 주입 코드는 제품 빌드에 포함하지 않는다.

```powershell
node tools/build-state.mjs --rom "D:/private/Final Fantasy III (Japan).nes" --gbdk "D:/tools/gbdk"
node tools/build-state-verifier.mjs
node tools/verify-state.mjs
node tools/verify-state.mjs --negative
node tools/build-native.mjs --scene
node tools/build-native-verifier.mjs
node tools/verify-native.mjs --scene
node tools/verify-native.mjs --scene --platform-negative
node tools/build-native.mjs
node tools/verify-native.mjs
npm test
```

`local.json`은 원본/GBDK/MesenCore/.NET 경로를 제공한다. 상태 검사 ROM은 정답 데이터 때문에 4MiB이며 제품 메모리 사용량을 뜻하지 않는다. 필드/사운드 ROM은 계속 256KiB다. `--reuse-fixtures`는 원본·생성기/6502 코드·정답 파일의 해시가 모두 일치할 때만 로컬 정답 생성을 생략한다. 원시 결과와 빌드 로그는 `evidence/state/`, `evidence/native/`, `.local/`, `build/`에만 둔다.

## 통합 회귀와 메모리 예산

원작 초기화는 부팅 시 예약된 상태 영역에 실행한다. 기존 은행 검사에 `9 → 10 → 9` 호출을 추가해 오디오 IRQ가 동작하는 동안 원본 표를 읽는 필드 난수 함수를 반복 호출한다. 이때 쓰는 두 바이트는 검사 전용이며 게임 진행 난수로 사용하지 않는다. 전체 활성 상태 1,024바이트는 매 관측마다 원작 초기 상태와 비교한다.

| 최종 검사 | 사운드 | 필드/사운드 |
|---|---:|---:|
| 논리 틱 / 출력 이벤트 | 3,600 / 10,753 | 3,600 / 10,682 |
| 오디오 지연 / 큐 고갈 | 0 / 0 | 0 / 0 |
| 데이터/상태 코드 은행 왕복 검사 | 3,476 | 3,571 |
| 타이머 드리프트 | -0.013ms | +0.027ms |
| 원작 초기 상태 / 스택 가드 / SVBK | 통과 | 통과 |

필드 장면 6/6회 완료, 14,928바이트 업로드, 최대 화면 작업 23타이머 틱(약 5.62ms), 표시 간격 최대 2논리 틱이다. 이전 기준선의 22틱보다 한 틱 증가했으며 지연 0 기준을 완화하지 않았다. 보호 영역 손상은 오류 26/플랫폼 오류 3으로 잡혔고, 기존 호스트 검사 17/17도 통과했다. SRAM 쓰기/읽기와 사운드를 동시에 실행하는 메뉴 부하는 아직 측정하지 않았다.

필드 ROM의 고정 ROM 끝은 `$23D3`(7,213바이트 여유), 고정 WRAM 끝은 `$CC41`(정적 3,137바이트)이다. 은행 9는 561바이트, 은행 10의 상태/RNG/저장 코드와 입력 표는 1,785바이트다. 필드 작업 공간 `$D000`과 스택 가드 `$D7F0`는 유지했다. WRAM 은행을 추가로 열지 않았다.

- 상태 검사 ROM SHA-256: `07122f119c8a179ae74ebe703da65504b7370cf4d5c3eb81fa16d1810ac5d81d`
- 필드 ROM SHA-256: `5ec1a1803d11b76bdc15518d93326179e7d2599a427c81b241497f3f26dba306`
- 사운드 ROM SHA-256: `f3acb5f7296193b61b4c05e73a97f81cf2788a850707513dbd7764b0302221f1`

공개 허용 소스 107개만 별도 폴더로 복사하고 사용자 원본 ROM/고정 GBDK로 새로 빌드했다. 정답 데이터도 원본에서 다시 생성했으며 상태 검사 ROM과 필드 ROM 모두 위 해시와 바이트 단위로 일치했다. 원본 ROM, 추출 표, 정답 데이터, 관측, 저장 파일, 제공된 번역 자료는 공개 목록에 넣지 않았다.

## 남은 연결 작업

공통 바이트 상태/초기화/RNG 함수/원형 저장의 경계 검증은 확보했다. 24비트 값의 저장 폭을 유지한 것과 경험치·돈·성장 계산을 이식한 것은 다르다. RNG 비교 대상은 반환 난수·카운터·생성 표이며 원작 CPU 레지스터/스크래치 RAM 전체를 C ABI로 보존했다는 뜻도 아니다. 후속 소비자가 반환 플래그나 임시값에 의존하면 그 경계를 추가로 옮기고 대조한다. 다음은 로드맵의 자산 공급과 공통 표시 계약을 진행하면서, 실제 원작 소비자를 붙여 이름/메시지 속도/입력 샘플링·전투 진입 시드·저장 가능 조건을 검증하는 일이다. 이 단계에서도 원작을 대체하는 임의 포션·보상·메뉴 규칙을 추가하지 않는다.

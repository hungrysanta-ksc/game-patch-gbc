# 은행·메모리·시간 처리 기반

2026-11-23. 원작 사운드/제단 동굴 부하 검사에 공통 기반을 연결했다. 새 게임 초기화, 저장 슬롯 의미, RNG 또는 원작 메뉴/전투 기능을 추가한 단계는 아니다. 기존 [데이터 등록부](data-registry.md)의 소비 계약을 실제 GBC 코드에 연결하기 위한 기반이다.

## ROM과 호출 규약

| 은행 | 내용 | 접근 규칙 |
|---|---|---|
| 0 | IRQ, 오디오 출력 큐, 스케줄러, 데이터 읽기 래퍼, 현재 필드 렌더러 | 항상 매핑. IRQ에서 은행 변경/은행 함수 호출 금지 |
| 1–5 | NES 사운드 은행 36/37/38/39/09의 원본 데이터 | 생성된 길이 표 안에서만 읽기 |
| 6 | 기존 음정/노이즈 변환 표와 파형 | 음색 변환은 이전 단계 그대로 |
| 7 | 현재 원작 맵/그림/팔레트/이벤트 | 필드 빌드에만 존재 |
| 8 | 원작 사운드 로직과 원본 은행 36의 동일 복사본 | 외부 진입점은 `BANKED`, 내부는 같은 은행의 near call |
| 9 | 은행 복원·원본 데이터·잘못된 요청 검사 | 개발 부하 검사 전용 |
| 10–15 | 현재 미할당 | 앞으로의 소비자/자산 배치용 |

`platform-call.h`는 네이티브 제품 빌드에서만 은행 호출 ABI를 활성화한다. 기존 독립 알고리즘 검사는 near-call ABI를 유지한다. 별도 `mapped_bank` 캐시는 제거하고 GBDK의 `CURRENT_BANK`를 사용한다. 은행 8에서 은행 0의 래퍼를 호출하면 래퍼가 데이터 은행을 선택하고, 작업 후 은행 8을 복원한 다음 돌아온다. 원본 은행 36은 빈번한 엔벌로프 읽기의 왕복 비용을 줄이기 위해 소비 코드와 함께 배치한다. 빌더가 복사본을 원본 ROM과 바이트 단위로 대조한다.

`ff3_resource_byte/copy`의 핸들은 `(bank, offset, count)`다. offset은 GBC `$4000` 창 기준이며 유효한 생성 자산 길이 밖, 코드 은행, 미할당 은행은 오류다. 범위를 벗어난 요청을 잘라 읽지 않는다. 은행을 넘는 큰 자산은 추출기가 유효한 구간들로 나누어야 한다. 반환한 ROM 포인터를 다른 은행 전환 뒤 사용하는 API는 제공하지 않는다. 현재 렌더러의 직접 포인터 접근은 은행 0의 한 함수 안에서만 은행 7을 유지하고 종료 시 복원한다.

MBC5의 하드웨어 9비트 은행 번호와 현재 프로젝트의 8비트 호출 ABI를 구분한다. 이 기반은 은행 0..255까지만 지원하며 ROM 상위 비트는 0으로 고정한다. 은행 256 이상을 쓰려면 별도 ABI/검증이 필요하다. 근거: [Pan Docs MBC5](https://github.com/gbdev/pandocs/blob/master/src/MBC5.md), [GBDK 은행 호출/고정 래퍼](https://gbdk.org/docs/api/docs_rombanking_mbcs.html). 문서는 최신판이고 실제 빌드는 기존에 고정한 GBDK 4.5.0의 헤더/컴파일러로 검증한다.

## RAM과 상태 수명

| 주소 | 소유권/수명 |
|---|---|
| `$C000..CFFF` | SDK, IRQ가 읽는 큐/게시 스냅샷, 오디오 상태, 예약된 `ff3_game_state[1024]` |
| `$D000..D7EF` | 선택된 게임 모드의 작업 공간. 현재 `field_event` 1,031바이트를 `$D000`에 배치 |
| `$D7F0..D7FF` | 16바이트 보호 패턴. 매 프레임 검사하고 손상 시 오류로 중단 |
| `$D800..DFFF` | 스택 예산, 초기 SP `$E000`에서 아래로 사용 |
| WRAM 은행 2..7 | 예약. 현재 SVBK는 1로 유지하며 실행 중 전환을 지원하지 않음 |

현재 스택도 `$D000` 창에 있으므로 일반 C 함수가 SVBK를 변경하면 자신의 스택까지 바뀐다. 따라서 큰 총 RAM 용량을 곧바로 사용할 수 있다고 가정하지 않는다. 추가 WRAM 은행은 스택/IRQ에 안전한 복사 경로를 따로 검증한 뒤 개방한다. [Pan Docs 메모리 지도](https://github.com/gbdev/pandocs/blob/master/src/Memory_Map.md), [SVBK 규정](https://github.com/gbdev/pandocs/blob/master/src/CGB_Registers.md#ff70--svbkwbk-cgb-mode-only-wram-bank)

`ff3_game_state`는 NES `$6000..63FF` 영속 상태를 위한 1KiB 예약이다. 현재 진단 부팅의 0 초기화는 원작 새 게임 상태가 아니다. 원작 초기화, 저장 체크섬·3슬롯, 한글 이름 확장과 RNG 소비는 다음 작업에서 원작 함수와 대조한다. 이 예약 영역은 이번 사운드/필드 검사 동안 변경되지 않아야 한다.

카트리지 헤더는 CGB 전용, 256KiB ROM, MBC5+RAM+배터리(`$1B`), 32KiB SRAM으로 설정한다. 저장 하드웨어 공간을 마련한 것이며 SRAM 쓰기·저장 메뉴·재시작 복원 검증을 완료한 것은 아니다. 기존 128KiB ROM-only 진단물과 헤더/파일 크기가 다르다.

## 시간과 표시 작업

- 오디오 하드웨어 시계는 4,096Hz, 원작 논리 틱은 기존 `600988/10000 Hz` 계약을 유지한다. 정수/잔여분 누적으로 68 또는 69 타이머 틱을 더한다. 화면 프레임은 GBC VBlank를 따로 사용한다.
- 16비트 타이머 읽기는 짧은 critical 구간에서 원자적으로 수행한다. IRQ를 끈 채 ROM 복사나 VRAM 대기를 하지 않는다.
- 미래 큐 한도 205타이머 틱을 유지한다. signed 차이로 비교해야 이미 늦은 시각을 거대한 양의 미래로 오인하지 않는다. 경계/랩어라운드 6조건을 실제 빌드의 비교식으로 검사한다. 비교가 유효한 거리는 32,768타이머 틱 미만이다.
- 화면 로딩은 그래픽 16바이트, 타일 행/속성 행 각각 21바이트로 나눠 처리한다. 완료 전에는 로딩 중 상태이며, 원작 이벤트 시작은 맵 준비 후다. 그림을 축소하거나 원작 이벤트 명령을 변경하는 조정이 아니다.
- `native_ticks`는 큐 생산자의 선행 논리 시각이고 `native_consumed`는 실제 출력이 소비한 시각이다. 화면은 소비된 스냅샷을 사용한다. 앞으로 일반 게임 상태에 생산 시각을 그대로 적용하지 말고, 입력·진행 상태의 커밋 시점과 연출 예약을 구분해야 한다.

## 검증 명령과 범위

```powershell
node tools/build-native.mjs --scene
node tools/build-native-verifier.mjs
node tools/verify-native.mjs --scene
node tools/verify-native.mjs --scene --platform-negative
node tools/build-native.mjs
node tools/verify-native.mjs
npm test
```

빌드에서 모든 데이터 은행의 내용, 은행 8 복사본, 은행별 16KiB 상한, 외부 진입점/래퍼의 은행, 고정 WRAM 상한, 작업 공간 위치와 헤더/체크섬을 확인한다. 실행에서는 은행 9에서 각 데이터 은행의 앞/뒤 16바이트를 번갈아 읽고 원본 ROM에서 생성한 체크값과 비교하며 호출 은행 복원을 확인한다. 잘못된 은행·코드 은행·끝 바이트 초과·구간 초과 4가지는 목적지와 은행을 바꾸지 않고 실패해야 한다.

기존 원작 사운드 상태/음원 레지스터/VRAM 대조와 지연 0·큐 고갈 0 기준을 유지한다. 보호 패턴 손상 주입은 별도 실행으로 오류 26/플랫폼 오류 3을 확인한다. 단일 보호 구간은 모든 종류의 메모리 오류나 미래 전투의 최대 스택 사용량을 증명하지 않는다. 상태 영역 보존, SVBK, 반복 은행 전환과 기존 원작 출력의 회귀 검사를 함께 사용한다. 실기 검증이나 음색 개선은 이번 범위가 아니다.

## 최종 관측 결과

고정 MesenCore로 다음 결과를 확인했다. 녹음하지 않았다.

| 검사 | 사운드 자동 시나리오 | 필드/사운드 통합 |
|---|---:|---:|
| 논리 틱 / 출력 이벤트 | 3,600 / 10,753 | 3,600 / 10,682 |
| 관측 샘플 | 120 | 1,188 |
| 타이머 지연 / 큐 고갈 | 0 / 0 | 0 / 0 |
| 타이머 드리프트 | -0.024ms | +0.081ms |
| 원본 데이터 은행 왕복 검사 | 3,476회 | 3,572회 |
| 오류 입력 거부 / 예약 상태 보존 | 4종 / 통과 | 4종 / 통과 |

필드 장면 6회가 모두 끝났고, 원작 그래픽/팔레트/타일맵/흔들림/사운드 요청과 대조했다. 업로드 합계 14,928바이트, 최대 화면 작업 22타이머 틱(약 5.37ms), 최대 표시 갱신 간격 2논리 틱이다. 작은 업로드 단위 때문에 냉간 로딩은 146–150논리 틱으로 길어졌다. 이는 현재 부하 검사 로더의 비용이며 최종 게임 맵 전환 성능의 합격 기준이 아니다.

보호 영역을 의도적으로 손상시킨 별도 실행은 오류 26/플랫폼 오류 3으로 중단했다. 호스트 테스트 17/17 통과. 공개 허용 소스 95개와 사용자 원본 ROM/고정 컴파일러만으로 별도 폴더에서 재빌드한 필드 ROM은 바이트 단위로 동일했다.

- 필드 ROM SHA-256: `aa1b42e8accbb63118b9e32410f54ef61ba04c62a45663320d21cb5ac8647f64`
- 사운드 ROM SHA-256: `42d89c3dbafda525020e114264774539121db2010ffc8106d0f0b6e2069b4ef0`
- 필드 고정 코드 끝 `$224E`: 코드 끝 기준 7,602바이트 여유(이전 1,731바이트). 초기화 데이터/코드까지 포함한 실제 고정 ROM 끝은 `$2282`, 남는 공간은 7,550바이트다. 빌드 상한 검사도 초기화 구간을 포함한다.
- 은행 8은 코드+원본 복사본 14,612바이트, 은행 9는 검사 코드 534바이트.
- 고정 WRAM 끝 `$CC3F`: 정적 3,135바이트에 상태 예약 1,024바이트가 포함된다. 필드 작업 1,031바이트는 별도 `$D000`에 있다.

원시 관측은 `evidence/native/`, 빌드/실패 원인 조사/재현 로그는 `.local/`에만 보관한다. 다음 작업은 예약한 상태 공간에 원작 초기값·정수 폭·RNG·저장 직렬화를 연결하고 대조하는 것이다. 이후 NPC/플레이어·메뉴·전투가 같은 상태를 사용하도록 연결한다.

## 상태/저장 후속 작업

위 수치는 플랫폼 기반 PR 당시의 기준선이다. 이후 [공통 상태·난수·저장](state-save-rng.md)에서 예약 상태를 실제 원작 초기 상태로 바꾸고 코드 은행 10을 추가했다. 현재 검사에서는 0 채움 대신 원작의 전체 초기 상태를 비교하고, 은행 9 → 10 → 9 중첩 호출도 사운드와 함께 실행한다. 최신 ROM 해시/예산/회귀 결과는 후속 기록을 따른다.

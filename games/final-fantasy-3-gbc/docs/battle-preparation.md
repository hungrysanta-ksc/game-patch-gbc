# 상주 전투 준비 비용과 원작 사운드 채널

## 이번 변경의 범위

사용자는 전투 돌입의 초기 리소스 준비에 약 500ms를 허용했다. 현재 화면을 표시하면서
비활성 자원을 준비해도 되지만, 오디오 계산에서 생긴 지연은 별도로 개선한다.
이 허용치는 전투 중 모든 상태 변경이나 매 프레임의 500ms 지연을 허용한 것이 아니다.
원작 연출의 의도된 대기와 추가 로딩 지연도 구분한다.

PR 63의 같은 네 프로필(정면/백어택 × 두 적 배치), 668개 원작 상태와 실제 화면을 기준으로
비교한다. 일반 아군 OBJ, 원작 석화 BG, 28×28 적, V6 위치, 현재 표시/다음 준비와
원작 상태 확정 경계는 유지한다. 완성 그림을 ROM에 넣는 방식으로 대체하지 않는다.

## 원작 구조와 GBC의 변경 이유

원작 석화 맵 요청은 배우의 두 열 영역을 갱신한다. GBC의 7:8 적 축소 및 팔레트 제한은
경계 셀 합성과 잔여 색 OBJ를 요구하지만, 변하지 않은 상주 적/지형까지 재전송할 이유는 없다.
이번에는 다음처럼 중복 임시 공간과 전송을 줄였다.

- 석화 셀 수가 결정된 뒤 잔여 패턴을 최종 비활성 패턴 영역에 직접 쓰고 OBJ도 직접 구성한다.
  중복 패턴 384바이트와 위치 48바이트를 없애고, 반쪽 행 이력에 4바이트를 추가했다.
  정적 WRAM 순감소 428바이트, 끝 주소 0xCDD6, 0xD000 앞 여유 554바이트다.
- HDMA의 16바이트 정렬 조건에 맞춰 이전/현재 석화가 있는 반쪽 행만 전송한다.
  ID 16바이트와 속성 16바이트를 보내며, 다른 반쪽의 상주 소유권은 유지한다.
  페이지별 이전 영역과 새 영역의 합집합을 갱신하므로 해제된 셀도 원본으로 복원한다.
- 이미 opening 경로에 있던 고정 오디오 표 읽기, 연속 워드 읽기, 펄스/스윕 상수화,
  12바이트 진단 복사를 상주 석화 빌드에도 적용한다. FF3_AUDIO_FAST로 계산 경로만 선택하며
  요청 순서, 큐 크기, 보충 임계값, 타이머, 출력 변환 표와 채널 점유 규칙은 변경하지 않는다.

신규 큰 상주 버퍼는 없다. 활성 석화 셀을 다시 합성하는 비용은 남아 있으며, 다음은
고정 셀 할당과 변경된 배우만 재구성하는 방식이다. 현재 여유를 근거 없이 다른 버퍼로
소모하지 않고, 실제 같은 셀/원작 요청을 처리하는 최악 비용으로 비교한다.

## 사운드 채널을 다시 확인한 결과

GBC는 두 펄스, 한 파형, 한 노이즈 채널이다.
[Pan Docs Audio](https://raw.githubusercontent.com/gbdev/pandocs/master/src/Audio.md)는
CPU 배속과 APU 동작 속도가 별개임도 설명한다. 채널 수 차이와 CPU 변환 비용을 같은 원인으로 보지 않는다.

고정 원본 ROM의 36/8B9D·8BB8에서 효과음을 요청하고 8030을 실행했다.
97개 효과음 슬롯 각각 128회 갱신에서 두 번째 펄스 점유는 64개, 노이즈 점유는 73개,
둘을 함께 점유한 슬롯은 40개다. 실제 출력 주소는 4004–4007 또는 400C–400F였다.
이것은 원작 효과음이 다섯 번째 채널 하나만 전용으로 사용한다는 해석과 다르다.
효과음 우선 점유와 이후 음악 출력 복원을 그대로 보존해야 한다.

또한 효과음 요청 없이 전투곡 0x20만 1200틱 실행해도 4011의 0이 아닌 DAC 쓰기 41회를 관측했다.
36/8310의 볼륨 조건에 따른 직접 DAC 타격음이며, 이 경로를 DPCM 샘플 스트림으로 오인하지 않는다.
현재 GBC backend는 이 타격음에 CH4를 짧게 차용한다. 원래 노이즈/효과음과의 음색 충돌 가능성은
남아 있다. 이번 출력 바이트 동일성은 그 기존 변환의 타이밍 보존을 뜻하며 음질 개선이나
동시 음색 보존을 입증하지 않는다. 음색 단계에서 CH3 혼합·다른 타격음 근사 등을 동일 장면으로
비교하되 효과음이나 음악을 임의로 생략해 성능을 얻지 않는다.

## 계측 경계와 검증

외부 Mesen Lua는 원본/후보 ROM에서 CPU가 대기 요청을 처음 읽는 시점부터 요청 완료까지를 읽기 전용으로 계측한다.
이 전체 요청에는 cold-load, 원작 상태 진행과 그래픽 캐시 교체, present, 전송/게시 대기가 포함된다.
기존 party_max_prepare는 present만 측정하므로 두 수치를 혼용하지 않는다.

비용은 오디오 생산자, 전송·팔레트 함수의 비오디오 경과, 석화 함수의 비오디오·비전송 경과,
나머지로 배타 분류한다. IRQ 시간은 당시 실행 중인 분류에 포함된다. 전송 분류는 순수 DMA 시간이나
VBlank 대기만의 값이 아니다. 함수 복귀는 SDCC 인자 제거를 포함한 스택 위치로 확인한다.
총 사이클과 분류 합, 668요청의 순서·프로필·프레임을 모두 검사한다.
Mesen의 500개 로그 항목 제한을 피하려고 32개 기록씩 묶으며, 초기 프로필을 누락하지 않는다.
디버거가 주 루프 도중 요청을 넣을 수 있으므로 작업 플래그 쓰기나 첫 오디오 호출을 시작점으로
삼으면 요청 일부가 누락된다. 초기 계측의 로그 잘림/늦은 시작 시도는 폐기하고 CPU 읽기 경계로 재실행했다.

고정 Mesen 코어에서 각 실행의 668화면, 원작 상태/패턴/맵/실제 픽셀과 오디오 10,800틱이 일치했다.
오디오 지연·버퍼 부족·잘못된 DMA/래스터 쓰기는 모두 0이다. 기준/후보 표시는 같은 원작
진행을 사용하지만 빨라진 화면 준비로 이후 요청이 만나는 음악 시점은 달라진다. 아래 요청별
비교를 동일 오디오 위상의 단일 함수 비용으로 해석하거나 모든 개별 요청이 빨라졌다고 주장하지 않는다.

전송 바이트는 줄었어도 대기 포함 전송 함수의 합계 시간은 늘었다. 인터럽트/음악 위상과
팔레트 VBlank 대기가 포함되므로 전송 바이트 감소를 같은 비율의 시간 감소로 주장하지 않는다.
현재 상태 진행 최악 요청은 profile 0/frame 119이며, 오디오 414.107ms, 전송·팔레트 150.500ms,
석화 200.602ms, 나머지 15.562ms다. 이전 최악은 profile 0/frame 117이었다.

**초기 로딩은 500ms 예산 미달성이다.** 후보 최악 2725.464ms 중 오디오 1592.653ms,
전송·팔레트의 비오디오 경과 1039.298ms, 나머지 93.513ms였다. 이 진단의 로딩은
프로필 전체 초기화이며 최종 탐색→전투 진입 구현 완료를 뜻하지 않는다. loader는 양쪽 맵의
ID/속성 4096바이트 초기화, 적 자산, 아군 패턴 4096바이트, 지형/팔레트를 따로 처리한다.
작은 팔레트 요청의 반복 VBlank 대기와 협력 오디오 보충이 남아 있다. 디버거가 주 루프 중간에
요청을 넣을 수 있으므로 loader 진입 자체가 작업 플래그/보충 계약을 확정하도록 하는 개선도
검토한다. 진입 오디오 위상을 고정한 비교와 현재 화면/비활성 자원의 수명 검증을 다음 관문으로 둔다.

자동 대기는 같은 오디오 종료 시점까지 실행하므로 후보의 게시 횟수가 더 많다.
지연 게시 누계 1497→2066만으로 악화/개선을 판단하지 않고 최대 간격 8→5와 준비 시간을 함께 본다.
원작 속도 달성, 정적인 60fps, 500ms 진입 완료로 세지 않는다.

기존 혼란 회귀는 642화면/10,800틱 일치, 최대 present 274.902→234.619ms,
최대 게시 간격 7→5다. 호스트 154검사와 실제 링크된 오디오 출력 오브젝트의 순서 포함
8192대조도 통과했다. 출력 오브젝트 SHA-256:
`55eeff1b2bba4c52618c938098ec4d0ce7a8ed18226d9e31e18768fcd1c4e172`.

기준 표시 ROM: `556307c5774d72407a5cd8d06edc311a6d6cd2925439918eb46a0c7bc2febc92`.
후보 표시 ROM: `776bac0d0e07fabd03aa005b813a067ddd4f9fe19cb749920ce2e3419d9e1499`.
회귀 표시 ROM: `8689db56d10cbda0a68d4d962672f38d35cbbb1cd5a8102d1c854e828e649280`.
공개 허용 소스 501개만 복사한 별도 디렉터리에서 표시/함수 대조/오차 주입 ROM 세 개와
보고서가 바이트 단위로 재현됐다. 입력 ROM과 고정 도구 경로는 비공개 local.json으로 공급했다.

재현 명령:

```text
npm test
npm run build:battle-stone-overlap
npm run verify:battle-preparation
node tools/verify-audio-output.mjs --resident
npm run build:battle-confusion
npm run verify:battle-confusion
node tools/export-source.mjs --check
```

보스 실제 상주 표시, 다른 열로 이동한 석화 이력, 창·포격·숫자의 전체 통합,
일반 게임 진행과 실기·청취 검증은 미완료다. 이번 준비 최적화를 전체 전투 완료로 세지 않는다.
원본 ROM·추출 데이터·생성 ROM·비교 캡처·계측 원문은 비공개이며 소스와 검증 규칙만 배포한다.

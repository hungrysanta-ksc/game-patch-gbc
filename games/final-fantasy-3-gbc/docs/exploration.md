# 원작 일반맵 이동과 NPC 대화 연결

`build/exploration/ff3-exploration.gbc`는 원본 ROM에서 일반맵 29, NPC 배치,
플레이어 그림·포즈·팔레트, 충돌 속성, NPC 조건·이벤트·문자열, 음악을 빌드한다.
방향키로 이동하고 앞 칸 NPC에게 A로 말을 건다. 대화 중 A/B로 페이지를 넘기고
이벤트가 끝나면 같은 위치·방향의 탐색으로 돌아온다. 한글은 기존 비공개 번역
대응표와 7×7 글꼴을 사용한다. 개발 시작 위치 `(10,10)`은 검증 경로를 위한
직행 지점이며, 원작 새 게임의 시작 위치나 진행 완료를 뜻하지 않는다.
필드 RNG 시작 시드는 이 검증 진입에서 0/0으로 고정하며, 이후 소비와 갱신은
기존 원작 RNG 구현을 사용한다. 새 게임 전체의 난수 이력을 재현했다는 뜻은 아니다.

## 원작 소비자와 적용 범위

참조는 기존에 고정한 `everything8215/ff3`의 `ff3j.asm`과 지원 일본어 ROM이다.
빌드와 검증은 원본 바이트를 사용하며 주석/역어셈블리 파일 자체에 의존하지 않는다.

| 원작 위치 | 연결한 동작 |
|---|---|
| 3F/E32E, E36E..E393 | 이전 A 래치 확인, 방향 갱신, 충돌 시에도 방향 유지, 이동 시작 |
| 3F/E4E9..E54B | 앞 칸, 6비트 좌표 랩, 맵 밖 기본 타일, 두 바이트 충돌 속성 |
| 3F/E3F1..E493 | NPC 예약 위치의 이동 차단과 물리 위치의 접촉 표시를 구분 |
| 3F/E494..E4E8 | NPC 반 칸 반올림, 높이 0/3 예외, 첫 일치 슬롯, 얼굴 돌리기 플래그 |
| 3F/E3B4..E3EF | 계단·다리·높이 층·벽 판정과 실패 시 속성 복구 |
| 3F/E58F..E668, E900 | 방향별 1픽셀 이동, 음수 방향의 선행 타일 변경, 반 칸 우선순위 |
| 3D/BDB9, 3E/C711 | 원작 필드 RNG를 소비하는 일반맵 인카운트 검사. 맵 29의 원작 확률은 0 |
| 3E/D8D3..D97B, DC1A..DC69 | 원본 크기 플레이어, 걷기 프레임·흔들림·반전·배경 우선순위 |
| 3A/9091, 9050 | 원작 초기 파티 상태에 따른 플레이어 팔레트 |
| 3B/B2C6..B2FA | 대화 상대의 일회성 반대 방향 포즈 |
| 3F/E9BB 이후 | 기존 원작 NPC 조건 → 지원 이벤트 → 한글 대사 → 탐색 복귀 |

플레이어의 그림은 원본 16×16이며 축소하지 않는다. GBC 화면에서는 기준점을
`(72,61)`로 옮기고 카메라가 따라간다. 원작의 위치·방향·서브픽셀을 유지하며
논리 시간과 화면 제출을 분리한다. 화면 준비 중 지연된 논리 틱은 최대 8개씩
따라잡고, 대화 표시 중에는 이동을 멈춘다. 대화를 닫을 때 지난 이동 시간을
한꺼번에 적용하지 않는다.

NPC 자율 이동 AI, 동행 NPC, 차량/월드맵, 상태별 맵 초기화, 문·보물상자·출입구,
전투 진입, 독/바닥 피해, 메뉴와 캐릭터 교대는 이번 소비자가 아니다. NPC는
원작 초기 배치에 서 있다. 지원하지 않는 타일·메뉴·인카운트·피해 경로를 만나면
`field.error`로 중단하고 오디오는 계속 서비스한다. B/Start/Select를 대화 버튼으로
바꾸지 않는다. 오류 번호는 1=확장 타일, 2=트리거, 3=미지원 버튼 소비자,
4=전투 요청, 5=피해, 6=OAM 총량, 7=자산, 8=카메라 불연속, 9=스캔라인,
10=메모리 보호다. 기존 `asset_error`/`npc_error`/`text_error`도 별도로 유지한다.

## 표시와 오디오 예산

32×32 BG 링에 진입하는 행/열만 업데이트한다. 새 줄은 화면 밖 여유 공간에
작성하고, 열은 타일/속성 4쌍마다 짧은 임계 구간을 끝내 오디오 TIMER를 허용한다.
열의 고정 주소 전송은 SM83 코드로 처리하며, 연속된 행은 한 VBlank에서
32바이트 타일/속성 GDMA를 모두 수행한다. 두 경로 모두 IRQ를 막은 뒤 LY와
STAT 모드 1을 확인한다. 열은 LY 150, 행은 LY 148까지만 시작한다.
주 실행부에서 VBlank를 기다리는 방식은 오디오 생산자가 바쁠 때 갱신을 놓쳤다.
따라서 실제 전송은 고정 ROM의 VBlank 콜백에서 진행한다. 두 OAM 버퍼 중 비활성
버퍼에 플레이어와 NPC를 준비하고 다음 VBlank의 기본 GBDK DMA와 같은 시점에
SCX/SCY를 반영한다. 초기 로딩 이후 LCD를 끄지 않는다.

이동 중에는 제출 후 기다리지 않는다. `pending`과 `upload_pending`이 해제되기
전에는 다음 표시 작업을 시작하지 않아 OAM/배경 버퍼 소유권을 유지한다.
그동안 논리 이동과 오디오는 계속 진행하며, 표시할 변화는 `render_dirty`에
남겨 충돌 시 방향 전환도 유실하지 않는다. 배경 링의 여유 4타일 때문에 새로
예약한 줄은 현재 뷰포트 밖에 있다. 대화 시작/종료는 기존 창 작업 공간과의
전환점이므로 예약 전송을 완료한 뒤 진행한다.

원작 포즈는 빌드 시 GBC의 사분면 순서와 속성 비트로 변환한다. 화면 안에
있는 16×16 객체는 네 스프라이트를 바로 쓰고, 가장자리는 원작 순서대로
개별 클리핑한다. 자세/반전/우선순위는 바꾸지 않는다. 스캔라인 예산 검사는
계속 유지하되 반복 계산과 메모리 접근을 줄였다.

- 코드 은행 9: 판정/이동. 은행 10: 배경 링과 객체 표시. IRQ는 고정 ROM.
- `$DB70..DBB2`: 이동 상태와 계측 67바이트, `$DBBF`까지 예약.
- `$DBC0..DBFF`: 독립 BG 전송 버퍼 64바이트. 한글/OAM 계산 작업 공간과 분리.
- `$DC00..DC9F`: 두 번째 OAM 160바이트.
- `$DCA0..DCAF`: 새 스택 경계 보호. `$DCB0..DFFF`: 스택 여유 848바이트.
- 기존 맵/한글 작업 공간, 오디오 큐, 원작 상태 1KiB와 ROM 은행 계약 유지.
- 플레이어 패턴은 VRAM 은행 1의 `$8C00..8CFF`, OBJ 팔레트 2/3.
  NPC 패턴/팔레트 및 한글 패턴과 겹치지 않는다.

OAM DMA의 HRAM 대기와 IRQ 보호는 고정 GBDK 4.5.0 기본 핸들러를 사용한다.
사양 근거: [Pan Docs VRAM/OAM 접근](https://github.com/gbdev/pandocs/blob/master/src/Accessing_VRAM_and_OAM.md),
[Pan Docs OAM DMA](https://github.com/gbdev/pandocs/blob/master/src/OAM_DMA_Transfer.md),
고정 도구체인의 `gb.h`/VBlank 구현. 이번 관측은 고정 Mesen Core의 실행 결과이며
실기 인증이나 음색 개선의 완료로 계산하지 않는다.

## 재현 명령

```powershell
npm run build:exploration
node tools/build-exploration-verifier.mjs
npm run verify:exploration-units
npm run verify:exploration
npm test
node tools/export-source.mjs --check
```

함수 비교는 미수정 6502 명령을 실행해 기대값을 만든 뒤 같은 입력을 GBC에
전달한다. 실제 조작 검증은 별도로 ROM을 다시 시작하고 방향키/A 입력만으로
접근·충돌·대화·복귀·재접근을 수행한다. 위치나 대화 요청 변수를 직접 써서
게임플레이 통과를 만들지 않는다. 오디오 재시작 명령은 반복 가능한 동일 부하
조건을 위한 계측 입력이다. 기본 실행에서는 원작 맵 선택기의 음악을 계속 재생한다.

독립 Lua 관측은 실제 VRAM/팔레트/OAM DMA/SCX/SCY/APU 쓰기를 검사한다.
플레이어와 NPC OAM 기대값은 원작 렌더러에서 가져오며, 원작 자산에서 만든
예상 픽셀과 에뮬레이터 스크린샷을 비교한다. 한글 창도 원작이 선택한 문자열의
검수 번역을 확장한 결과와 비교한다. 원시 관측·스크린샷·추출 표·생성 ROM은
`build/`, `evidence/`, `.local/`에만 저장하고 소스 배포에서 제외한다.

  기존 검증본과 같다. 기존 정적 텍스트/대사 진단의 동작은 변경하지 않는다.

함수 비교·개발 진입에서의 버튼 검증·전체 게임 정상 진행을 서로 구분한다.
위 결과는 이번 소비자와 선택된 맵의 범위이며 NPC AI/트리거/전투까지 완료됐다는

### 지연 원인과 채택하지 않은 변경

이전 ROM `23dc4484…`도 같은 버튼 경로와 추가 관측기로 다시 실행했다.
아래 수치는 같은 Mesen Core/음악 부하의 비교이며, 화면 상태 예약의 새 바이트를
읽는 조건만 구버전 관측기에서 제외했다. 원시 결과는 로컬
`evidence/exploration/movement-comparison.json`에 남긴다.

| 측정 범위 | 이전 | 최적화 후 |
|---|---:|---:|
| 표시 함수 전체 최대(기존에는 대기 포함) | 202.6ms | 17.6ms |
| 준비 시작 → 실제 SCX 반영 최대 | 171.0ms | 32.9ms |
| 준비 시작 → 실제 SCX 반영 95백분위 상한 | 75ms | 28ms |
| 연속 이동 중 스크롤 갱신 관측 간격 최대 | 201.2ms | 83.7ms |
| 연속 이동 중 스크롤 갱신 관측 간격 95백분위 | 100.7ms | 50.2ms |

스크롤 간격은 프레임 단위 관측이므로 약 한 프레임의 표본화 단위가 있다.
속도가 0이 되거나 대화로 들어간 구간은 제외하고 연속 이동의 변경 간격만 센다.
논리 이동 횟수가 늘어난 것을 속도 변경으로 해석하지 않는다. 조작 경로는 목표
칸까지 기다린 뒤 방향을 바꾸므로 표시/처리 지연이 줄면 반복 구간의 횟수도 달라진다.

이전 PR #11의 CPU 표시 작업 최악은 202.6ms였다. 배경 줄 전송과 OAM 제출을
각각 기다리며 오디오 큐를 채우던 경로, 런타임 포즈 변환/객체 예산 계산,
매 타이머 웨이크업마다 수행하던 보호 구역 검사가 겹쳤다. 이번에는 비동기
소유권 관리와 전송/객체 계산을 개선하고 보호 검사는 논리 틱 경계로 옮겼다.

오디오 생산량을 두 원작 틱 정도로 줄이는 실험은 긴 효과음 부하에서 마감
지연을 일으켰으므로 폐기했다. 최종 `audio-native.c`와 오디오 IRQ는 이전
버전 그대로이며 약 세 틱의 선행 준비를 유지한다. 후속 최적화에서는 남은
50~84ms 갱신 간격의 원인을 별도로 줄여야 하며, 음악 버퍼를 희생하거나
원작 이동 속도를 낮춰 통과시키지 않는다.

## 후속: 오디오 생산 중 이동 화면 정체 개선

현재 탐색 ROM SHA-256:
`cd6e55da34a2ef49a4d03e66e93cff500437da441c676b3137318b2e9af1833a`.
이 절이 최신 결과이며 위의 PR #11/#12 수치는 비교 기준으로 보존한다.

`native_busy`의 시작/종료를 독립 Lua로 관측하니, 기존 오디오 생산 호출이
최대 81.424ms 동안 반환하지 않았다. 이미 예약된 전송은 IRQ에서 처리되지만,
새 이동 상태를 그리는 메인 루프가 그동안 실행되지 못했다. 원작 효과음 7을
시작하는 부하에서도 긴 갱신 간격이 관측됐다.

1. 매 여덟 원작 틱마다 공개하는 216바이트 상태와 12바이트 메타데이터를
   연속 복사로 바꿨다. 기존 인덱스 루프가 바이트마다 포인터를 재계산하는
   생성 SM83 코드를 확인했다. 이 변경만으로 생산 최대 66.668ms,
   갱신 간격 95백분위 33.5ms까지 개선됐지만 최대 간격은 83.7ms가 남았다.
2. 소리 데이터/변환 표 조회에서 반복적인 범용 범위 검사와 2바이트 복사를
   줄였다. 빌더가 검증한 ROM 은행 1..5의 8KiB 및 은행 6의 4,128바이트
   계약 안에서만 직접 읽는다. 음정은 0..2047, 잡음 인덱스는 0..15만
   빠른 경로를 사용한다. 나머지 인수는 기존 검사 경로로 보내며, 잘못된
   원작 은행의 오류와 호출자의 ROM 은행 복원을 유지한다.

오디오 큐 용량·선행 준비, 악보/반복/엔벌로프·템포·페이드, 출력 변환 표,
타이머 IRQ, 이동/충돌/방향 코드와 60.0988Hz 논리 시계는 변경하지 않았다.
검증 스냅샷은 같은 완료 이벤트에서 같은 바이트를 비활성 버퍼에 쓰고 마지막에
공개 번호를 바꾼다. 샘플 빈도를 낮추거나 검사를 제거해서 얻은 개선이 아니다.

| 측정 범위 | PR #12 기준 | 현재 |
|---|---:|---:|
| 오디오 생산 호출 최대 | 81.424ms | 50.805ms |
| 이동 중 스크롤 갱신 간격 최대 | 83.7ms | 50.4ms |
| 이동 중 스크롤 갱신 간격 95백분위 | 50.2ms | 33.5ms |
| 준비 시작 → 실제 SCX 반영 최대 | 32.887ms | 32.795ms |
| CPU 표시 작업 전체 최대 | 17.6ms | 16.8ms |

현재 실행은 7,188 관측 프레임, 실제 화면 반영 4,266회다. 오디오 생산 호출
57,708회를 관측했으며 짝 누락은 0이었다. 연속 이동 98.01초에서 논리 시간의
차이는 12.5ms였다. 갱신 간격은 프레임 단위 관측이고 함수 전체 지연과 다르다.
60fps 고정 갱신은 아직 보장하지 않는다.

- 원작 비교 4,288건, 실제 버튼 대화/복귀 3회와 381칸 이동 통과.
- 스크린샷 12장/276,480픽셀 일치. 영상 쓰기 79,344회, OAM DMA 7,190회,
  스크롤 레지스터 쓰기 8,532회. 잘못된 영상/OAM/스크롤 쓰기와 LCD-off 0.
- 원작 오디오 7,200틱/21,366이벤트, 지연·큐 고갈 0. 실제 APU 쓰기
  30,938회/해시 16366으로 기준과 일치. 메모리 보호 구역 유지.
- 기존 호스트 검사 30개 통과. 공유 오디오 변경은 대사창 및 사운드 전용/
  맵 이벤트 소비자도 별도로 검증하며 결과는 각 검증 문서에 기록한다.

회귀 기준은 실제 반영 최대 35ms, CPU 표시 최대 20ms와 함께 **이동 갱신
간격 최대 55ms/95백분위 35ms, 오디오 생산 최대 55ms**를 검사한다.
일반맵 전체의 성능 보장으로 확대하지 않으며 NPC AI·동행 통합 때 같은 기준으로
부하를 다시 확인한다. 원시 결과는 로컬 `evidence/exploration/`에 보존한다.

같은 공급 코드의 대사창 검증도 82장/1,889,280픽셀과 한글 2,350자를 대조해
통과했다. 부팅 음악이 검사 재시작 전 내보낸 출력은 별도 집계하고 실제 재시작부터
원작 쓰기 횟수/해시를 대조하도록 관측 경계를 고쳤다. 탐색은 재시작 전 쓰기 0,
대사창은 7회였으며 재시작 후에는 양쪽 모두 30,938회/16366으로 일치했다.
사운드 전용 3,600틱 및 맵 이벤트 6회 반복 검증도 지연·큐 고갈 0으로 통과했다.
공개 허용 소스 182개와 명시적 외부 입력만으로 탐색/대사 오디오/정적 대사/
텍스트/사운드 전용/맵 이벤트 ROM 여섯 종류를 바이트 단위로 재현한다.

## 일반 NPC 연결 후

후속 [일반 NPC 이동·애니메이션](npc-motion.md)에서 원작의 무작위 이동, 목적지
예약 충돌, 연속 포즈와 대화 중 정지/복귀를 연결했다. 최종 원작 비교는 8,640건이며,
NPC가 움직이는 부하에서도 갱신 간격 최대 50.420ms / 95백분위 33.545ms를
검증했다. 표시 CPU 16.602ms, 실제 SCX 반영 31.670ms, 오디오 생산 32.096ms다.
원작 음악/효과음/페이드 7,200틱과 실제 APU 쓰기는 동일하고 지연·큐 고갈은 0이다.

기준으로 한다. 위 PR #13 수치와 182개 파일 수는 그때의 결과이며 현재 공개
소스 목록은 186개다.

# 보스 등장 블록의 상주 화면 연결

기준: PR 69 병합 `6eab5cb2615fa7374f00e56d61f29aca8a27217a`, 2026-11-26.
원작 자원 수명 등록의 다음 단계로 `B479` 이후 보스 CHR 시프트를 실제 GBC BG/OBJ에 연결한다.
일반 적 28×28, 아군 원본 크기, V6 좌표 변환은 바꾸지 않는다.

## 원작 구조와 변환 경계

| 근거 | 유지하는 동작 | GBC에서 달라지는 부분 |
|---|---|---|
| `2F/A3B8`, `ff3j.asm:4200` | 원작 포인터 로더로 보스 그래픽 주소를 얻음 | 원본 바이트는 ROM에 상주하고 대상 셀의 공간 색인만 생성 |
| `2F/BE7F`, `ff3j.asm:7830` | 그래픽별 64바이트 블록 개수 | 블록별로 영향을 받는 GBC 셀 목록을 함께 저장 |
| `2F/BE97..BF6F`, `ff3j.asm:7835` 이후 | 각 블록의 7→0 시프트, 짝수/홀수 행 방향, 백어택 반전, 완료 후 정규 진열 | 7/8 축소가 NES/GBC 타일 경계를 다르게 만들므로 해당 셀만 변환 |
| `B304..B330`, `B52A` | 등장 완료 뒤 상태 그래픽 준비, 표시 게이트와 카운터 | 아군·상태 OBJ와 보스 색 보정 OBJ를 같은 40개 OAM에 게시 |

실행 중 프레임 번호로 완성 그림을 찾지 않는다. 원작 `Ff3EntryTail`의 블록/시프트가 작업을
요청한다. 셀의 64픽셀마다 원본 CHR 주소·비트·팔레트 소유자를 나타내는 2바이트 색인을 사용한다.
현재 블록 이전은 확정된 원본, 현재 블록은 원작 시프트, 이후는 초기 빈 CHR로 읽는다.
매 화면의 전체 보스 이미지나 2,304바이트 CHR 복사본을 WRAM에 유지하지 않는다.

색인 생성은 그림이 가질 수 있는 8개 시프트의 색을 조사한다. BG 팔레트 2는 지형,
3은 메뉴로 예약한다. 기존 보스 팔레트로 부족한 셀은 BG 4..7에 정확히 같은 색을 배치하고,
한 팔레트에 안 들어가는 셀만 원본 색의 보조 OBJ를 쓴다. 색을 삭제하거나 근사하지 않는다.

## 수명과 한도

실제 편성에 연결된 보스 그래픽 20종 × 정면/백어택에서 최대 셀 128개,
한 원작 블록의 최대 변경 셀 14개, 보조 OBJ 최대 8개다. 아군 24개와 상태 아이콘 8개를
합쳐 OAM 40개 이내다. 이는 공격 효과·피해 숫자까지 동시에 들어간다는 증명이 아니다.
별도 팔레트는 최대 3개이며 메뉴 팔레트 3을 빌려 쓰지 않는다.

GBC VRAM bank 1의 0번은 공용 빈 타일, 1..20은 지형이다. 보스는 21..255를 사용한다.
현재 표시 페이지가 참조하는 번호를 먼저 예약하고, 바뀐 셀을 빈 번호에 만들어 다음 페이지에 연결한다.
타일/맵 준비가 끝난 뒤 VBlank에서 BG 페이지와 OAM을 함께 게시한다. 등장 전 스크롤은
BG와 OAM 페이지를 독립적으로 사용하므로 첫 보스 프레임은 실제 비활성 BG 페이지를 기준으로
선택한다. OAM 번호로 선택하던 후보는 픽셀이 일치해도 활성 맵 쓰기 감사에서 실패해 수정했다.
사용하지 않는 페이지는
직전 차이 행과 이번 변경 행만 복구한다. 처음 쓰는 페이지는 전 행의 소유권을 초기화한다.
전체 셀을 매 행마다 검색하지 않도록 행별 색인과 최대 8개의 보조 OBJ 목록은 빌드 때 만든다.

임시 바인딩 128바이트·출력 32바이트·예약 표 256바이트는 기존 704바이트 작업 공간을 재사용한다.
두 페이지의 셀 번호 272바이트는 화면 수명에 걸쳐 유지되므로 작업 공간에 두지 않는다.
메뉴/아군의 bank 0 그래픽을 보스 변환용으로 쓰지 않는다. 보스 ROM은 시험 프로필의 공간 색인 때문에
64뱅크를 사용하지만, 최종 전체 게임 ROM 크기를 확정한 것은 아니다.

## 검증 범위

호스트 검사는 40프로필의 4,720단계 전체에서 실제 6502 실행 후 CHR·네임테이블을 직접 읽어
대상 픽셀과 비교한다. 바인딩 생성/시프트 함수를 참조 정답으로 재사용하지 않는다.
큰 백어택 보스의 원작 실행은 매 블록마다 비트 반전 표를 다시 만드는 비용이 있어,
전용 관측에서만 기존 후반부 검사와 같은 600만 명령 상한을 사용한다. 일반 관측은 300만을 유지한다.

GBC 시험은 최대 128셀/288시프트의 그래픽 8(편성 376)과 최대 8보조 OBJ의 그래픽 19(편성 359)를
정면/백어택으로 실행한다. 원작 OAM/상태, 실제 160×144 픽셀, VRAM 셀 내용,
표시 중 페이지/타일을 수정하지 않는지, 음악·효과음·페이드를 각각 검사한다.
완성 프레임은 로컬 검증용이며 배포 소스나 실행 ROM의 프레임 입력으로 넣지 않는다.

첫 구현에서는 상태 표시 전환 중 오디오 버퍼 부족이 발생했다. 셀이 바뀌지 않아도 보조 OBJ를 위해
전체 셀을 순회하던 비용을 없애고, 맵 행 검색을 행별 색인으로 바꿨다. 이것만으로는 백어택의
상태 활성화 시점이 안전하지 않았다. 원작 OAM·상태 처리 구간은 기존 3틱 준비량을 유지하고
OAM 생성/좌표 변환/보스 준비 사이에 서비스한다. 보스의 짧은 픽셀 작업은 2틱 양보를 유지하며
16픽셀마다 서비스한다. 원작 음악 명령·출력 패킷을 생략하거나 타이머를 늦추지 않는다.
두 실패의 프레임/오디오 관측은 로컬에 보존한다.

최초 6회 반복 오디오 시험에서는 수동 988화면 전체 동안 버퍼 부족 0을 확인했지만,
이후 연속 표시 관측이 390 DMA에 그쳐 기존 500회 관문에 미달했다. 관문을 낮추지 않고
진단 음악·효과음·페이드 일정만 8회로 늘린다. 이는 원작 음악이나 게임 속도 변경이 아니다.
전체 오디오 일정 길이에 맞춰 검증기의 남은 프레임 상한도 계산한다.

최종 Mesen 실행에서 988화면·원작 오디오 28,800틱(시험 8회)을 통과했다.
원작 OAM/상태·모든 표시 픽셀·타일 내용이 일치하며 오디오 지연/버퍼 부족, 잘못된 DMA,
활성 보스 타일/맵 쓰기는 모두 0이다. 원작 보스 시프트 720회, 실제 한 줄 OBJ 최대 8개다.
보스 패턴 99,584바이트, 맵 103,808바이트가 전송됐다. 맵 수치는 최초 상주 맵 준비를 포함한다.
지형의 별도 640바이트를 보스 패턴으로 잘못 집계하지 않는다. 명령 대기 연속 관측 3,064 DMA 동안
패턴/맵 재전송은 0이다. 정적 WRAM 끝은 $CC86, 예약 구간 $D000까지 890바이트가 남는다.

실제 화면 준비 함수 최대는 740.479ms다. 전체 요청 비용은 상태 진행/오디오/전송/게시까지 포함하여
최대 745.272ms(프로필 1, 원작 관측 31)이며, 오디오 420.633ms,
셀 처리 123.762ms, 전송 183.308ms, 나머지 17.569ms다.
최초 준비는 630.424..702.026ms다. 초기 500ms와 원작 프레임 속도는 미달성이다.
공유 계측 JSON의 historical `stoneMs` 열은 이 모드에서 보스 셀 처리 비용이다.
다음은 행별 비트 선택 표·연속 타일 전송과 실제 원작 창의 동시 자원 검증이다. 이번 연결을 속도 완성으로 세지 않는다.

기존 혼란/석화 668화면·10,800틱, 요청마다 작업 공간 덮어쓰기 회귀도 통과했다.
해당 ROM은 최종 보스 전용 수정 뒤에도 `204b82ea0df2342b4867417f5df8bbb3e259a00c46569aa79cf1692afa9c6a76`으로 동일하다.
호스트 162검사 및 최종 관련 재검사, 배포 allowlist 524파일의 독립 빌드가 통과했다.
보스 ROM SHA-256: `2be04b0ddf9bdb7dfa701534b2f4276d4169e0092351663bf3c20a3115719af0`.
빌드 보고서 SHA-256: `af0fa31c7b105bbf3e1ec13febc168ca80d3d4c722ea2c85a3b171cc543e52cc`.
모든 화면 관측은 원작의 논리 대기 순서별 비교이며, 정상 게임에서 원작 속도로 실행된다는 의미가 아니다.

## 남은 통합

이번 경로는 보스 등장과 비석화 상태 아이콘까지다. 석화/혼란과 보스의 동시 사용,
실제 한글 메시지·HP·명령/아이템 창, 포격·공격/숫자 및 특수 이벤트 복귀를 완료로 세지 않는다.
창의 초기 리소스/열기/닫기 계약과 도가·우네·가루다 등은
[자원·이벤트 등록부](battle-resource-contracts.md)를 계속 정본으로 사용한다.
다음 통합은 같은 예약표에 원작 창 5종과 한글 글리프 갱신을 연결하고, 원작 호출/닫기 시점 및
HP·상태·숫자와의 공존을 검사하는 것이다. 초기 진입 500ms와 원작 프레임 속도도 별도 관문으로 유지한다.

재현: `npm run build:battle-boss`, `npm run verify:battle-boss`,
`node --test tests/battle-boss-cells.test.mjs`. 원본 ROM·추출 자산·번역·실행 증거는 로컬 전용이다.

# 변경 객체의 스캔라인 한도 검사 비용

기준은 PR 82 병합 `03fb3ff642420accd4492ec6dfa14ab8f3d4164c`다.
원작 행동의 자원 수명과 객체 갱신 순서를 유지하면서 GBC에서 추가로 필요한
객체 한도 검사 비용만 줄인다. 음악·효과음 엔진과 자원 로드 시점은 바꾸지 않는다.

## 원작 구조와 GBC에서 필요한 검사

- `2F/B24F..B258`: 전진 → `A9CF` 직업 그림 → `A8EA` 양손 무기 그림 →
  `AEF0` 애니메이션 순서다. `A8EA..A962`는 양손 속성/그림/팔레트를 읽어
  `A942/A953 → A1B9`로 각각 로드한다. 매 프레임 재로드하는 구조가 아니다.
- `33/A05E → A42B`는 공격 scratch의 160바이트를 지우고, `A065/A06E`는
  공격자와 무기 객체의 생성 순서를 구분한다. `A3DD..A3EB`의 공격자/애니메이션
  갱신은 `90EA/9299`로 이어진다. `A3F5`는 캐릭터별 24바이트 OAM 영역을 지정하며
  `A3F9..A41C`가 해당 캐릭터 영역을 초기화한다. 다른 객체의 수명과 구분된다.
- `33/A365..A3DA`는 원작 명중 상한과 8프레임 반복, 효과음 요청, `A3C8 → F8B0`
  게시 순서를 소유한다. 이번 변경은 이 반복·생성·게시 경로를 수정하지 않는다.

기존 GBC 어댑터는 행동 시작 시 유지 객체와 줄별 점유 수를 한 번 만들고,
매 그림에는 변경 객체만 생성한다. 이 구조를 유지한다. 다만
[Pan Docs OAM](https://raw.githubusercontent.com/gbdev/pandocs/master/src/OAM.md)의
40객체/줄당 10객체 한계 때문에, 승인한 V6 좌표와 효과를 합친 뒤 점유를 검사해야 한다.
X가 화면 밖인 객체도 줄 한도에 포함되므로 X나 투명 픽셀로 검사를 생략하지 않는다.
이 GBC 전용 제약을 원작의 게임 로직인 것처럼 옮기지 않는다.

## 원인과 변경

읽기 전용 bank 56 진입/복귀 훅으로 오디오·IRQ 시간을 제외해 측정했다.
최대 양손 검류 조건에서 시작 검사 1회는 8.088ms, 변경 객체 검사 59회는
151.125ms였다. 나머지 그림은 기존 동일 그림 재사용 24회이며 검사를 새로 늘리지 않는다.

고정 SDCC listing에서 안쪽 8줄 루프의 카운터가 스택에 놓이고, 매 줄마다
스택 주소 계산·증가·재조회·루프 비교가 반복되는 것을 확인했다.
`reserve8()`은 같은 8줄을 같은 순서로 증가시키되 고정 길이 조건식으로 표현한다.
11번째 객체가 된 첫 줄에서 즉시 거부하며, 그 이전/이후 줄의 변경 여부도 기존과 같다.
144바이트 기준 점유 복사, 40객체 검사, 좌표 범위, 유지 객체의 순서, 페이지 게시,
원작 픽셀·숫자·RNG와 오디오 서비스 지점은 그대로다. 새 캐시나 RAM은 추가하지 않는다.

## 비교와 해석

| 최대 양손 검류 | PR 82 | 이번 빌드 |
|---|---:|---:|
| 전체 행동 ms | 2177.113 | 2110.175 |
| 최초→최종 실제 DMA ms | 2076.127 | 2025.867 |
| 최대 실제 DMA 간격 ms | 83.956 | 83.956 |
| 변경 객체 검사 CPU ms | 151.125 | 123.209 |
| 시작 검사 CPU ms | 8.088 | 8.088 |
| 그 밖의 준비 CPU ms | 493.186 | 493.536 |

검사 CPU 비용은 약 18.5%, 전체 시간은 약 3.1% 감소했다. 첫 칼질 최대 간격은
개선되지 않았으며 원작 속도 달성을 주장하지 않는다. 행동이 짧아져 그 안에 수행되는
오디오 생산·IRQ 양도 달라진다. 이를 오디오 엔진 자체가 빨라졌다고 해석하지 않는다.
원작의 전체 프레임·반복과 10회 사운드 요청은 보존한다.
bank 56 코드는 `0x26D→0x2B4`(+71바이트), 고정 WRAM 끝은 `0xCEF8`로 같다.
전체 ROM 크기는 변하지 않는다. 작은 코드 증가로 반복 제어를 줄인 선택이다.

`--auto --profile-oam`으로 비용을 재현한다. 프로파일러는 컴파일러 해시와 링크 심벌,
실제 ROM의 고정 명령 바이트와 RET를 확인하고 현재 매핑된 ROM 은행을 검사한다.
오디오/IRQ의 우선 귀속을 유지하며, 호출 수는 실제 준비 수와 같아야 한다.
과거 ROM 비교에는 해당 소스에서 보존한 `--oam-listing <absolute path>`를 지정한다.
ROM에 측정 명령을 삽입하지 않는다. 짧은 `--action-only`는 전체 승인에 사용하지 않는다.

## 경계 검증

기존 10/11객체·40객체·위/아래 가장자리·고정 슬롯·재사용 검사에 더해, 8줄 각각이
첫 초과 줄이 되는 조건을 실행한다. 거부 전 줄은 증가하고 초과 줄은 11이 되며,
뒤의 줄은 손대지 않아야 한다. 실패 후 다음 정상 요청도 통과해야 한다.
같은 8조건에서 정확히 10객체인 경우 모든 줄이 처리됐는지도 확인한다.

## 최종 검증

- GBC에서 위 경계 검사와 원작 OAM 960조건을 실행해 통과했다. 오류를 넣은 원작
  기준 fixture는 첫 조건/바이트의 불일치로 거부됐다. 호스트 관련 검사도 5/5 통과했다.
- 봉 계열 636장, 적 위치·정면/백어택 688장, 무기→숫자 116장, 검류 368장,
  기존 밀집 숫자·공통 호출자 198장: 총 2,006장의 실제 OAM·타일·팔레트·픽셀 일치.
- 위 5회와 자동 검류/봉 계열 2회를 각각 7,200틱 실행했다. 원작 음악/동적 효과음
  요청·소비 해시 일치, underrun·late·VRAM/OAM·메모리 가드 오류 0.
  두 자동 실행 모두 83게시·10사운드 요청과 실제 DMA 간격 90ms 미만 관문을 통과했다.
  봉 계열 전체 2110.143ms, 최대 DMA 간격 83.956ms다.
- 프로파일러는 이전/현재 ROM과 각각의 listing을 통과시키고, 이전 listing으로 현재
  ROM을 해석하려는 경우 `Linked OAM return`에서 거부했다. 독점 비용의 합과 호출 수를 검사했다.
- 허용 소스 592파일의 별도 빌드에서 ROM/보고서 등 9산출물이 바이트 일치했다.
  원본 ROM·번역·추출 자산·관측 자료는 로컬에만 둔다.

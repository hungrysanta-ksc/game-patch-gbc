# 보스 행 변환·묶음 전송과 한글 창

기준: PR 70 병합 `5bdfa4abba8dd8e00dbfe28f9a4442c8bbcde987`, 2026-11-26.
원본 ROM·번역·폰트와 생성 ROM, 관측 화면은 로컬에만 보관한다.

## 원작 구조와 비용 변경

`2F/BE97..BF6F`의 64바이트 블록, 7→0 시프트, 짝수/홀수 행 방향,
백어택 반전과 단계 확정은 기존 C 실행기를 유지한다. 매 픽셀의 주소/비트 계산을
GBC 한 행이 참조하는 최대 두 원본 바이트와 비트 선택표로 바꾼다.
선택표는 공간 변환만 나타내며 프레임·블록·시프트별 완성 그림을 담지 않는다.
원본 두 비트플레인에 현재 시프트를 적용한 뒤 색별 마스크를 BG/보조 OBJ에 나눈다.

셀당 색인은 128→72바이트다. 대표 128셀 프로필은 기존 16,384바이트 대신
행 프로그램 9,216 + 선택표 3,584바이트, 36셀 프로필은 4,608 대신
2,592 + 2,560바이트다. 작은 프로필에서는 ROM 데이터가 544바이트 늘어난다.
선택표용 ROM 은행 38..41을 쓰지만 전체 진단 ROM은 기존과 같은 64은행이다.
활성 화면이 참조하는 타일을 예약한 뒤 연속 빈 슬롯을 한 번씩 검색하고,
최대 256바이트 패턴 묶음과 최대 4행 맵 묶음으로 보낸다. DMA 임계 구간의
기존 128바이트 상한은 바꾸지 않는다. 전송 바이트 수 자체는 줄이지 않는다.

원본 소스, 화면 상태, 예약 타일과 페이지 서명은 유지한다. 셀 변환 후에는
704바이트 공용 작업 공간을 맵 행 조립에 재사용한다. 그 공간에 장기 수명 상태를
남기지 않으며 게시 전까지 활성 보스 패턴/맵을 쓰지 않는다.

## 실제 한글 창 소비자

원작 `34/8E83`의 다섯 창 사각형, `8D1B` 열기/`8E14` 닫기,
`9BA2..9CE0`의 네 HP 행과 실제 PPU 프레임/팔레트를 사용한다.
V6의 기존 행동창 상단 106px, 7×7 한글, 3px 공백, HP만 5px 숫자를 유지한다.
커서가 필요한 선택창의 103px 상단 계약은 변경하지 않는다.

새 `battle-live-ui.c`는 HP 4행과 열린 창 5개의 텍스트를 보유한다.
열림 조합별 완성 타일 목록은 ROM에 넣지 않는다. 변하지 않는 원작 프레임과
검증된 글리프 사전으로 해당 행만 조립하고 VBlank에 전송한다.
닫을 때는 현재 HP와 남은 창 상태에서 가려졌던 행을 복원한다.
이는 현재 원작 호출 순서에서 검증한 동작이다. 창이 열린 상태의 임의 HP 갱신을
원작 저장 버퍼와 동일하다고 일반화하지 않는다.

BG bank 0의 타일 112..211, BG 팔레트 3, 양쪽 맵의 13..17행을 사용한다.
아군·상태 OBJ 0..111 및 bank 1의 지형/보스 영역과 분리한다.
기존 원작 메뉴 CHR 예약 112..255 중 필요한 영역을 재목적화하며,
문자 원본/프레임은 ROM에 남겨 모든 창 조합을 다시 만들 수 있다.
프레임 테두리는 원본 픽셀에서 만든 2bpp 행 자료(2,212바이트)로 읽고, 글자도 행 마스크로 합성한다.
전체 메뉴 조립은 등장 초반 1..5번째 화면에 한 행씩 분산한다. 첫 화면 로딩에는 추가하지 않는다.
원작 명령 대기 경계에서는 팔레트와 양쪽 맵의 ID/속성 네 묶음만 게시한다.
이후에는 창이나 HP가 겹치는 행만 다시 조립한다.
큰 보스 변환과 메뉴 조립은 같은 작업 공간을 순서대로 쓴다.

HP 창은 원작 등장 종료 후 명령 대기 단계에 연결했다. 메시지는 원작 아이템/독 표시
소비자를 실행해서 관측한 열기·닫기·HP 경계 16개를 디버거 입력으로 실제 GBC에
전달한다. 해당 요청이나 완성 화면은 실행 ROM에 링크하지 않는다.
이는 표시 소비자 연결 검증이며 보스가 그 아이템을 사용하거나 독 피해를 받는
정상 전투를 구현했다는 뜻이 아니다. 전투 계산·행동 호출자 연결은 별도로 남는다.
진단 파티 이름은 사용자 샘플의 한글 이름을 명시적 입력으로 쓰며 일본 ROM의
정식 이름이라고 주장하지 않는다. 번역문 내용이나 승인된 폰트는 변경하지 않았다.

## 재현과 검증

```powershell
node tools/build-battle-party-oam.mjs --boss
node tools/verify-battle-party-video.mjs --boss --costs
node tools/build-battle-party-oam.mjs --windows
node tools/verify-battle-party-video.mjs --windows --costs
npm test
node tools/export-source.mjs --check
```

같은 988화면·720 보스 시프트·28,800 오디오 틱에서 창 없는 경로의 최대 화면 준비는
740.479→333.252ms다. 전체 단계 요청 최대는 745.272→350.830ms이며,
초기 로드 포함 최대는 702.026ms다. 초기 500ms 및 원작 화면 속도는 아직 미달성이다.
보스 패턴 99,584바이트, 맵 103,808바이트와 지형 640바이트는 동일하다.
픽셀/OAM/원작 상태 대조, 음원 이벤트 해시와 타이머 검사, 오디오 부족·늦음·잘못된
DMA·활성 보스 타일 쓰기 0을 확인했다. 타이밍 검증을 음질 개선으로 세지 않는다.

픽셀 단위 테두리 조립 후보는 첫 UI에서 기존 100프레임 준비 제한을 넘겨 채택하지 않았다.
행 조립만 적용한 후보도 첫 UI 요청 1,312.265ms로 비용이 한 경계에 몰렸다.
최종 후보는 테두리 행 복사/글자 마스크, 초기 5행 분산, 맵 20→4묶음 전송을 함께 사용한다.
첫 UI에 맞춰 제한을 늘리거나 원작 프레임·숫자를 생략하지 않았다.
1,004장의 캡처 번호가 세 자리를 넘으면서 검증기 정렬 문제도 발견되어 숫자 순서로 정정했다.

창 포함 최종 ROM은 988개 등장/명령 화면과 메시지/HP 경계 16개, 총 1,004장을
픽셀 단위로 대조했다. 원작 상태/OAM/지형과 28,800 오디오 틱도 통과했다.
오디오 부족·늦음·잘못된 DMA·활성 보스 패턴/맵 쓰기는 0이다.
전체 최대 present 336.426ms, 단계 요청 381.845ms, 초기 로드 703.291ms다.
첫 UI 경계 최대는 381.845ms로 분산 전 1,312.265ms와 구분한다.
메시지/HP 요청 최대 619.658ms에는 관측용 두 프레임 대기도 포함한다.
메뉴 패턴 17,280바이트와 맵 2,560바이트를 별도 소유권으로 검증했다.
정적 WRAM 끝은 $CD2D, $D000 전 여유 723바이트다.

## 남은 통합

원작 행동 호출자의 동적 값과 이 표시 API의 직접 연결, 미관측 3번 창 경로,
보스+석화+무기/마법/피해 숫자 공존, 원작 속도와 초기 로드 지연,
도가/우네·가루다 등 정상 이벤트 전투는 남아 있다.
제품 관문 0/3, R2 전체 통합 0/8을 유지한다.

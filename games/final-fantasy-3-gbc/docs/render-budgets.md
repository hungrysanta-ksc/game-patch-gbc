# R2: 밀집 NPC와 전투 자산 예산 조사

2026-11-23. PR 17 병합 `f8ee57adcdd812b89381194028e71a26bbabc7ef` 이후 첫 R2 묶음.
**8×16으로 바꾸기만 하면 해결된다는 가정은 폐기한다. R2는 아직 미완료이며 R3로 넘어가지 않는다.**
이번 변경은 원작 소비자 조사와 실패를 재현하는 검사기다. 제품 탐색/사운드 실행기는 변경하지 않았다.
그림 누락·깜박임·색 축소 정책을 새로 채택하지 않았다.

후속 [밀집 NPC 합성 후보](npc-composition.md)는 기존 8×8 실패 637개 정지 입력을 색 변경 없이
예산 안에 넣고 GBC 자산 공급을 검증했다. 아래 8×16 실패 수치/ROM은 당시의 재현 기록이며 유지한다.
새 후보의 동적 합성·플레이어/동행·오디오 동시 부하는 여전히 후속 범위다.

## 원작과 대조한 범위

원본은 `spec/source.json`의 일본판 SHA-256
`262a98737975df25fff80ad91090c3da039d2828035c6253140d2c5f3b176ea2`다.
[개발 스킬](development-skills.md)의 고정 FF3 역어셈블리를 주소 안내로 쓰고,
실제 ROM 명령을 `Driver6502`로 실행한다. 이 도구는 전체 NES/스토리 실행기가 아니다.

| 범위 | 원작 소비 코드 / 파일 오프셋 | 검사 결과 |
|---|---|---|
| 전투 편성 512슬롯 | `2F:A02A–A0B7`, `5C010/5C410/5CA10` | 그룹·수량 범위 대조. 최대 수량을 대입해 `9FAA/A31F`의 배치·슬롯 조사, 최대 8마리 |
| 참조 적 224 ID | `A42E→F942`, 보스 `A3B8` | 그래픽 주소/길이 대조. 223 ID 해독, 206은 별도 공급 타일 `$2A` 미해결 |
| 적 속성·팔레트 | `A0E7`, `A86C/A820`, `A6FB` | 해독한 223 ID의 속성 주소와 비트 소비 대조. 4×4 그림의 위쪽 빈 2타일 행도 반영 |
| 무기 88 / 마법 선택 96 | `A8EA–A90F`, `33:AF6F`; `5D0A8/5D1E0` | 원작 선택 결과 대조 |
| 마법 프레임 128 | `33:B7CF`; 포인터 `1718` | 36칸 RLE 해제 결과의 타일·뒤집기 속성 대조. 프레임 11/15는 36조각 |
| 마법 스크립트 91 | `33:B696–B6CA`; 포인터 `CC10` | 실제 256바이트 복사 대조. 스크립트 29/36이 위 36조각 프레임 참조 |
| 기타 전투 전송표 14 | `2F:A15F` | 원시 전송 파라미터 목록. 레코드 0의 길이는 타일맵 행, 나머지는 16바이트 타일 단위 |

총 1,139개 슬롯/ID 사례의 원작 비교이며 속성 검사는 그 안의 223개 그래픽에 추가 적용했다.
512개 전투나 91개 연출의 정상 플레이 완료 수치가 아니다. 수량 상한 조합의 RNG/스토리 도달성,
마법의 실제 대상 위치·연속 프레임·소환·동적 팔레트는 아직 검증하지 않았다.

원작의 이상한 동작도 보존한다. `A143`의 OR 결과는 `$7F`에 저장되지 않아 `A07F`의 호출 경로에서
팔레트 반전으로 쓰이지 않는다. 이전 독립 시제품의 반전 해석을 이번 분석기로 가져오지 않았다.
`B696`의 스크립트 로더도 길이를 `$82`에 저장하지 않아 실제 256바이트를 복사한다.
둘 다 임의로 고치지 않고 원작 결과와 대조한다. MMC3 8KiB 은행과 전송표의 16KiB 은행 쌍을 구분한다.

## 밀집 NPC: 총량과 줄당 한계는 별개

GBC는 OAM 40개, 한 줄에 선택하는 OBJ 10개다. 8×8/8×16 크기는 화면 전체에 공통이며
8×16의 위/아래 타일은 팔레트·우선순위를 공유한다. 투명한 절반도 Y 범위에 들어오면 선택 수를 쓴다.
[Pan Docs OAM 원문](https://raw.githubusercontent.com/gbdev/pandocs/master/src/OAM.md)

768개 맵 선택 × 2,115개 카메라 = **1,624,320개 정지 입력**을 전수 조사했다.
모든 표시 플래그를 켠 진단 입력으로, 현재 포즈만 사용하며 플레이어/동행은 포함하지 않았다.
8×16 후보는 열마다 두 타일의 속성이 같으면 합치고, 다르면 투명 절반을 둔 두 OBJ로 보존한다.
최적 포장 알고리즘이나 제품 적용 결과가 아니다.

| 후보 | 총 OAM 초과 입력 | 줄당 초과 입력 | 최대 총수 / 줄당 |
|---|---:|---:|---:|
| 기존 8×8 | 592 | 45 | 48 / 12 |
| 속성을 보존한 8×16 후보 | 0 | 5,230 | 40 / 20 |

기존 PR 7의 592/45를 재현했다. 8×16은 총수를 줄이지만 투명 패딩과 속성 분리로 줄당 수를 늘린다.
플레이어+동행 16×16 두 명의 보수적 추가 예약은 8×8에서 8 OBJ, 8×16에서 4 OBJ이며,
둘 모두 같은 줄에 최대 4개를 더할 수 있다. 이 예약은 실제 동행 구현이나 정상 공존 증명이 아니다.

실제 픽셀 손실은 선택 수 초과와 구분한다. 원작 초기 플래그를 쓴 두 사례를 독립 GBC ROM으로 재현했다.
카메라 좌표는 8픽셀 타일 단위다.

| world / map / camera | OBJ / 최대 줄당 | 제한 없는 원작 그림과 비교한 실제 손실 |
|---|---:|---:|
| 1 / 87 / (12,0) | 32 / 12 | **158픽셀** |
| 0 / 139 / (0,42) | 22 / 20 | 0픽셀: 겹침으로 가려진 대조 사례 |

두 사례 모두 OAM 선택 전에는 8×16 재포장과 원작 8×8의 모든 픽셀이 같다.
Mesen의 실제 OAM/화면을 독립 픽셀 계산과 비교해 0→1→0 세 화면 69,120픽셀이 일치했다.
검사 통과는 **후보의 실패 양상을 정확히 예측했다는 뜻**이다. 5,230개 모두가 눈에 보이게 깨진다는 뜻도 아니다.
맵 139의 겹침은 이벤트 이동 전 정지 상태이므로 이후 이동까지 안전하다는 근거가 될 수 없다.

역참조도 비공개 등록부에 남겼다. 맵 86/87의 관련 ID 30–34에는 이벤트 50/51/81/82/101의
F4/F5 참조가 있으며, 맵 139의 관련 ID에는 이벤트 72/98/101 참조가 있다.
NPC 조건 분기도 함께 저장했다. 이는 문법상 참조다. F4/F5는 현재 world를 사용하므로
해당 이벤트의 world·실행 순서·동시 표시가 확인되기 전 정상 도달/불가능으로 분류하지 않는다.

## 전투: 색과 OBJ를 함께 풀어야 한다

아군은 승인한 16×24 원본 네 명을 y=10/34/58/82에 둔다. 정지 상태는 8×8에서 24 OBJ,
8×16 패딩에서는 16 OBJ다. 24픽셀 간격에서 32픽셀 패딩이 겹치므로 줄당 최대는 각각 2/4다.
22직업의 원시 42타일/직업, 서로 다른 네 직업의 168타일은 원시 자산량이며
8×16 재포장·패딩 이후 최종 상주 아틀라스 크기를 보장하지 않는다.

원작 파티 24슬롯과 연출 40슬롯은 GBC의 총 40개보다 크다. 마법 36조각+정지 파티 24개만으로도
60개가 된다. 피해 숫자·상태·커서 등은 연출 슬롯을 공유하므로 각각의 최댓값을 무작정 더하지 않는다.
가능성이 있는 다음 후보는 같은 속성의 마법 6×6을 세로로 합쳐 18 OBJ, 파티를 16 OBJ로 만드는 것이다.
기하학적으로 총 34/줄당 10에 들어갈 수 있으나 실제 속성·동시 표시·대상 위치를 아직 증명하지 않았다.

적은 원작에서도 배경 타일을 사용한다. 우선 적 BG/아군·효과 OBJ 구성을 검토하되,
승인한 32→28 중간 축소를 일반형에 7/8로 확장한 **후보**와 144×96→96×64 보스 후보를 조사했다.
모든 크기에 대한 아트 승인을 받은 것으로 간주하지 않는다. 각 이미지의 앵커는 타일에 맞췄다.
원작 두 팔레트의 RGB555 색을 유지한 최근접 축소에서:

- 해독 가능한 고유 그림/팔레트 쌍 250개 중 **161개**에 4색 초과 타일이 생겼다.
- 초과 타일 452개, 한 타일 최대 7색이다. 고블린 32→28 예시도 일부 타일에 5색이 모인다.
- 따라서 한 BG 타일/한 팔레트로 그대로 옮길 수 없다. 과거 시제품의 색 재배정은 일반 변환 정책의 근거로 삼지 않는다.

위 검사는 개별 이미지의 필요조건이다. 편성 배치 후 타일 공유, 화면 전체 8개 BG 팔레트,
공격 시 반짝임·보스의 외부 타일 공급까지 통과했다는 뜻이 아니다.

VRAM은 두 은행 총 768패턴이다. signed BG에서 BG가 접근 가능한 512개와 OBJ가 접근 가능한
512개 중 256개는 공유하므로 합쳐 1,024개로 세지 않는다.
[Pan Docs Tile Data 원문](https://raw.githubusercontent.com/gbdev/pandocs/master/src/Tile_Data.md)
계획용으로 한글 창 116, 상단 40, 적 영역 경계 패딩 포함 224셀을 예약하면 BG 132개가 남고,
OBJ 전용 영역은 256개다. 이는 실제 전투 아틀라스나 8팔레트 공존 검증 결과가 아니다.
적 224셀 전체는 3,584바이트로, 현재 창의 VBlank당 128바이트 할당이면 최소 28 VBlank라는
산술 결과만 얻는다. LCD를 켠 전투 전송/오디오 부하 측정은 아직 없다.

## 재현과 이번 검증

`local.json`의 원본 ROM·고정 GBDK·MesenCore·.NET 경로를 사용한다. 이 검사기는 번역/폰트를 읽지 않는다.
원시 목록·그림·ROM·실행 로그는 `build/`, `evidence/`, `.local/`에만 저장한다.

```powershell
npm run audit:render-budget
npm run build:render-budget
npm run verify:render-budget
npm test
node tools/export-source.mjs --check
```

`build/render-budget/ff3-render-budget.gbc`는 두 장면을 A로 바꾸는 **무음 실패 재현 ROM**이다.
기존 게임/오디오 빌드와 연결하지 않았다. 자동 검사는 디버거로 페이지 요청을 설정하며 조이패드 입력 검사는 아니다.
`scene0-ideal.png`와 `scene0-hardware.png`는 누락 비교용이며 배포하지 않는다.
ROM SHA-256: `cb48f1211940412ed313d19758660fd350616e785b0975297f33e7809d54f922`.
실행 코어 SHA-256: `1ba99d2c848e007c60cbd7fceca058440758eb44837a93a6724d29d72723c994`.
동일 코어의 자동 검사와 캡처 육안 확인이며, 독립 에뮬레이터/실기 검증은 아니다.
투명 패딩·은행 쌍 주소·미해결 타일·잘못된 마법 포인터를 검사하는 회귀도 추가했다.
전체 호스트 검사 33건이 통과했다. 허용 목록 210개 소스만 별도 폴더에 복사하고 외부 ROM/GBDK
경로를 지정해 검사 ROM과 전체 조사 JSON이 바이트 단위로 동일하게 재생성되는 것도 확인했다.
최종 조사 JSON SHA-256은 `021bc0fe839283a79e505f4cbbf9d8ead2c0bf4afe9c49e401e91bc5c938fee0`이다.
기존 제품 실행기/메모리/스케줄러는 변경하지 않아 이번에 제품 ROM의 오디오 회귀를 다시 실행하지 않았다.
새 후보를 제품 전송 경로에 연결할 때 오디오와 은행/가드 검사를 반드시 함께 수행한다.

## 이어서 할 R2 작업

1. world 1/2 맵 86/87의 NPC 30–34와 맵 139의 이벤트를 실행 순서까지 역추적한다.
   정상 공존이 배제되지 않는 입력은 그대로 예산 검사에 남긴다.
2. 밀집 장식/NPC를 BG에 합성하는 후보를 하나 구현해 OAM·우선순위·겹침·이동 복원을 검사한다.
   전체를 8×16으로 바꾸는 방식은 채택하지 않는다. 얼굴/색/우선순위와 원작 표시 순서를 보존해야 한다.
3. 적의 색 초과에는 팔레트 경계를 고려한 좌표 변환 및 BG/OBJ 보조 후보를 비교한다.
   206의 외부 타일 `$2A` 공급도 추적한다. 색/실루엣 손실이 필요하면 먼저 실제 비교안을 만들고 승인받는다.
4. 36조각 마법과 원본 아군의 실제 위상별 슬롯 소유권을 연결해 8×16 후보를 검사한다.
   최대 보스/편성과 한글 창의 최종 VRAM·팔레트·ROM 은행·WRAM 예약을 확정한다.
5. 선정한 후보만 기존 오디오/전송 경로에 연결해 최악 부하를 측정한다.
   초과 입력이 해결되거나 구체적 차단 근거가 확정된 뒤 R2를 닫고 R3로 이동한다.

전체 마법/맵 구현을 R2에서 끝내려는 계획은 아니다. 앞으로의 기능을 불가능한 표시 예산 위에
쌓지 않도록 대표 최악 사례에서 변환/상주 정책을 검증하는 것이 이 묶음의 완료 조건이다.

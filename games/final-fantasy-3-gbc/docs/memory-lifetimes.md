# 메모리 수명과 안전한 WRAM 은행 접근

2026-11-23, R1의 현재 실행기 재배치와 계약. 기준은 PR 16 이후의 탐색·이벤트·대사/사운드 빌드다.
원작 게임 규칙·이동 속도·음원 큐 크기는 바꾸지 않는다. 실제 메뉴/전투 모드 전환은 아직 미구현이며,
이 문서의 전환 조건을 그 소비자가 생길 때 추가 검증해야 한다.

## 재배치

PR 15의 고정 WRAM 끝 `$CFCA`는 `$D000`까지 54바이트를 남겼다. 이 중 오디오 관측용
불변 스냅샷 두 개(232×2바이트)를 WRAM 은행 2로 옮겼다. 원작 GameState 1,024바이트,
오디오 큐 16×64바이트, 음원 실행 상태와 인터럽트 소비 상태는 고정 은행에 유지한다.

은행 1에는 현재 스택이 있으므로, 다른 은행을 선택한 채 C 함수·인터럽트·일반 스택 접근을
실행하면 안 된다. `src/memory.c`는 고정 ROM의 짧은 어셈블리 함수 안에서만 은행 2–7을
선택하고 한 번에 최대 16바이트를 복사한다. 고정 RAM 입력은 직접 전송하며, 은행 1/스택의
입출력은 고정 RAM 중간 버퍼를 거쳐 SVBK=1일 때 접근한다. 반환된 은행 포인터는 없다.

현재 고정 도구의 `CRITICAL`은 DI/EI를 생성한다. 호출 시 IME가 꺼져 있던 경우를 보존하기 위해
이 복사 함수는 IE를 은행 1 스택에 저장하고 0으로 마스킹한 뒤 복원한다. IME는 변경하지 않는다.
다른 은행이 보이는 동안에는 PUSH/POP/CALL/RET/SP 상대 접근이 없으며, 마지막 POP/RET 전에
반드시 은행 1로 돌아온다. 이 기계어 구조와 데이터 피연산자의 고정 WRAM 주소를 빌드에서 검사한다.

첫 구현의 장시간 탐색/이벤트 검사에서는 타이머 시계 오차가 기존 0.5ms 범위를 벗어났다.
탐색 검사에서 약 1.1ms의 지연이 관측됐다. 은행 복사 자체는 80μs 미만이지만 직후 GBDK의
OAM DMA와 초기 VBlank 작업이 이어질 수 있다. 최종 구현은 LY 141–143에서는 호출자의
인터럽트 설정을 유지한 채 기다린 후 복사한다. 원작 시계·큐 목표나 검사 한도를 완화하지 않는다.
후속 이동 검사에서는 범용 중간 버퍼 복사가 생산 시간을 늘려 표시 간격 기준을 넘겼다.
고정 RAM의 스냅샷은 같은 16바이트 전송 함수를 직접 반복하도록 개선해 중복 복사와 C 스택
임시값 처리를 줄인다. 8틱마다 요청한 스냅샷은 큐 보충/양보 이후에 공개하되 창 전송 중에는
미룬다. 정상 탐색 중에는 이동 중이 아니고 다음 논리 마감까지 20타이머틱(약 4.9ms)의 여유가
있을 때만 복사한다. 따라서 부하 중의 진단 요청은 합쳐져 과거와 관측 간격이 같지 않다.
스냅샷의 이벤트 번호·상태는 서로 대응하며, 게임 틱·음원 틱·실제 출력 패킷은 생략하지 않는다.
모든 실제 음원 출력 이벤트는 별도 관측으로 계속 대조한다.

## 실제 배치와 소유권

`tools/memory-layout.mjs`가 최종 링크 심볼을 검사하고 `build/*/report.json.memory`에 아래
반개구간 배치, 고정 영역 잔량, 스택 크기, 전송 함수 기계어를 기록한다. 과거 플랫폼 문서의
`D800` 스택 경계를 현재 탐색 ROM에 적용하지 않는다.

| 4 | 미할당 4KiB | 검사에서 실제 GameState 복사에 사용. 게임 저장 슬롯이 아님 |

| 6–7 | 미할당 8KiB | 검사 중 왕복 복사만 수행 |

`D7EF` 1바이트와 `DA50..DA60` 16바이트는 정렬 여백이다. 빌드는 모든 구간의 인접 관계와
중복을 확인한다. 고정 영역에 최소 한 페이지(256바이트)를 남기는 개발 예산 검사를 추가했다.
이는 전체 전투에 충분하다는 계산이 아니라 고정 영역을 다시 무심코 채우는 것을 막는 변경 검토선이다.

원작 전투 RAM 지도에는 필드 DP 보존, 파티 4×64·몬스터 8×64·소환 64바이트 작업 상태 등도
존재한다. 동행의 네 칸 이력 큐만을 전체 동행 상태 크기로 간주하지 않는다. 원작 RAM 주소를
GBC 고정 RAM에 하나씩 누적 할당하지 않으며, 전체 전투/동행 크기는 소비 코드 이식 때 확정한다.

## 모드 전환 계약

1. GameState와 음원 큐/시계는 모든 모드에서 생존한다. 원작 상태의 변경은 해당 소비자만 수행한다.
2. 현재 모드의 배경·OAM·창 업로드가 끝나고 IRQ가 참조할 버퍼/콜백을 새 모드에 맞게 정리하기
   전에는 활성 작업 공간을 재사용하지 않는다. 은행을 바꿔 DMA 입력을 다른 데이터로 바꾸지 않는다.
3. 메뉴와 필드가 동시에 필요한 상태는 중첩 수명으로 취급한다. 전투가 필드를 중단할 때 보존할
   위치·객체·RNG·이벤트 상태는 원작 소비 코드에 따라 결정한다. 모두 지우거나 전부 동결한다고 가정하지 않는다.
4. 보존 데이터는 은행 번호·오프셋·길이의 저장 핸들로 접근한다. 모드별로 소유 구간을 예약하고
   미할당 은행의 사용을 빌드 배치표에 추가한다. 일반 C 코드나 IRQ가 SVBK를 직접 바꾸지 않는다.
5. 재진입은 저장/재로딩된 상태와 표시 자산을 일치시킨 후 입력을 재개한다. 같은 원작 상태·RNG와
   오디오 연속성을 함께 대조한다. 메뉴·전투 전환 자체의 통과는 R4–R6의 실제 연결에서 별도 기록한다.

추가 은행은 저장 공간이다. 전투 계산에 쓰는 활성 상태를 그곳에 놓고 기존 C 함수에 포인터만
넘기는 방식은 허용하지 않는다. 활성 전투 작업 공간은 은행 1의 모드별 재사용 또는 고정 영역
예산으로 설계하고, 은행 3/5에는 중단된 상태를 보존한다.

이번 검사기는 은행 3으로 현재 필드 작업 공간, 은행 4로 GameState를 복사하고 작은 버퍼로
다시 읽어 대조한다. 활성 상태를 가짜 메뉴/전투 데이터로 교체하지 않는다. 이것은 저장 영역의
접근·보존 검증이며 정상 게임의 모드 전환이나 SRAM 저장 구현 완료를 의미하지 않는다.

은행 검사는 2–7번 은행 왕복·경계/0길이·비정렬 길이·잘못된 요청·재진입 거부·IE/IME 보존·
실제 GameState/작업 공간 복사를 포함한다. 관측기는 실제 SVBK 쓰기 사이의 SP/IME, IE 마스크,
IRQ 진입 은행과 시간을 읽는다. 기존 음원 APU 쓰기·원작 상태·영상 접근·이동 시간 한도도 유지한다.

부팅 때 현재 SP 아래에 스택 표식을 채우며, 실행 후 남은 표식으로 사용 범위를 관측한다.
표식 값과 같은 바이트가 다시 쓰일 가능성 때문에 이는 수학적인 최악 스택 깊이 증명이 아니다.
가드·원작 대조·실제 인터럽트/은행 관측과 함께 사용한다. 실기와 모든 미래 호출 경로는 별도다.

## 근거

후속 [전체 화면 캐시 진단](composition-cache.md)은 은행 3/4에 합성 결과 6,144바이트를 두고,
은행 1의 `$D000..D79F`에 상주 키/이전 셀/표시 슬롯/속성, `$DB00/$DC00`에 OAM,
`$DBA0/$DCA0`에 OBJ 그림 키를 둔다. 스택 바닥은 `$DD00`이다. 지도 그림자 2,304바이트는
채택하지 않고 고정 영역의 변경 마스크 4바이트로 대체했다. 두 BG 지도를 교대로 쓰므로
기존 한글 창과 지도 소유권이 충돌한다. 이 배치는 **독립 진단의 검증 배치**이며, 기존 탐색
작업 공간 위에 함께 올려도 된다는 뜻이 아니다. 실제 입력 생산자와 창 열기/닫기를 연결할 때
모드별 동시 생존 영역 및 팔레트/글꼴/지도 복구를 다시 검증한다.

후속 [합성 핵심 루틴 진단](composition-kernel.md)은 별도 빌드에서 `$D800..D94C`를 입력으로,
기존 `$D950` 스테이징 중 48바이트를 출력으로 사용한다. 비재진입 커널의 고정 scratch는
25바이트다. 이 진단의 링크/가드/은행/스택 검사는 제품의 대사·탐색 버퍼와 동시 소유가
가능하다는 뜻이 아니다. 제품 타일 캐시를 통합할 때 위 활성 모드 소유권에 다시 배치한다.

- 사양: [Pan Docs의 SVBK](https://github.com/gbdev/pandocs/blob/master/src/CGB_Registers.md#ff70--svbkwbk-cgb-mode-only-wram-bank). 고정 은행 0과 선택 창 1–7의 구분. 사이트 직접 열기/다운로드가 실패해 같은 문서의 GitHub 원문으로 확인했다.
- 도구: [GBDK 코딩 지침](https://gbdk.org/docs/api/docs_coding_guidelines.html). 고정 4.5.0 도구의 실제 생성 코드도 별도로 검사하며, 최신 웹 문서를 ABI 증거로 대체하지 않는다.
- 원작 구조: [고정 참조 리비전](https://github.com/everything8215/ff3/tree/1acef8117120ff891003de249b1a74bc8d94d674)의 RAM 지도와 [원작 상태/RNG 소비자 대조](state-save-rng.md). 주석 지도만으로 미래 전투 메모리 완료를 주장하지 않는다.

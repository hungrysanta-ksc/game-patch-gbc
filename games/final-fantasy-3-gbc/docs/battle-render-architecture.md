# 원작 전투 구조와 현재 표시 경로 회고

2026-11-25 사용자 질문에 따라 PR 53 병합
`c96ba3ee7d0475a41df6b30c2f47821f85be1407`을 재점검했다.
결론: 원작 규칙을 이식한 코드와 원작 실행 결과를 표시하는 검증용 경로가 혼재한다.
현재 전체 화면 타일 스트리밍의 지연을 곧바로 GBC의 이식 한계로 해석하면 안 된다.
**프레임 합성 시제품의 미세 최적화보다 원작의 자원 수명과 갱신 단위를 옮기는 일이 우선이다.**

## 실제 구현 구분

| 영역 | 현재 구현 | 아직 같지 않은 부분 |
|---|---|---|
| 음악·효과음 | `audio-control/channel/music/engine.c`가 원작 bank 36의 명령·반복·엔벌로프·템포·요청·페이드를 실행 | NES 논리 APU 쓰기를 GBC로 변환하며 소프트웨어 스윕, 시간 큐, 진단 비용이 추가됨. 원작 APU와 같은 하드웨어 처리 비용이 아님 |
| 전투 규칙·시작 호출자 | `battle-physical/context/opening/party.c` 등에서 원작 상태·산술·분기·요청을 이식하고 원작 실행과 대조 | 전체 전투 호출자와 모든 직업/마법/아이템 소비자가 통합된 것은 아님 |
| 등장·포격 그림 | `battle-opening-assets.mjs`가 원작을 빌드 시 실행하고 NMI 대기 경계의 화면을 수집 | 원작의 일반 그래픽 소비자가 GBC에서 실행되는 구조가 아님 |
| V6 화면 구성 | `scenePixels`로 좌표·축소를 적용하고 `actionComposition`으로 BG/잔여 OBJ에 합성 | 이동/스크롤/우선순위의 결과가 새 타일 그림으로 바뀜. 이동할 때 좌표만 바꾸는 비용을 유지하지 못함 |
| 전송 | `packBattleFrames`가 안정 타일 ID와 이전 페이지별 차분을 만들고 `battle-atlas.c`가 비활성 BG 페이지를 갱신 | 전체 프레임을 무조건 전송하는 것은 아니지만, 합성 때문에 달라진 타일이 많아져 두 페이지·맵·속성·패턴 전송이 증가 |
| 숫자·한글 창 | 원작 숫자 수명과 배치를 보존하고, 숫자 구간은 그림을 고정한 채 OAM을 예약 갱신. UI는 원작 창 자료를 사용 | 많은 숫자·아군·효과가 함께 있을 때 BG로 옮길 대상을 프레임 전체 합성으로 해결하는 경로가 남음 |

따라서 “자산만 추출해 임의 게임을 만든다”는 설명도, “원작 엔진 구조가 전부 이식됐다”는
설명도 정확하지 않다. 원작 함수 이식은 실재하지만 최근 반복 최적화의 주 대상은 제한된
그림 시제품이었다. 이 한계는 개별 문서에 기록돼 있었으나 다음 작업 선정에 충분히
반영하지 못했다. 그림 일치·무음/누락 없음과 제품 렌더러의 효율/확장성을 분리해 관리한다.

## 원작과 다른 작업량의 직접 근거

`tools/battle-render-architecture.mjs`는 지원 ROM의 원작 그래픽 소비자를 다시 실행하고,
PR 53의 같은 등장 자료에서 현재 GBC 그림 전송량을 계산한다.

- 원본 ROM SHA-256: `262a98737975df25fff80ad91090c3da039d2828035c6253140d2c5f3b176ea2`.
- 기준 GBC ROM: `171f4519961aa5cb1edc33a1f325f4ed66554fcbfebfc5306eb0ffd972c928d9`.
- 기준 report SHA-256: `785f4bd71a48a64f9e845c48e393f38051f84990751fd7a5eb12f8e149ab01af`.
- 원작 근거: `battle-transition-source.mjs`의 `presentationMachine`/`entryTransition`,
  `2F/B469` 등장과 `2F/AE5E`의 적·메뉴 스크롤. `recordTransfers`는 실제 `$2007` 쓰기를 센다.
- GBC 근거: `battle-opening-assets.mjs`의 원작 요청→그림 목록,
  `battle-scene-assets.mjs`의 `stableSceneTiles`/`packBattleFrames`,
  `battle-atlas.c`의 `stage_show`/`prepare`/`queue_mask`.

| 원작 관측 경계 | 35 | 35 |

원작은 진입 전에 자산이 적재된 상태에서 스크롤 값·OAM·포즈와 필요한 CHR/맵만
갱신한다. 현재 GBC 경로는 이 움직임을 최종 픽셀로 만든 다음 차분 패턴을 업로드한다.
위 비교는 **원작 비래스터 소비자의 쓰기 기록과 GBC 생성 자료의 차분 계산**이다.
GBC 초기 두 페이지, UI 추가 전송, OAM DMA, 팔레트를 제외했으며 하드웨어 시간이나
정확한 속도 배수 비교가 아니다. 그래도 추가 타일 전송이 구현 구조에서 발생함은 확인된다.

## 하드웨어 차이의 의미

GBC의 배속 CPU·메모리·색상 기능은 활용할 수 있지만 NES의 모든 기능에 대한 상위
호환은 아니다. GBC는 총 40 OBJ/줄당 10, NES는 총 64/줄당 8이다. 작은 화면에서는
같은 객체가 더 좁은 줄에 겹친다. GBC 배속에서도 LCD와 VRAM DMA의 속도는 그대로다.
CPU 명령 비용도 달라 클럭 비율을 그대로 성능 비율로 볼 수 없다.

근거: [Pan Docs CGB 레지스터](https://github.com/gbdev/pandocs/blob/master/src/CGB_Registers.md),
[Pan Docs OAM](https://github.com/gbdev/pandocs/blob/master/src/OAM.md),
[Pan Docs CPU](https://github.com/gbdev/pandocs/blob/master/src/CPU_Comparison_with_Z80.md),
[NESdev PPU](https://www.nesdev.org/wiki/PPU_programmer_reference).

이 차이는 원작의 구조를 버릴 이유가 아니라, 원작의 데이터·논리·갱신 의도를 유지하며
출력 장치에 맞는 소비자를 만들 이유다. 스크롤·타일 상주·OAM 갱신을 우선 사용하고,
겹침/팔레트 제약 때문에 필요한 영역만 합성한다. 모든 아군을 항상 OBJ에 두는 정책도
미리 확정하지 않는다. 네 자리 숫자×8명과 마법/상태/아군이 공존하는 예산을 함께 검증한다.

## 수정한 구현 순서

1. **원작 프레임별 작업 계약.** CHR 적재/재사용, BG 스크롤·맵 수정, OAM 포즈/좌표,
   팔레트, 창, 소리 요청을 각각 원작 주소·소유자·수명·갱신 조건으로 등록한다.
   현재 픽셀 합성 결과는 기준 이미지로 보존하고 제품 런타임 입력과 분리한다.
2. **정면/백어택 등장부터 실제 소비자 연결.** 원작 등장 상태를 GBC에서 진행하고,
   배경/축소 적 타일/무축소 아군 포즈를 상주시킨다. 스크롤·OAM·필요한 맵 열을 갱신한다.
   지형·적·아군·창의 서로 다른 스크롤 영역, 석화 BG, 진열과 가림은 별도 조건으로 검증한다.
   미리 만들어 둔 `frame id → 완성 그림` 목록을 일반 구현으로 확장하지 않는다.
3. **포격·피격·숫자·창을 같은 자원 수명에 연결.** 이미 이식한 호출자/계산 결과를
   포즈·효과 메타스프라이트·명중 위치·팔레트·소리 요청으로 전달한다. BG 합성은
   필요 영역과 실제 공존 조건에 제한하고, 타일 ID를 객체/자산 수명 동안 유지한다.
4. **한 프레임 예산으로 검증.** 원작 논리 틱/최소 대기/숫자 도트, 실제 VRAM 전송량,
   OAM 전체/줄당 수, 최악 CPU 시간, 게시 마감, 음악·효과음 연속성, 메모리 수명을 함께 검사한다.
   원작과 같은 일을 얼마나 싸게 처리하는지가 기준이며 시제품 200ms를 영구 예산으로 삼지 않는다.
5. **공유 소비자 확장.** 무기·직업기·아이템·마법/소환의 단일/전체 대상과 상태 변화에
   같은 계약을 적용한다. 동작 경로의 수를 늘리기 전에 공통 상태와 표시 자원 소유권을 연결한다.

오디오 역시 원작 악보/명령의 의미와 순서는 유지하되 제품 실행용 표현·뱅킹·호출 구조를
GBC에 맞춘다. 논리 NES APU→GBC 변환의 비용과 실제 음악 VM 비용을 구분하고,
진단 기록은 제품 필수 처리와 분리한다. 음색은 사용자 지시대로 후순위다.

## 이번 실험의 처리

PR 53 이후 계산 최적화 후보 `a7e5e6c...`는 최대 준비 지연 230.957ms,
48개 버퍼 후보 `1b02ddc8...`는 219.238ms로 기준 218.994ms를 개선하지 못했다.
두 후보는 화면/오디오 검사를 통과했지만 요청된 성능 목표를 충족하지 않았다.
후자의 최대 마스크 호출은 165.101→14.421ms, 최대 원작 틱은 20.975→20.187ms였으나
이는 전체 준비 지연 해결이 아니다. 검사 기준을 완화하거나 이 후보를 병합하지 않는다.
추가 미검증 인자 전달 실험까지 로컬에 보존한 뒤 작업 소스를 PR 53으로 복원했다.

이번 변경은 조사 도구·회고·작업 계획만 공개한다. 기존 런타임과 완료 관문은 바꾸지 않으며,
후속 최적화 요청은 위 구조 수정에 따라 계속할 미완료 작업이다. 기존 원작 함수/폰트/창/
오디오/픽셀 대조와 메모리 검사는 재사용한다. 전체 게임 진척률을 올리는 근거로 세지 않는다.

재현: `node tools/battle-render-architecture.mjs <보존한-PR53-report.json>`.
원시 ROM·번역·생성 자료·실험 패치·캡처는 Git 밖의 로컬 증거에 보존한다.

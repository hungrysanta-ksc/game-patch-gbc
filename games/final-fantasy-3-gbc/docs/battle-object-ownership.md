# V6 배치와 표시 구조의 분리

2026-11-25, 기준 PR 56 병합 `07940e892004f0ba6780abf3405e67b07724d570`.
사용자 요청에 따라 아군을 BG에 합성한 기존 V6 구현을 재점검했다.
**V6의 승인된 좌표·크기·창 배치는 유지하고, 일반 아군의 기본 표시 경로는 원작처럼
상주 패턴 + OBJ로 바꾼다.** 화면 전체 합성은 일반 렌더러의 기본 구조가 아니다.

## 원작의 실제 소유권

| 대상 | 원작 소비자와 구조 | 채택 방향 |
|---|---|---|
| 일반 아군·포즈 | `32/90D8..91CA`, 아군당 6개의 8×8 OBJ, 원작 슬롯 40..63. 21개 포즈의 위치/반전/타일 표를 읽음 | 원작 표·좌표·포즈·순서 유지. 패턴은 상주하고 OAM만 갱신 |
| 사망·개구리·미니 | 같은 OAM 소비자, `2F/B651` 종류 캐시에 따라 필요한 패턴만 교체 | 원작 캐시 수명 유지. 모든 그림을 매 프레임 다시 적재하지 않음 |
| 석화된 아군 | `2F/B72B..B7BA`가 2열 × 3/4행 BG 자료를 준비하고 `B6C8`이 게시 | 원작 자체의 BG 예외. 해제 때 같은 영역 복원 |
| 적·지형 | 원작 BG 패턴/맵과 등장 스크롤, 보스의 부분 패턴 갱신 | 자산 수명 동안 타일을 유지. V6 축소/팔레트 때문에 필요한 부분만 변환 |
| 상태·대상·피해 숫자·효과 | `32/9F11`, `33/AD2B` 등 원작의 공유 OBJ 구간 | 상태별 공존과 우선순위를 보존하며 부족분의 소유권을 따로 결정 |
| 창 | 원작 창 자료·수명 | 기존 한글/V6 UI 유지, 아군 움직임 때문에 창을 재합성하지 않음 |

`B469`가 좌표/포즈를 먼저 초기화하더라도 처음 두 대기에서는 아직 아군 OAM을 그리지
않는다. 실제 관측으로 이 차이를 확인해 새 표시 경로도 reset-hidden OAM을 유지한다.
현재 상태 값만 보고 매번 모든 그림을 그리면 이런 원작 게시 순서를 잃는다.

## 왜 모든 레이어를 그대로 옮길 수는 없는가

GBC는 총 40 OBJ, 줄당 10 OBJ다. X로 숨긴 객체도 줄당 선택 수를 쓰므로 새 어댑터는
화면 밖 객체의 Y를 숨긴다. 8×16 모드는 위/아래 타일의 속성을 공유하고 전 화면에
공통 적용된다. [Pan Docs OAM](https://raw.githubusercontent.com/gbdev/pandocs/master/src/OAM.md)

기존 [8×16 조사](render-budgets.md)는 개수 감소만으로 줄당 한계를 해결할 수 없음을
이미 보였다. 이 결과를 무시하고 8×16으로 일괄 전환하지 않는다.

또한 적의 7:8 축소는 원작의 색 경계를 새 8×8 격자 안으로 옮긴다. BG 한 타일에서
4색을 넘으면 원래 색을 유지하려면 추가 팔레트 배치나 보조 OBJ가 필요할 수 있다.
기존 V6 전체 합성기는 이런 제약과 밀집 숫자를 한 번에 풀었지만, 그 과정에서 일반
아군 이동까지 새로운 BG 패턴으로 만들었다. 이는 시제품의 손실 없는 표시를 위한
방법이었으며, 이동 비용·타일 수명까지 원작을 따른 제품 구조는 아니었다.

## 이번 대표 경로의 비교

`audit:battle-object-ownership`은 원작 정면/백어택 등장·상태 변경·아이템·적 8명에게
9999 표시와 인빈시블 포격/생존·전멸 경로의 **1,302개 관측**을 비교한다.
이는 모든 직업·마법·편성이나 정상 플레이 경로의 전수 검증이 아니다.

| 후보 | 최대 OBJ / 줄당 | 한도 초과 관측 |
|---|---:|---:|
| 원작 OBJ만 V6 좌표로 이동 | 56 / 8 | 76 |
| 위 후보 + 원작 BG 4팔레트로 축소 색을 보존하는 보조 OBJ | 68 / 10 | 350 |
| 위 후보 + 같은 색 자료를 쓰는 장면군에 BG 7팔레트를 공유 | 63 / 8 | 306 |

아군·상태 OBJ만 떼면 최대 24 / 줄당 3이며 이 조사 범위에서는 모두 들어간다.
원작 OBJ만 옮겼을 때의 초과는 적 전체 숫자와 포격 숫자 구간이었다.
축소 BG의 보조 OBJ는 고정 4팔레트에서 최대 14개, 공유 7팔레트 후보에서 최대 9개다.
7팔레트 후보도 해결 완료가 아니며, 여덟 번째 BG 팔레트는 UI에 남겨 둔다.

계수는 실제 보이는 도트가 있는 타일만 포함하므로 낙관적인 하한이다. 투명 타일도
그대로 배치하면 하드웨어 선택 수는 늘 수 있다. 팔레트 후보는 관측 장면을 사용하는
개발용 비교이며, 미래 프레임을 아는 제품 정책으로 채택하지 않는다. BG 색 복원은
픽셀 일치를 확인했지만 보조 OBJ와 모든 효과의 교차 우선순위까지 증명한 것은 아니다.

따라서 “아군을 항상 BG로”도, “모든 것을 원작과 같은 OBJ로만”도 채택하지 않는다.
**일반 아군은 OBJ가 기본이다.** 초과 장면의 숫자·효과·색 보정 영역을 먼저 분리하고,
원래 수명 동안 작은 BG 영역을 갱신/복원하는 후보를 검사한다. 아군을 BG로 옮기는
추가 예외가 정말 필요하다면 해당 겹침·팔레트·예산의 구체적 근거부터 제시해야 한다.
도트 삭제, 아군 축소, 숫자 생략, 임의 깜박임은 해결책으로 삼지 않는다.

## 새 실행 경로와 검증 경계

`battle-party-oam.c`는 26바이트 입력에서 원작 24 OBJ를 직접 만든다. 위치/반전 표의
6개 포인터를 원작과 왕복 확인했고, 절대 타일/아군별 상대 타일, 숨김, 팔레트 OR,
혼란 반전과 백어택 반전 허용 플래그를 실제 `32/90D8` 실행 결과와 대조한다.
V6 좌표와 NES→GBC 속성 비트 변환은 별도 함수로 분리했다. 미지원 포즈/보이는
priority 속성은 출력 변경 전에 실패한다. 숨겨진 reset OAM의 미사용 속성은 허용한다.

`battle-party-video.c`는 기존 등장 C 상태기를 실행해 이 소비자에 연결한다.
초기 패턴·팔레트·상태만 ROM에 넣으며 **프레임별 그림/OAM/상태 목록은 넣지 않는다.**
관측 프레임은 Git 밖의 정답 파일로만 사용한다. 4개 진입 프로필은 정면/백어택 ×
일반/사망·석화·개구리·미니 혼합 상태다. 일반 직업 0..3의 초기 자산을 사용한다.

이 ROM은 **검은 BG 위에서 아군만 표시하는 독립 진단**이다. 전체 전투 화면이 아니며
석화 BG·적·지형·창·상태 아이콘·피해 숫자는 아직 연결하지 않았다. 석화 상태가
아군 OBJ를 숨긴다는 검사는 석화 그림을 완성 화면에 표시했다는 뜻이 아니다.
전체 OBJ 패턴 4,096바이트를 프로필 적재 때 한 번 변환·게시하는 보수적 상주 공급이며,
일반 게임의 최종 타일 패킹/교체 정책은 아직 아니다.

원작의 대기마다 다음 OAM을 준비하고 이른 VBlank에 160바이트 HRAM DMA로 게시한다.
늦으면 현재 화면을 유지하고 모든 논리 단계를 순서대로 표시한다. 기존 오디오의
2틱 이상 선행 시 협력 양보 경로를 재사용하며 음악 명령·출력 변환은 바꾸지 않는다.
상태기/출력/스크린샷·전체 원작 음악/효과음/페이드 일정은 같은 ROM에서 검사한다.

### 최종 검사 결과와 남은 성능 차이

- 원작 OAM과 GBC C 출력 963건 통과: 21포즈·방향·숨김·팔레트 조합, 정면/백어택의
  모든 바이트 좌표 입력, 실제 진입 관측을 포함한다. 잘못된 입력의 출력 불변과
  오차 주입 ROM의 case 0/index 0 실패도 확인했다.
- 실제 GBC 화면 123장, 원작 NES 비트플레인 V6 기준과 native GB 타일 디코딩의
  픽셀 일치. 일반/혼합 상태의 정면/백어택을 확인했다.
- 같은 ROM에서 원작 오디오 7,200틱의 소비 이벤트/출력 해시 일치, underrun과
  출력 지각 0. 자동 이동 중 그래픽 VRAM 쓰기 0, OAM DMA 5,073회, 잘못된 VBlank
  게시 0. 실제 DMA 시작의 최대 LY는 146이었다. 4,096Hz 오디오 시계와 에뮬레이터
  시계의 누적 차이는 약 −0.0062ms로 3ms 기준을 통과했다.
- OAM 구성·좌표 변환의 최대 경과 시간은 약 10.254ms다. 오디오와 상태 진행까지
  포함한 자동 표시에서는 1,526회의 1프레임 초과 간격, 최대 3프레임 간격이 남았다.
  전송량 감소를 원작 속도 달성이나 전체 전투 성능 개선으로 주장하지 않는다.
- 호스트 검사 138개 통과. 이후 팔레트·좌표 회귀를 보강한 해당 검사 3개도 재실행했다.
- 공개 허용 소스 467개만 복사한 깨끗한 디렉터리에서 양성·오차 주입·실제 표시
  ROM 세 개와 생성 보고서가 모두 바이트 단위로 재현됐다.
- 실제 표시 ROM SHA-256:
  `8ea71aeea4a2a5ce696990e9c0815dc534c265e6e935580e5989f3795d08eff2`.

초기 검증 후보는 `9D88`이 지운 물리 팔레트를 자산으로 잡아 검은 화면끼리 일치했다.
직접 스크린샷 확인에서 발견해 시각 통과 판정을 철회했다. 최종 빌드는 원작의
`7D07..7D16` 팔레트 버퍼와 등장 중 실제 PPU 게시를 연결해 확인하고, 최종 장면의
비검정 색상 존재를 필수 검사한다. 원작 패턴의 진입 중 불변도 별도로 확인한다.
CPU 주소 공간에서 OAM을 읽으면 mode 3에 FF가 반환되는 관측 오류도 수정해,
기존 검증기와 같은 Mesen 물리 OAM 메모리 영역을 사용한다.

추가 시계 검사에서 DMA 뒤 통계 갱신까지 인터럽트를 막으면 약 −3.69ms의 누적
차이가 생기는 것을 발견했다. HRAM DMA가 끝나면 TIMA 처리를 허용하도록 바꿔
위 최종 수치로 재검증했다. 기준을 완화하거나 오디오 명령을 생략하지 않았다.

V6 좌표 변환에서는 부호 있는 16비트 계산 대신 원래 바이트 좌표와 native OAM의
+8/+16 오프셋을 결합했다. 화면 밖 판정까지 모든 바이트 좌표를 독립 부호 연산 기준과
대조했으며, 단순 오버플로로 화면 반대편에 객체가 나타나게 하지 않는다.

재현: `npm run audit:battle-object-ownership`, `npm run build:battle-party-oam`,
`npm run verify:battle-party-oam`, `node tools/verify-battle-select.mjs --party-oam --negative`,
`npm run verify:battle-party-video`. 원시 입력·추출 자산·캡처·ROM은 공개하지 않는다.

## 다음 순서

1. 이 아군 OBJ 경로를 유지한 채 적·지형 상주 BG와 스크롤/부분 패턴 게시를 연결한다.
   축소 BG의 보조 OBJ까지 같은 예산에 포함하고, 석화 BG와 상태 아이콘을 연결한다.
2. 숫자 최대 32개와 보조 OBJ가 공존하는 구간의 부분 BG 숫자 후보를 검증한다.
   원작 32프레임·전 도트·가림 순서와 복원을 유지하고 아군은 우선 OBJ에 남긴다.
3. 원작 창·포격·무기/직업/마법·소환에 같은 소유권을 적용한다. 실제 대상·발동 조건과
   동시 공존을 확인한 뒤 타일/팔레트/OBJ 예산과 음악·효과음 부하를 통합 검증한다.

이번 아군 단독 실행의 성능을 전체 V6 전투의 속도 개선으로 환산하지 않는다.

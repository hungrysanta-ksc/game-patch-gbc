# 등장·포격 화면 준비 최적화

기준: PR 48 병합 `17397add41ca2ede2422ef30f9f3e81751cabd05`.
작업 브랜치 `ff3-opening-speed`. 원작/번역/출력 ROM과 실행 증거는 비공개다.

## 원인과 변경

기존 [등장·포격 연결](battle-opening-video.md)은 원작 그림과 숫자를 보존하지만
프레임마다 하단 창 여섯 행을 다시 구성한다. 동일한 UI도 ROM 은행을 열두 번 읽고,
열두 개의 행 전송을 준비하며, 행마다 오디오 선행 준비를 호출한다.
객체/배경 전송과 창 전송 사이에도 완료 대기가 있어 표시 준비 시간이 누적된다.

기존 ROM의 정면 생존 경로는 28.781초다. 제한된 계측 실행에서 준비 단계 3
(객체 준비/전송 완료 대기/창 구성)에 152회 합계 22.576초가 누적됐다.
이 계측은 첫 경로 이후의 일부 준비도 포함하므로 전체 경로 시간의 정확한 구성비로 쓰지 않는다.
준비 단계의 병목 위치를 찾는 자료이며, 완주 속도는 동일한 8요청으로 따로 비교한다.

변경은 `FF3_OPENING_VIDEO` 안에 한정한다.

- 두 화면 버퍼마다 마지막 UI와 글꼴 소유자를 기억한다. 두 맵 평면의 13~18행이
  변경되지 않고 UI/글꼴도 같으면 창 갱신을 재사용한다. 상단 행의 아군 발 등
  일부 도트만 바뀌어도 재구성한다. 숫자 종료/버퍼 무효화도 변경 마스크로 처리한다.
- 여섯 행을 연속된 192바이트 두 평면으로 읽고 완성한 뒤 두 전송으로 큐에 넣는다.
  WRAM 원본은 전송 완료까지 고정된다. 기존 예약 범위와 DMA 최대 길이는 유지한다.
- ROM 원본을 참조하는 객체/배경 큐와 완성된 창 큐를 함께 처리한다.
  오디오 선행 준비량을 낮추지 않고 창 구성 시작·중간·완료 대기에서 공급한다.

먼저 창 재사용만 적용한 중간 ROM은 같은 정면 생존 경로가 19.890초였다.
이 결과를 보고 창 재구성 자체의 행별 작업과 불필요한 대기를 추가로 합쳤다.
중간 ROM을 최종 합격 결과로 세지 않는다.

일괄 처리만 적용한 후보는 정면 생존 16.843초였지만 전멸 중 창 재구성에서 오디오 큐
고갈 3회를 검출했다. 선행 준비량이나 검사를 낮추지 않고, 창 구성을 시작하기 전과
세 행을 구성한 뒤에 공급하는 경계를 추가했다. 해당 실패 ROM/관측은 비공개로 보존한다.

## 검증 방법과 범위

```text
npm test
npm run build:battle-opening-video
npm run verify:battle-opening-video
node tools/battle-opening-performance.mjs <PR48-baseline-folder>
```

비교 도구의 기준 폴더에는 PR 48의 `report.json`, `load.json`을 둔다.
ROM 해시와 고정 코어를 확인하고 251개 그림, 원작 요청/표시 경로, 한글 자산,
오디오 계획이 그대로인지 대조한다. 원작 숫자 프레임·대기와 데이터 생략으로 얻은
단축은 허용하지 않는다. 여덟 경로 각각이 기존 시간보다 빨라야 한다.

실행 검증은 실제 캡처 전체 픽셀, 상태 경계, 숫자 공급 마감, 동적 효과음과 APU 쓰기,
VRAM/OAM 버퍼 소유권 및 타이머를 그대로 검사한다. Lua의 `scene-cost`는 구간별
누적 시간/횟수/최댓값을 남기며, 단계 4에는 표시 대기, 단계 8에는 숫자 이후 경계도
포함되므로 이 값을 순수 CPU 실행 시간이라고 부르지 않는다.

네 가지 제한된 원작 관측 경로에 대한 준비 최적화다. 일반 편성의 실시간 공급기,
정상 게임 진행, 실기, 음색 승인과 전체 연출의 원작 속도는 별도 관문으로 남긴다.

## 최종 검증 결과

각 경로를 두 번 실행했다. 전체 소요 시간은 기존 28.178~36.482초에서 17.831~24.227초로
줄었고, 동일한 여덟 요청 각각의 단축률은 32.6~37.1%다.

| 경로 | 기존 최대 | 최적화 최대 | 매회 단축률 최소 |
|---|---:|---:|---:|
| 정면 생존 | 28.781초 | 18.450초 | 35.9% |
| 정면 전멸 | 36.482초 | 24.227초 | 32.6% |
| 백어택 생존 | 28.195초 | 17.864초 | 36.6% |
| 백어택 전멸 | 35.327초 | 23.423초 | 33.5% |

- 호스트 회귀 126/126 통과. 공개 소스 416개만 복사한 빌드의 ROM/보고서가 일치했다.
- 원작 그림 251개와 요청·대기·문자·오디오 계획은 기준 빌드와 동일하다.
- 상태 경계 348건, 표시 단계 1520건, 실제 캡처 1784장/41,103,360픽셀 일치.
- 숫자 8회 × 32프레임, 공급 지연 0회. 최대 표시 오차 3.207ms.
- 원작 오디오 21600틱, 동적 효과음 12요청, APU 144443쓰기 대조. 큐 고갈·출력 지연·잘못된 VRAM/DMA·활성 버퍼 쓰기 0회.
- 전체 최대 OBJ 40개/한 줄 9개. 스택 미사용 266바이트.
- 준비 1212회 중 창 재구성 432회; 나머지는 같은 버퍼의 창을 재사용했다.
- ROM SHA-256: `3b7c7e3085da0d3b3abd7b6a94a69f600eaaa2dd2a5b0d25ecc00b14498b7d6d`. 코어는 PR 48과 동일한 고정 MesenCore다.

전체 연출의 원작 속도 관문은 여전히 미통과다. 현재 표시 대기를 끝낸 뒤 다음 그림을
준비하는 구조의 추가 지연이 남는다. 다음 작업은 원작 대기 중 선행 준비가 가능하도록
실행 경계를 나누고, 같은 도트·숫자·오디오 검사를 유지하는 것이다. R2 0/8, 제품 관문 0/3을 유지한다.

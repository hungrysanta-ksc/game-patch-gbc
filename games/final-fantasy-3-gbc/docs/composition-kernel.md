# GBC 타일 합성 핵심 루틴과 오디오 동시 부하

기준: PR 19 병합 `38c7391bc602d9bc068cc542e2c04955bc41ceb7`.
[앞선 정지 프레임 후보](npc-composition.md)를 실제 SM83 타일 계산으로 옮기는 R2의 중간 검증이다.
게임 렌더러 통합이나 R2 완료가 아니다. 플레이어/동행·카메라·한글 창 공존은 아직 미검증이다.

## 이번에 실행하는 경계

원작 `B2FD/B1EE`, 이벤트 `ACD1`, 이동 `B17C`로 생성한 기존 22개 상태를 재사용한다.
원작 도달성의 한계도 그대로다. 이벤트 81의 전투 이후 상태를 검사한 것이지 전투를 실행하거나
새 게임부터 그곳까지 플레이한 것은 아니다. 원작 출처/조건은 빌드 보고서의 각 프레임에 유지한다.

각 8×8 셀은 원작 BG의 2bpp 인덱스, 원작 순서의 OBJ 타일과 상대 좌표·팔레트·배경 뒤 플래그,
대상 색 인덱스 변환표를 공급받는다. 원작 그림의 뒤집기는 기존 원작 픽셀 해독 경로에서 처리한다.
완성된 합성 타일이나 가림 마스크를 ROM에 넣지 않는다. `composition-kernel.c`가 GBC에서
투명도·첫 OBJ 우선권·BG 가림을 계산하고 BG+잔여 OBJ 두 팔레트의 타일 48바이트를 만든다.
선행 OBJ가 BG에 가려져도 그 뒤 OBJ를 보이게 하지 않는다. 색/얼굴/실루엣을 생략하지 않는다.

대상 팔레트 선택은 여전히 호스트의 기존 탐욕 탐색이다. 22개 프레임의 7,920셀을 입력 바이트로
중복 제거한 232개 원작 작업과, 별도로 표시한 7개 경계/오류 작업을 실제 GBC에서 실행한다.
후자는 겹침 우선권·음수 좌표·16층·잘못된 길이/층수·미지원 색을 검사하는 단위 입력이다.
원작 게임 장면 수나 도달성에 더하지 않는다.

결과는 기존 `text-vblank.c`로 LCD가 켜진 상태에서 격리된 VRAM `$8000..802F`에 전송한다.
WRAM 결과와 실제 VRAM 바이트를 원작 최종 픽셀에서 별도로 만든 기대값과 대조한다.
이 목적지는 진단 전용이다. 전체 맵의 타일 상주 교체·팔레트/OAM 동시 커밋·찢어짐 없는 카메라
표시를 구현했다는 뜻이 아니며, 이 빌드의 화면을 새 플레이 샘플로 제시하지 않는다.

## 성능 판단과 다음 구현

첫 픽셀 단위 구현은 원작 입력에서 타일 하나 최대 226/4096초(약 55.18ms)가 걸렸고,
오디오 큐 고갈을 재현했다. 해당 후보는 채택하지 않았다. 실패 원시 관측은 로컬
`evidence/composition-kernel/rejected-pixel-loop/`에 보존한다.
후속 구현은 한 줄의 8픽셀을 비트 마스크로 함께 처리한다. 타일 사이에는 기존 오디오 생산기를
호출하고, 전송 대기 중에도 같은 생산기를 서비스한다. 오디오 출력 변환표는 변경하지 않았다.

줄 단위 구현의 스택 지역 변수 버전은 원작 최대 약 14.89ms였다. SDCC의 스택 상대 주소 접근을
줄이도록 25바이트의 고정 scratch를 분리한 최종 버전은 **원작 타일당 최대 11.47ms**다.
작업 전체 중앙값은 약 6.59ms, 합성 16층의 별도 경계 입력까지 포함한 최대는 약 26.37ms다.
런타임 자체 계측과 별도로 읽은 Mesen 시계의 전체 최대는 26,206µs이며 자체 4096Hz 계측 해상도는 약 0.244ms다.
기능을 정확히 계산하는 커널을 확보했지만, 이 비용으로 전 화면을 매 프레임 계산할 수 있다는
판정은 아니다. 원작 입력 12ms/경계 입력 28ms를 타일 단위 회귀 상한으로 둔다.

최종 부하 실행에서 239종을 반복해 3,761회 실행했고 정상 입력의 기대 바이트/VRAM 비교와
오류 입력의 명시적 거부를 통과했다.
정상 작업의 VBlank DMA 3,716회, 실제 APU 쓰기 28,509회, 원작 7,200틱/21,366이벤트를 검사했다.
잘못된 VRAM/DMA 시점·LCD 끄기·음악 큐 고갈·재생 지연은 모두 0이었다.
WRAM 은행 관측 오류 0, 스택 미사용 워터마크는 978바이트였다. 고정 WRAM 끝은 `$CA6C`,
커널 ROM 은행 12의 코드는 819바이트다. 제품 통합 전 이 여유를 그대로 가져다 쓸 수는 없다.

검증 ROM SHA-256: `cf7520fc67968e0908dcacd1ef44c4c3e41d17f4c86ac0e67e7cf31267e7f509`.

측정 결과는 아래 검증 산출물에 기록한다. 커널 시간은 오디오 IRQ를 포함하지만 ROM 입력 복사,
팔레트 탐색, 타일 캐시, 전송 대기와 전체 화면 커밋은 포함하지 않는다. 요청→전송 완료 시간도
원시 기록에 별도로 남긴다. 타일 단위 성공을 이동 프레임 전체의 성능으로 환산하지 않는다.

다음은 정적인 장식/배경을 미리 변환하고 실제 바뀐 부분에만 이 루틴을 쓰는 경계다.
맵에서 유지할 팔레트 정책과 타일 캐시를 먼저 정하고 플레이어·동행 가림, 카메라 경계,
숨기기·이동·한글 창·재진입의 복원을 통합한다. 변경되지 않은 영역까지 매 프레임 재합성하거나,
전체 프레임을 ROM에 저장하는 방식을 제품 구조로 채택하지 않는다.
그다음 적 색 보존·206 외부 타일·아군/큰 마법/한글 공존 예산을 닫고 R3로 진행한다.

## 메모리와 재현

진단 입력은 은행 1 `$D800..D94C` 333바이트, 출력은 기존 전송 스테이징 `$D950..D97F`
48바이트다. 사이의 3바이트와 `$D7F0..D7FF`, `$DB60..DB6F`를 가드로 검사한다.
커널 코드는 ROM 은행 12, 입력 데이터는 16 이후, 메타데이터는 7에 둔다.
오디오 엔진/큐는 기존 고정 WRAM, 진단 스냅샷은 은행 2다. 입력/출력은 일반 WRAM 포인터이며,
오디오용 은행 접근이 끝나면 은행 1과 호출자 ROM 은행이 복원되어야 한다.
이 배치는 독립 진단 빌드의 소유권이다. 제품 대사 버퍼와 동시에 사용할 수 있다고 예약한 것이 아니다.

```powershell
node tools/build-composition-kernel.mjs
node tools/verify-composition-kernel.mjs
node tools/verify-composition-kernel.mjs --idle
```

`build/composition-kernel/report.json`에 원본/출력 해시·원작 소비자·입력 수·링크 예산을 기록한다.
`evidence/composition-kernel/{load,idle}.json`은 실제 셀 결과·VRAM·시간·오디오 소비 이벤트다.
`*.lua.log`는 실제 APU 쓰기와 VRAM/DMA/LCD·WRAM 은행 관측이며 `*-result.json`이 판정 결과다.
고정 MesenCore에서 검증하며, 실기/독립 에뮬레이터나 음질 청취 승인을 대신하지 않는다.
원본 ROM, 생성 입력·ROM, 관측은 공개하지 않는다. 소스 allowlist만 배포하고 외부 원본으로 재생성한다.

음질의 노이즈/다른 변환 방식 검토는 사용자 요청에 따라 [후순위 과제](audio-backlog.md)에 기록했다.

공개 대상 소스 228개만 별도 폴더에 복사하고 외부 원본 ROM/고정 도구로 재빌드해 ROM과
빌드 보고서의 해시가 일치했다. 그 복사본의 실제 GBC 부하 실행과 일반 작업 폴더의 오디오
단독 실행 모두 원작 기준 실행에 대응하는 GBC APU 쓰기 28,509회/동일 순서 해시를 통과했다.
호스트 회귀는 39개 통과다.

검증 도중 두 경계도 바로잡았다. 두 OBJ 팔레트의 공유 색을 무조건 첫 팔레트로 보내면
기존 후보보다 잔여 OBJ 층이 늘어나므로, 선택된 잔여 팔레트 정책을 그대로 따른다. 모든 셀의
BG/OBJ 결과를 기존 후보의 타일과도 대조한다. 검증기는 음악 종료 뒤 이미 시작한 셀의 전송까지
기다리며 독립 계측 횟수와 완료 횟수를 정확히 대조한다. 어느 검사도 허용 오차를 늘리지 않았다.

# 원작 등장 자원 계약과 상태 소비자

2026-11-25, PR 54 구조 회고 이후 첫 구현. 기준 병합은
`e8cd8812f706969d0ad83fe4635cbf11e406c413`이다.
이번 경계는 **원작 `2F/B469`부터 `B479` 직전까지**다. 전체 전투 등장이나
V6 표시 교체를 완료한 것으로 세지 않는다. 원작을 호출해 얻은 프레임을 런타임에서
재생하는 대신, 원작 상태·자원 갱신을 계산하는 C 소비자를 만들었다.

## 원작이 처리하는 단위

`tools/audit-battle-entry.mjs`가 실제 원작 명령을 실행해 대기 경계, 스크롤,
OAM 변경, PPU 쓰기 주소·작성자·양을 기록한다. 다음은 초기 그래픽 적재 이후의 계약이다.

| 소유자 | 원작 근거 | 수명과 갱신 |
|---|---|---|
| 지형 | `2F/AD53,AD9A,ADC0` | 지형 256바이트를 작업 메모리에 읽고, 7단계 마스크 × 4행을 순서대로 적용. 한 대기마다 PPU `$0600..06FF` 중 64바이트만 교체 |
| 적 | `2E/A31F`, `2F/AE4F,AE5E` | 이미 적재한 CHR·맵을 유지하고 독립 영역의 스크롤·페이지를 변경. 이번 접두 구간에서는 적 그림/맵 쓰기 없음 |
| 아군 | `2F/B4AC`, `33/BD45,BE89`, `32/90D8` | 직업 그래픽을 재사용해 위치·포즈를 갱신. 미니는 1픽셀, 일반/개구리는 2픽셀 이동. 개구리 Y 변위, 혼란 반전 조건, 사망/석화의 이동 없음 보존 |
| 메뉴 | `2F/AE39` | 이미 적재한 맵에 대해 독립적으로 16단계 스크롤 후 페이지 비트 해제 |
| 팔레트 | `3F/F8B0,F88C` | 최초 대기 뒤 기존 버퍼 32바이트 전송. 접두 구간의 매 프레임 팔레트 재생성 없음 |
| 후속 처리 | `2F/B479..B4A9,B5C3,BE97` | 보스 등장 조건, 정규 진열 위치, 상태 그림/석화 BG 복원, 적 개수 갱신. 이번 소비자는 이 소유자에게 넘겨야 하며 완료로 무시할 수 없음 |

정상 정면/백어택은 접두 구간 30번의 원작 대기를 사용한다. 전열 미니의 `F0→D0`
이동처럼 더 긴 경우 33번으로 늘어난다. 28번의 지형 갱신은 상태와 무관하게
1,792바이트이고, 접두 구간 맵 쓰기는 0바이트다. 마지막 상태 복원까지 포함한 전체
`B469`는 다른 범위다. 이번 기본 진열 `[0,1,0,1]`의 전체 조사에서는 맵 28바이트이며,
PR 54의 전체 포격 호출자 안에서 얻은 22바이트와 초기 상태/관측 경계가 다르다.
서로 다른 표본을 성능 개선으로 비교하지 않는다.

## GBC에 옮긴 부분과 남긴 경계

- `src/battle-entry.c`는 원작의 초기화, 스크롤, 이동, 마스크 행 진행을 실행한다.
  시작 위치·진열 표·개구리 변위/포즈·마스크의 92바이트는 지원 ROM에서 추출한다.
  `battle-entry-source.mjs`에 은행/주소, 소비자, 참고 어셈블리 행, 실제 바이트 해시를 기록한다.
- 상태는 39바이트다. `INITIAL → TERRAIN → WALK → TAIL`은 원작 대기 위치를
  비동기 요청으로 표현한 것이다. 호출자는 게시가 끝난 뒤에만 같은 ticket을 승인한다.
  함수는 LCD를 기다리거나 오디오를 실행/차단하지 않는다. 잘못된 ticket과 재시작은
  상태를 변경하지 않고 거절한다.
- 지형 함수는 현재 행 64바이트만 만든다. 전체 화면 픽셀, 프레임 ID, 프레임별 완성
  그림 자산을 입력받지 않는다. 입력 지형 256바이트와 출력 행 64바이트는 WRAM에 둔다.
  원작의 NES 2bpp 결과를 반환하며 GBC 인코딩·VRAM 게시를 했다는 뜻은 아니다.
- `TAIL`에서는 승인을 거절한다. `B479` 이후 보스/상태 경로를 연결하기 전에는
  상위 `FF3_OPEN_GRAPHICS/0` 요청을 완료 처리할 수 없다.
- 기존 V6 시제품과 오디오는 이번에 바꾸지 않는다. 새 소비자는 아직 기존
  `battle-atlas.c`의 전체 화면 전송을 대체하지 않는다.

관측값은 NMI 대기 **직전의 논리 상태**다. `AE5E`는 현재 스크롤을 출력한 뒤 다음 값을
계산하므로 관측한 `$0F`를 같은 프레임의 GBC SCX로 곧바로 쓰면 한 단계 어긋날 수 있다.
OAM 그림 작성과 실제 DMA 게시 역시 구분해야 한다. 다음 어댑터에서 이 게시 경계까지
맞춰야 하며, 이번 비래스터 원작 도구는 실제 스캔라인 타이밍의 증명이 아니다.

## 구조와 효율 판단

| 비교 | 채택/보류와 근거 |
|---|---|
| 원작의 상주 적 타일 + 스크롤/OAM 변경 | 유지할 기본 구조. 접두 구간은 적 CHR 재전송이 필요하지 않다는 원작 쓰기 기록 확보 |
| 모든 움직임을 완성 BG 그림으로 합성 | 일반 구현 경로로 확장하지 않음. 기존 자료는 최종 픽셀 비교 기준으로 보존 |
| 원작 terrain 64바이트 작업 | 이번 C에 유지. 원작 마스크/행/대기를 그대로 실행하므로 첫 기준 구현으로 비용을 분리 측정 가능 |
| 7단계 지형을 빌드 시 미리 마스킹 | 후보. CPU AND 비용은 줄지만 ROM/VRAM 상주 비용과 맵 변경 비용이 생긴다. 최악 동시 자산에 맞는지 확인 전 채택/우월 주장 금지 |
| 전체 NES 메모리/PPU를 GBC에서 흉내 내기 | 하지 않음. 제품은 39바이트 상태와 원작 표를 소비하고, 원작 실행기는 개발 검증에만 사용 |

이번 독립 검사 ROM의 C/표 bank 크기는 1,569바이트다. 기존 전투 ROM에 함께 링크한
최종 메모리 예산은 아직 검증하지 않았다. 비교용 ROM 안의 약 1.7MB 프레임별 상태/정답은
검사 데이터이며 제품 자산이 아니다. 아직 실제 표시·오디오 동시 실행의 최악 CPU 시간,
VRAM 전송 마감, OAM 한도를 측정하지 않았으므로 “원작보다 빠름”이나 “지연 해결”을 주장하지 않는다.

## 검증

- 정면/백어택 × 256개 정규화 상태 조합: 512건. 각 슬롯에 다른 상태를 배치하고
  16가지 진열 조합과 혼란 위치 캐시 조건을 순환한다. 모든 비트 조합의 국소 소비자 검사이며
  이 조합이 모두 정상 플레이에서 발생한다는 뜻은 아니다.
- 실제 원작의 대기/종료 상태 16,064개를 39바이트씩 GBC 컴파일 결과와 비교했다.
  지형 출력 14,336행, 917,504바이트도 실제 원작의 다음 경계 PPU 내용과 일치했다.
- 지원 원본 ROM SHA-256: `262a98737975df25fff80ad91090c3da039d2828035c6253140d2c5f3b176ea2`.
- 비교 ROM SHA-256: `54d01558186e0abc1a492f35a656f06e6c48dcaec2341b95eb2ba92e631050b8`.
- Mesen core: `1ba99d2c848e007c60cbd7fceca058440758eb44837a93a6724d29d72723c994`.
- 정답 첫 바이트를 변조한 오류 검출용 ROM은 case 0/index 0에서 예상대로 실패했다.
- 기존 검사를 포함한 호스트 테스트 132개 통과. 원작 대기 소유자와 30..33회 경계
  제한을 추가한 뒤 해당 3개 검사와 자원 감사를 다시 통과했다.
- 공개 허용 목록 446개 파일만 복사한 경로에서 재빌드한 ROM과 보고서가 동일했다.
  원작/로컬 도구 설정은 별도 입력이며, 기존 생성 헤더·정답 파일을 복사해 재사용하지 않았다.
- 원본/추출 표/비교 ROM/원시 상태/캡처는 Git에 넣지 않는다. 공개 파일만으로 빌드하되
  지원 ROM과 고정 도구, 로컬 설정은 별도 제공한다.

재현: `npm run audit:battle-entry`, `npm run build:battle-entry`,
`npm run verify:battle-entry`, `node tools/verify-battle-select.mjs --entry --negative`.

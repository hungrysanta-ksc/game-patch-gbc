# 현재 프레임 표시 중 다음 그림 준비

기준: PR 49 병합 `19bad2a5b2a3fb6759561351a50b7b15d2879de1`.
작업 브랜치 `ff3-opening-pipeline`. 앞선 [창 준비 최적화](battle-opening-performance.md)의
같은 네 경로·251개 그림·원작 요청과 대기를 유지한다.

## 실행 경계

기존 호출자는 현재 그림 게시 → 원작 표시 대기 → 다음 그림 준비를 순서대로 실행했다.
이번에는 현재 그림 게시/효과음 요청 후 대기 마감을 고정하고, 그 시간 안에 다음
일반 그림의 준비를 시작한다. 준비와 게시를 분리해 아래 불변 조건을 유지한다.

- 선행 준비는 비활성 BG/OBJ/OAM과 팔레트 준비 공간만 쓴다. 현재 화면은 유지한다.
- 다음 원작 요청의 ack, 상태 확정, 효과음, 화면 게시는 이전 표시 대기가 끝난 뒤다.
  미리 읽는 것은 고정 원작 관측 경로의 불변 표시 자산이다. 일반 게임에서 미확정 AI나
  입력 결과를 추측해 실행하는 기능이 아니다.
- 그림이 같아 전송할 필요가 없어도 원작의 논리 단계와 대기는 생략하지 않는다.
- 준비가 마감보다 늦으면 현재 화면을 더 유지한다. 새 그림이나 도트를 버려 시간을 맞추지 않는다.
- 숫자 32프레임은 두 OAM 버퍼를 사용하는 기존 전용 스케줄러가 소유한다.
  숫자 구간 및 그 진입 준비는 이번 일반 그림 선행 준비에서 제외한다.
- 오디오 선행 준비량과 창 구성 중 공급 경계, 기존 DMA 크기/게시는 그대로다.

GBC 진단 카운터는 선행 준비 횟수, 마감 초과 횟수/최대, 표시 대기와 실제 준비가 겹친
타이머 틱을 기록한다. 합산 겹침 시간은 실제 완주 단축 시간과 다르다. 은행 접근/호출자
처리와 VBlank 대기가 있으므로 단축 수치는 같은 여덟 완주 요청을 직접 비교한다.

## 검증

```text
npm test
npm run build:battle-opening-video
npm run verify:battle-opening-video
node tools/battle-opening-pipeline.mjs <PR49-baseline-folder>
```

기준 폴더에는 PR 49의 `report.json`과 `load.json`을 둔다. 도구는 기준 ROM 해시와
같은 고정 MesenCore인지 검사한다. 모든 그림·요청·한글·오디오 계획이 동일하고,
여덟 경로가 각각 단축됐는지 확인한다. 선행 준비 가능한 모든 인접 단계가 실제로
실행됐는지 카운터와 대조하며, 그림 게시 간격의 원작 최소 대기를 별도로 검사한다.

대기 검사는 `action_serial`이 기록되는 실제 SM83 메모리 쓰기 순간의 타이머를 사용한다.
스크린샷용 프레임 폴링은 단계 변경을 한 프레임 늦게 발견할 수 있으므로 그 관측 시각을
시작 시각으로 간주하지 않는다. 모든 단계의 쓰기 순서·프로필·항목을 캡처와 대응시키고,
대기 허용 오차는 기존 2타이머 틱 그대로 유지한다. VBlank/DMA/픽셀 검사는 별도다.

실제 재검증에서 두 번째 백어택 생존 경로 27→28단계는 프레임 폴링으로
117.432ms였지만, 단계 변경 쓰기 시각은 133.545ms였다(원작 최소 133.114ms).
앞 단계의 폴링 관측이 67틱 늦었던 것이 원인이다. 게임 ROM을 바꾸거나 판정 허용
오차를 늘리지 않고, 같은 ROM의 모든 1,520단계를 직접 기록해 대조했다.

기존의 상태 경계·전체 실제 캡처 픽셀·숫자 마감·원작 오디오 이벤트/APU 쓰기·활성
버퍼 보호 검사는 유지한다. 현재 네 경로 검증을 전체 편성·정상 플레이·실기나 음색
승인으로 확대하지 않는다. 전체 연출의 원작 속도 관문은 준비 마감과 함께 별도로 보고한다.

## 최종 검증 결과

전체 소요 시간은 PR 49의 17.831~24.227초에서 15.805~21.565초로 줄었다. 같은 여덟
요청의 단축률은 9.5~12.4%이며, 이전 두 번의 최적화와 혼합해 이번 단축률로 세지 않는다.

누락으로 마감을 맞춘 결과가 아니다. 다음에는 준비 자체의 비용을 오디오 생산·은행

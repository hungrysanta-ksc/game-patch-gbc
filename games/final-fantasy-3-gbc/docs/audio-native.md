# 원작 음악 엔진과 GBC 출력 연결

후속 업데이트: 현재 빌드는 256KiB 은행 호출 기반을 사용합니다. 아래 수치는 최초 통합의 이력이며, 최신 메모리 배치·업로드 단위·검증 결과는 [은행·메모리·시간 기반](platform-foundation.md)을 참고하세요.

기준일: 2026-11-22. 음악 요청·템포 진행·페이드 처리를 원작대로 이식하고 기존 GBC 음원 변환에 연결한다. 음색 조정은 계속 보류하며 녹음하지 않는다. 게임 전체나 최종 음질의 완료 선언은 아니다.

## 실행 경로

사용자 원본 NES ROM → 지원 해시 검사 → 사운드 원본 뱅크 추출 → C 엔진/출력 코드와 GBDK 링크 → `build/native/ff3-native-audio.gbc`.

128 KiB CGB 전용 MBC5 테스트 ROM 안에서 악보·반복·엔벌로프·음악 요청·효과음 처리를 직접 실행한다. 미리 만든 APU 타임라인이나 원본 함수의 반환 상태를 재생하지 않는다. 원본 ROM의 `$36/$37/$38/$39/$09` 뱅크를 데이터로 읽으며 포함된 6502 코드를 GBC에서 실행하는 것은 아니다. 추출/리컴파일은 로컬 빌드 과정에 속한다. 배포 소스에는 이 뱅크 데이터가 없다.

`audio-engine.c`는 단일 사운드 상태와 실제 C 함수 호출을 연결한다. `audio-music.c`가 새로 옮긴 범위는 `$8925..$8B9C`이며, 이전 단계의 제어부·채널 VM과 함께 사용한다.

| 원작 처리 | 보존한 동작 |
|---|---|
| 음악 요청 `$8925..$899E` | 새 곡, 같은 곡 재요청, 이전 곡 복귀, 정지, 페이드의 플래그 우선순위 |
| 곡 선택/초기화 `$899F..$8AA6` | 원본 뱅크/헤더 표, 비활성 `$FFFF` 채널, 원작이 초기화하는 필드만 초기화 |
| 정지 `$8AA7..$8ABF` | 즉시 음소거 또는 페이드아웃, 효과음 점유 채널 보존 |
| 페이드 `$8AF0..$8B2C` | 16논리 틱 간격, 종료 틱, 8비트 래핑과 원작 카운터 값 |
| 템포 `$8B2D..$8B9C` | 16비트 누적값에서 150씩 소비, 채널 4→0 순서로 악보 갱신, 채널 0→3 엔벌로프는 프레임당 한 번 |

같은 곡 재요청은 초기화를 생략하며, 이전 곡 복귀는 저장한 곡을 다시 초기화한다. 곡 `$37`의 보호/효과음 억제 예외도 보존한다. 템포 명령이 나왔을 때 그 틱에 이미 더한 값을 소급 변경하지 않는다. 요청 API는 음악 65슬롯, 효과음 97슬롯 범위를 검사한다.

## 실제 GBC 출력

`audio-output.c`는 이전 VGZ 플레이어와 같은 주파수/노이즈 표·CH3 파형·소프트웨어 스윕·음량 변경 시 재트리거 정책을 사용한다. 표 해시는 `4fe09777e2b2d7a51782b944a03b050484e00fc183c0c5eb3d422a7f8f90489c`다. 원작 `$4011` 쓰기는 논리 출력에서 대조하며, 기존 개발 후보인 2/4096초 CH4 타격음 차용을 별도로 적용한다. 원작의 정확한 DAC 파형을 재현했다는 뜻이 아니다.

GBC 배속 모드와 4096 Hz 타이머를 사용한다. 논리 원작 틱은 Mesen CE의 NTSC 값 `60.0988118623484 Hz`를 `60.0988 Hz`로 근사하여 68/69 타이머 틱 간격으로 누적 오차 없이 스케줄한다. 근사 오차는 0.2 ppm 미만이다. 소프트웨어 스윕은 별도의 120 Hz 일정으로 진행한다. GBC VBlank마다 한 번 호출하여 NES/GBC 프레임 속도 차이를 누적시키지 않는다.

메인 루프가 원작 코드와 변환을 계산하고 16칸 출력 큐에 쓰기 묶음을 준비한다. 선행 준비 한도는 205타이머 틱(약 50 ms)이며 마지막 준비 패킷 한 간격까지 더 진행할 수 있다. 인터럽트는 지정 시각에 GB 레지스터 쓰기를 수행한다. 즉시 게임 요청을 이미 준비한 과거 틱으로 소급 적용하지 않으므로 소량의 요청 지연이 있다. 최종 게임 통합에서는 이 지연과 CPU/뱅크 예산을 함께 검증해야 한다.

GBC 빌드는 `FF3_SINGLE_ENGINE`으로 단일 상태와 콜백을 직접 참조한다. 곡 뱅크 조회/물리 ROM 뱅크 전환은 캐시하며, 원작 계산 순서는 바꾸지 않는다. GBDK 기본 디스패처 대신 `ISR_VECTOR` 타이머 핸들러를 사용하고, 다음 패킷 시각까지는 최소 카운터 갱신만 수행한다. RAM 진단 스냅샷은 8논리 틱마다 별도 이중 버퍼에 완성한 후 공개한다. 큐의 소비 메타데이터와 출력 누적 해시는 모든 이벤트에서 갱신한다. 초기 C 구현에서 관측된 출력 시한 초과를 이 경로 최적화와 약 3원작 틱의 선행 준비로 해소했다.

초기 연결 검사에서 두 가지 실제 오류를 발견해 수정했다.

- 고정 코드 영역 초과를 링크된 원본 데이터 대조가 검출했다. 개발 메뉴의 일반 형식 출력 코드를 줄여 고정 영역 안에 배치했다. 빌드는 ROM 헤더/체크섬, 뱅크 데이터 일치, 컴파일러의 겹침/초과 경고를 검사한다.
- 고정 GBDK/SDCC에서 16비트 타이머의 하위 바이트를 유지하며 OR하는 식이 잘못된 post-increment 저장으로 변환됐다. 두 번째 타이머 뒤의 타격음 플래그를 덮어썼다. 상·하위 바이트를 별도 배열로 갱신하도록 바꾸었다. 이는 변환 음색 조정이 아니라 메모리 쓰기 오류 수정이다. 초기 생성 기계어와 실패 관측은 로컬 `evidence/native/`에 남긴다.

## 대조 방법과 범위

`audio-engine-test.c`를 호스트 C와 GBDK로 각각 컴파일한다. 원본 ROM의 실제 6502 드라이버로 만든 기준과 매 틱 사운드 RAM 192바이트, 논리 APU 24바이트, 쓰기 개수·주소·값·순서를 대조한다. 시나리오 안에서는 이전 C 상태를 그대로 이어가며 기대 상태를 복사하지 않는다.

총 **11,524틱 / 95,940회 APU 쓰기**다. 모든 음악 65슬롯의 각 96틱, 효과음 97슬롯의 각 32틱, 같은 곡 재요청·교체·정지·복귀·페이드·효과음 점유 시나리오와 플래그/템포/페이드 경계 상태를 포함한다. 경계 상태는 합성 입력이며 자연 게임 도달 상태와 구분한다. 모든 곡의 끝까지나 모든 곡/효과음 조합의 전수 검증은 아니다.

실제 출력 ROM은 3,600논리 틱의 자동 요청 순서를 실행한다. 노래 변경·동일 곡 요청·이전 곡 복귀·페이드인/아웃·효과음 재요청/정지·곡 `$37`의 예외를 포함한다. 원본 6502 실행과 독립 JS 변환 기준을 사용해 다음을 대조한다.

- 준비한 원작 RAM/APU 상태와 논리 쓰기 누적 해시.
- 준비/소비한 출력 이벤트 수, 논리 틱과 GB 쓰기 누적 해시.
- 실제 읽을 수 있는 GBC 엔벌로프/음량/노이즈 레지스터와 채널 활성 상태.
- 출력 마감 지연, 큐 고갈, 타이머 경과 시간과 에뮬레이터 master clock의 차이.

쓰기 전용 주파수 레지스터는 읽어 대조할 수 없으므로 큐 쓰기 기록/소비 경로로 검증한다. 16비트 누적 해시는 장기 기록 비교용이며 무음 엔진 검사에서는 원시 쓰기 목록을 직접 비교한다. 청취 음질·파형 동일성이나 실기 전체 부하를 증명하는 검사는 아니다.

## 확인 결과

호스트 검사와 GBC 에뮬레이터의 무음 엔진 검사에서 11,524/11,524 PASS를 확인했다. GBC 오류 검출용 ROM은 첫 사례의 기대 RAM 한 바이트를 변경하여 오류 4 / 인덱스 0을 검출했다. 전체 엔진/오류 ROM 해시는 각각 `c8bee3e8414a9f7ff13cf10d4aebb418def38f4690774981d60f2b6ce655c85d`, `927b928193fc0f34cfe92fc4a6dce651637307fc776285b8459dc8be620363fc`다.

실제 출력 ROM SHA-256은 `2b312970851e2bc2562c2da4d97494956d111d2a13fdc0edcf9cc1d9d5df4a37`다. 약 60초의 자동 시나리오 결과는 다음과 같다.

| 항목 | 결과 |
|---|---|
| 원작 논리 틱 / 출력 이벤트 | 3,600 / 10,753 |
| 상태 관측 / 음량이 켜진 하드웨어 관측 | 120 / 92 |
| 원작 상태·논리 출력 / GBC 변환·소비 기록 | 일치 |
| 최대 출력 시한 지연(1/4096초 단위) / 큐 고갈 | 0 / 0 |
| DAC 타격음 후보 발생 횟수 | 74, 기준과 일치 |
| 타이머와 master clock의 경과 시간 차이 | -0.00016737초, 한 타이머 틱 미만 |

별도 관리형 Mesen 실행에서 실제 버튼으로 음악 32 요청, 페이드아웃 종료, 효과음 1 요청과 B 정지를 확인했다. 이 조작 구간도 엔진 오류·출력 지연·큐 고갈은 0이었다. 검증기는 소리를 녹음하지 않았으며 청취 음색 합격을 선언하지 않는다.

공개 허용 목록의 소스 74개만 복사한 별도 폴더에서 사용자 원본 ROM을 다시 입력해 재생 ROM, 엔진/오류 ROM, 검사 기준, 변환 표와 빌드 보고서가 바이트 단위로 같음을 확인했다. 검사 기준 SHA-256은 `332f362ac6e50cfa20b9b953d79694228282f75a6e5106d8eebd7226ee074b9a`다. 기존 Node 회귀 검사 13개와 포인터/콜백 방식의 채널 호스트 검사 4,336개도 통과했다. 자세한 원시 관측·호스트/컴파일 로그·재현 대조는 로컬 산출물로 보존한다.

에뮬레이터는 기존과 같은 Mesen CE `20ba206cef5ba207c21203176d02cb9f43dda9fb`, emucap 패치셋 `2e5e6e9db63a24b3fc549f026ce7f4d69b7aa539bc859b537a002cdc116210dd`다. 자동 검증은 고정 MesenCore SHA-256 `1ba99d2c848e007c60cbd7fceca058440758eb44837a93a6724d29d72723c994`만 허용한다. C ABI는 안정 공개 API가 아니므로 다른 빌드는 별도 검증이 필요하다.

## 재현

```powershell
node tools/build-native.mjs --rom "D:/private/Final Fantasy III (Japan).nes" --gbdk "D:/tools/gbdk"
node tools/build-engine.mjs --rom "D:/private/Final Fantasy III (Japan).nes" --gbdk "D:/tools/gbdk"
node tools/build-native-verifier.mjs
node tools/verify-native.mjs --engine
node tools/verify-native.mjs --engine --negative
node tools/verify-native.mjs
```

검증 도구는 `local.json`의 `mesenCore`/`dotnet` 경로를 사용한다. 실제 출력 검사는 START와 같은 자동 요청을 메모리 명령함에 넣으며 기대 상태를 쓰지 않는다. 원시 관측·빌드 로그·검사 기준은 `build/engine/`, `build/native/`, `evidence/native/`에 보존한다. .NET 도구는 녹음 API를 호출하지 않는다.

공개 대상은 코드·명세·문서뿐이다. 원본/생성 ROM, 악보·APU 기록·기준 데이터·VGZ·번역 자료·디스어셈블리는 업로드하지 않는다. 후속 단계에서 제단 동굴의 원작 바위 이벤트와 맵 로딩을 함께 돌리는 [첫 통합 부하 검증](field-audio.md)을 추가했다. 이동·NPC 조건 선택·한글 렌더링까지 합친 부하는 남아 있으며 음색 판단도 별도 미해결 항목으로 유지한다.

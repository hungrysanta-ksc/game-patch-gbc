# 같은 전투 상태의 합성·타일 교체와 적 후퇴 배치

2026-11-24. 초기 연결 기준: PR 29 병합 `a0c407d5db6f4973056e8e7b0f323946b536957a`.
아래 초기 결과는 PR 30의 기록이다. 이후 속도·백어택 수정은 문서 끝의 후속 절에 구분한다.
[원작 전환 검사](battle-transitions.md)의 상태를 기존 합성기와 GBC 전송기에 연결했다.
원작 등장→강제 석화/해제→개구리/해제→아이템 표시→아군 자세 갱신이 **같은 원작 VRAM/OAM**을 사용한다.
일반 56·백어택 53개의 서로 다른 관측 상태를 GBC에서 순서대로 공급한다.

정상 전투 실행기가 아니다. 선택/HP 계산/행동 메시지/피해 숫자/승패는 이 연결에 아직 없다.
`next-selection` 표시는 아군 자세 갱신 경계 이름이며 실제 명령 메뉴를 실행했다는 뜻이 아니다.
원작 NMI 함수 호출 전과 함수 반환을 관측하므로 109개 상태를 원작 PPU의 109프레임으로 부르지 않는다.
기존 [전체 표시 계약](battle-scene-contract.md)의 통합 통과는 여전히 **0/8**, 제품 관문은 **0/3**이다.

## 원작 표시 입력과 변환

- 원작 `2E/9D5F`, `2F/B469`, `B5C3`, `B15E`, `B5B8`을 이전 참조기로 실행한다.
  음악 요청과 하드웨어 대기는 가로채며 게임의 전체 PPU/IRQ/APU를 에뮬레이션하지 않는다.
- 적·지형은 원작이 갱신한 이름표/CHR/팔레트에서 읽는다. 석화 아군은 OBJ만으로 대체하지 않고 BG에서 읽는다.
  아군 OBJ는 원본 크기와 원작 타일·표정·자세를 유지한다. 범위 밖 BG 우선 OBJ는 조용히 무시하지 않고 거부한다.
- 이번 편성 3의 적 영역은 기존 7/8 후보와 상대 슬롯을 유지한다. 아군 기준점은 `(128,10/34/58/82)`다.
  지형은 원작 y=8..23의 16줄을 잘라 쓰는 검사 후보다. 최종 배경/전체 UI 배치 승인으로 취급하지 않는다.
- 아이템은 원작 포션 효과 마법에 연결한다. 이번 효과는 세 번째 아군 대상이며, 대상 위치를 보존한다.
  모든 무기/마법의 화면 기준 위치를 이 아군 대상 변환 하나로 처리하지 않는다.
- 원작 OBJ 팔레트 네 개만 잔여 색에 쓰면 적끼리 섞이는 셀을 표시하지 못했다.
  이 입력에서는 원작 BG 0/1과 OBJ 1/3을 잔여 OBJ 팔레트로 선택해 색을 바꾸지 않고 합성했다.
  모든 편성의 최적 해법이 아니며 실패는 명시적으로 남긴다. BG 팔레트 하나는 한글 창에 예약한다.

## 사용자 피드백: 적을 뒤로 이동

아군과 적의 겹침을 줄이도록 **편성 전체를 기본 8픽셀 후퇴**시킨다. 일반 전투는 왼쪽, 백어택은 오른쪽이다.
각 적을 따로 재중앙 정렬하거나 아군/적의 크기를 바꾸지 않는다. `battle-layout.mjs`의 같은 이동량을
그림과 적 대상 마법의 기준점에 적용한다. 원작의 대상 선택/명중 계산/각도표를 변경한 것은 아니다.
물리 무기의 실제 궤적 이식은 미완료이며 향후 같은 기준점을 사용해야 한다.

화면 끝의 그림을 자르지 않도록 정착한 적 그림에 8픽셀 여유가 있는 편성만 옮긴다.
대표 편성 `3/13/47/44/234/301/79/83`의 실제 이동량은 `8/0/0/8/0/0/8/0`픽셀이다.
부족한 여유만큼 1픽셀 이동한 후보는 편성 47의 타일 경계 분할을 바꿔 OBJ 실패가 36→43상태로 늘어났으므로
채택하지 않았다. 타일 경계를 보존하는 8픽셀 이동 또는 유지로 정했다.
8편성에서 가시 픽셀과 상대 배치를 보존했다. 이미 가장자리에 붙은 편성의 겹침까지 해결했다는 뜻은 아니다.
이동량은 편성의 정착 상태에서 한 번 결정하므로 애니메이션 중 그림 폭에 따라 적이 좌우로 흔들리지 않는다.

편성 3의 원작 전환 관측에 대한 아군/적 불투명 픽셀 겹침은 다음과 같다. 효과 픽셀은 아군 실루엣으로 세지 않는다.

| 입력 | 겹침 있는 관측 상태: 전→후 | 한 상태 최대 겹침 픽셀: 전→후 |
|---|---:|---:|
| 일반 | 10→0 | 4→0 |
| 백어택 | 15→2 | 269→88 |

백어택에 남은 두 상태는 등장 도중이다. 등장 완료 후 상태/아이템 경로에서는 두 방향 모두 겹침 0이다.
이 수치는 이번 편성·자세 경로의 결과이며 모든 전투의 충돌 보증이 아니다.
이전 배치 회귀를 유지하며 `audit-battle-placement.mjs --retreat`로 이동한 적/효과의 별도 예산을 조사한다.

## 상주 128타일에서 활성/다음 그림 분리로

단일 마법의 전체 그림 합집합을 상주시킨 방식으로는 이번 173타일짜리 한 장도 담지 못한다.
기존 `battle-atlas.c`에 전투 장면용 전송 모드를 추가했다.

| 자원 | 소유권 |
|---|---|
| BG 그림 | VRAM bank 0/1의 `$8800..$97FF`, 페이지당 256타일. 현재 페이지는 게시 전까지 보호 |
| 지도 | `$9800/$9C00` 이중 지도. 타일 속성의 bank 비트가 그림 페이지를 선택 |
| OBJ 그림 | bank 1의 `$8000..$87FF`, 페이지당 64타일 영역 중 실제 최대 40개 사용 |
| 한글 창 | 먼저 BG를 bank 0으로 정규화. 이후 bank 1의 글꼴과 `$9C00` 창을 빌림 |
| 창 닫기 | bank 1의 이전 그림을 무효화. 다음 사용 때 필요한 그림·지도를 다시 공급 |

타일 ID는 `$8800`의 첫 그림을 128로 매핑한다. 근거는 Pan Docs의
[타일 주소 지정](https://raw.githubusercontent.com/gbdev/pandocs/master/src/Tile_Data.md)과
[CGB 지도 bank 속성](https://raw.githubusercontent.com/gbdev/pandocs/master/src/Tile_Maps.md)이다.
각 비활성 페이지의 이전 점유자와 다음 입력을 비교해 16바이트 정렬 변경 구간을 전송한다.
팔레트도 전환마다 게시한다. 원작 음악 생산은 전송 대기 중 계속 서비스한다.

이번 파일은 유한한 원작 상태 입력을 빌드할 때 합성한다. 실행 중 게임 상태를 합성하는 전체 렌더러는 아니다.
페이지별 이전 그림에 대한 변경 구간 표도 진단용이며 전편의 모든 조합 표로 확대하지 않는다.
공유 실행기의 라이브 입력/변경 타일 계산으로 교체해야 한다. 기존 단일 마법 자동 시계 경로는 보존한다.

## 검증 범위와 다음 순서

한글 7×7 창은 석화·아이템 효과·마지막 상태에서 열기→다음 페이지→닫기→같은 그림 유지로 검사한다.
창 문구는 기존 검수된 탐색 대사의 **자원 공존 검사 입력**이다. 새로 상상한 전투 문구나 완성 전투 UI가 아니다.
원작 필드 음악·효과음·페이드 7,200틱 스트레스 계획을 같은 GBC 실행에서 비교한다.
아이템/무기의 실제 사운드 호출 시점과 동기화했다는 주장은 하지 않는다.

현재 전송은 원작 애니메이션 속도에 사용할 만큼 빠르지 않다. 원작 시간표를 늘려서 통과 처리하지 않는다.
다음은 실제 HP/상태 아이콘/대상 번호와 5종 행동 창·피해 숫자를 **이 입력/전송 경로에** 추가하고,
팔레트/타일 번호의 안정화와 변경 셀 공급으로 전송량을 줄여 원작 표시 시계에 연결한다.
소환/특수 보스/종료·필드 복원과 이전 실패 편성도 전체 계약에 남긴다. 아군 축소와 음색 변경은 하지 않았다.

```powershell
npm run build:battle-scene
npm run verify:battle-scene
node tools/audit-battle-placement.mjs --retreat
npm test
node tools/export-source.mjs --check
```

ROM: `build/battle-scene/ff3-battle-scene.gbc`. 이는 검증기가 요청을 공급하는 진단 ROM이다.
자동 입력은 `verify:battle-scene`에서 수행하며 일반 조작 가능한 전투 게임으로 제공하지 않는다.
ROM/그림/로그는 로컬에만 둔다. 공개 소스 재현 빌드에는 원본 ROM, 비공개 검수 번역/폰트와 고정 GBDK가 필요하다.

최종 검증: ROM SHA-256 `ca3ff749760e940c2100878bc92ded65eb0738fcb9b7be3a35cc41d032ef7074`.
실제 GBC 109상태와 창 동작을 479회 요청했고, 258장·5,944,320픽셀을 대조했다.
원작 오디오 7,200틱·21,366이벤트를 소비했으며 지연/버퍼 고갈, 활성 그림 덮어쓰기, 잘못된 VRAM/DMA 쓰기,
LCD 끄기, 메모리 가드 오류는 모두 0이다. 고정 WRAM 끝은 `$CDF8`, 관측 스택 미사용 영역은 286바이트다.
화면 변경은 중앙값 **234.44ms**, 최대 **402.09ms**, 한글 창 열기는 최대 **670.09ms**다.
스크린샷을 위한 유지 시간은 이 요청 완료 시간에서 제외한다. 원작의 연출 유지 기한 통과로 세지 않는다.

기존 마법 자동 시계 ROM을 다시 빌드해 이전과 바이트가 같음을 확인했다
(`5d6d11e7d4ae344773be0362d4516fa9e2d31a5f70101b592f31ac27304e5b7d`).
그 경로의 과거 재생 결과를 이번 109상태의 원작 시간 보증으로 쓰지 않는다.
후퇴 배치 감사 SHA-256: `30dda129f5ef53733d0450f7b8d75c055311de69ebed53ee88ac3d5dd427f113`.
이전 8편성·197상태의 OBJ 실패 60개는 그대로 미해결이며, 편성 47의 실패를 늘리는 1픽셀 후보는 제외했다.
호스트 전체 시험 65/65와 최종 배치/은행 회귀 3/3을 통과했다. 공개 허용 소스 296파일을 새 폴더로 복사하고
명시한 비공개 입력 경로와 GBDK만 공급해 ROM을 재빌드했으며, 위 최종 ROM 해시와 일치했다.

## 후속: 전송량·VBlank 비용과 백어택 등장 수정

기준은 PR 30 병합 `e4618cba0bb3b03d9ad9c1feefa7ffeea548577f`이다.
백어택에 남았던 겹침은 적을 더 뒤로 옮겨 해결한 것이 아니다. 원작 `2F/AE5E..AEA3`은
적 등장 영역의 배경 페이지를 `$07`에서 읽는데 변환기가 `$06`을 사용했다. 그 결과 등장 중
오른쪽에서 들어와야 할 적 그림 일부가 아군 쪽으로 감겨 나왔다. 원작의 페이지 선택을 적용했고
원작 스크롤 값, 아군 위치/크기와 8픽셀 후퇴 정책은 유지했다. 실패를 재현하는 회귀는 이전 페이지를
선택했을 때 **2상태/최대 88픽셀** 겹침을 재현하고, 실제 페이지에서는 전체 등장 경계의 겹침 0을 요구한다.
잘못 읽어 같아졌던 상태가 구분되어 입력은 일반 56·백어택 56, 총 **112관측**이다.

속도 병목은 그림 자체의 크기만이 아니었다. 매 상태마다 다시 고른 팔레트와 앞에서부터 매긴 타일 번호가
작은 변화를 큰 타일 교체로 만들었다. 최초/최후 변경 위치 사이의 미변경 바이트도 전송했고,
VBlank의 C 디스크립터 순회와 핸들러 순서 때문에 전송 가능 시간을 소모했다.

- 원작 OBJ 팔레트가 같은 입력은 공통 BG 팔레트 계획을 사용한다. RGB555 색은 바꾸지 않는다.
  현재 유한 검증 입력에서 계산한 계획이며 전편의 모든 미래 프레임을 요구하는 제품 설계가 아니다.
- 이전 저장소에 남아 있는 현재 필요 패턴의 번호를 먼저 보존하고, 해제 가능한 슬롯에 새 패턴을 배정한다.
  이 배정은 현재 그림과 이전 저장소만 사용하며 애니메이션 전체 타일 합집합을 상주시키지 않는다.
- 비활성 페이지의 이전 점유자와 비교한 **16바이트 변경 마스크**를 사용한다. 타일 ID 지도 5바이트,
  속성 지도 5바이트, BG 그림 32바이트, OBJ 그림 5바이트를 48바이트 행에 저장한다.
  변경 없는 구간은 건너뛰고 연속 변경은 최대 256바이트로 묶는다. OBJ 그림도 차이가 있을 때만 전송한다.
  창이 빌렸던 페이지는 무효화 행으로 완전히 재공급한다. 이전 상태 조합표는 여전히 유한 진단용이다.
- `FF3_BATTLE_STREAM`에서만 짧은 SM83 전송 루프와 게시→전투 전송→텍스트 핸들러 순서를 사용한다.
  DMA는 LY 144..149 검사 후 시작하며 ROM 은행을 복원한 뒤 타이머 IRQ를 허용한다.
  스트림 모드에서만 한 전송을 128→256바이트로 늘렸다. 7바이트 디스크립터의 길이 0은 256바이트를 뜻한다.
  2배속에서 DMA 자체는 약 128µs이며 설정·복원까지 포함한 DI→EI 구간을 실제 CPU 시계로 측정해
  오디오 타이머 한 주기(1/4096초)보다 짧음을 검사한다. 기존 다른 모드는 128바이트 제한을 유지한다.
  [Pan Docs VRAM DMA](https://raw.githubusercontent.com/gbdev/pandocs/master/src/VDMA.md)의 정렬·은행·CPU 정지 조건을 따른다.
- 화면 게시가 늦었으면 OAM까지 포함해 다음 VBlank로 미룬다. 실제 게시 때 HRAM OAM DMA, 팔레트,
  지도 선택을 같은 VBlank에서 처리한다. 팔레트 루프는 8바이트씩 풀어서 오디오 IRQ를 허용한 채 비용을 줄인다.
  실제 지도 선택 순간 OAM이 해당 페이지의 160바이트와 같은지 버스 관측으로 확인한다.

중간 후보의 게시 지연 오류는 실패로 보존했다. 전송 루프만 바꾼 후보는 관측 프레임 618,
변경 마스크와 초기 게시 보완 후보는 2703에서 `scene_error=8`이 나왔다. 이를 허용하거나
오디오 검사를 완화하지 않고, 핸들러 순서와 팔레트 비용을 함께 수정했다.
원작 오디오 생산/소비 코드와 음색 변환은 변경하지 않았다.

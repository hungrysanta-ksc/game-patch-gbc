# 전투 난수 상주 배치와 좌표 변환 비용

기준은 PR 80 병합 `7f3c9b64bbae363db7805abe4e924b1fdbd5e0bb`다.
새 연출을 추가하지 않고 고정 WRAM 부족과 검류의 성능 회귀를 분리해서 조사한다.

## 원작 소유권과 수명

`3F/FC27..FC91`은 전투 초기화에서 가상 NES 제로 페이지와 진입 A/C를
ADC 체인으로 합친 뒤 최종 바이트를 세 난수 카운터 `$15..17`에 넣는다.
`FC34..FC39`에서 그 바이트의 bit 1로 승수 3 또는 5를 선택한다.
`FC3B..FC91`의 표 생성에는 다른 초기 상태가 남지 않는다. `$7BE3..7CE2`의
256바이트 표는 다음 초기화까지 불변이며, `FBEF..FC26`과 직접 조회하는
전투 계산 소비자들은 원작의 세 카운터를 나누어 사용한다.

`32/98E0..991E` 명중 연출은 짝수 프레임에 카운터 0으로 두 값을 소비하고
각각 31을 AND하여 타격점을 만든다. 홀수 프레임은 같은 점을 유지한다.
`33/A44F`의 0..255 범위 호출은 원작 반올림 계산을 포함해 표의 바이트 그대로다.
매 행동 재시드하거나 연출 전용 난수열을 새로 만들지 않는다.

GBC에서는 원작 코드로 생성한 두 표 512바이트를 기존 연출 ROM bank 52에
보관하고 `{variant, counter[3]}` 4바이트만 RAM에 둔다. 별도 은행 전환이나
IRQ 공유 scratch를 추가하지 않는다. 기존 가변 표 표현은 아직 독립 계산 검증에
남아 있다. 현재 실제 화면은 명시한 원작 상태를 받는 개발 경계이며, 정상 전투
초기화와 계산이 이 커서를 공유하도록 연결하는 일은 아직 남아 있다.
variant는 진입 A 자체가 아니라 **ADC 체인이 끝난 값**의 bit 1이다.

빌드는 원작 생성기를 최종 초기값 256개에 대해 실행하여 정확히 두 표로
분류되는지 검사한다. 두 표의 합친 SHA-256은
`d1751ab6c928dcc5bf552a560440507f7ab279961a89de2bb81fe0d5de71707c`다.
링크 후 실제 bank/주소 범위와 ROM 바이트도 검사한다. 임의의 256바이트 표를
이 표현으로 바꿀 수 있다는 주장은 하지 않는다.

## 좌표 변환 구조

`33/A365..A3DA`는 검류와 봉 계열의 공통 양손/8프레임 루프다.
배우/무기 갱신과 `32/97B2` 명중 소비자를 호출한 뒤 `F8B0`에서 표시를 기다린다.
NES 소비자는 최종 OAM 좌표를 바로 쓰지만, GBC는 승인된 V6 배치와 적의 7:8
축소에 맞춰 좌표를 변환해야 한다. 원작 OAM 순서와 도트를 유지하면서 이 추가
변환 비용을 줄이는 것이 이번 변경의 범위다.

기존 한 함수의 객체마다 검사하던 배우/타격 구간 전환을 구간 시작으로 옮긴다.
0..9의 배우/무기와 10 이후의 타격 데이터를 동일한 투영 함수에 전달한다.
원작 데이터 생성, 난수 호출, 프레임 수, 동일 그림 재게시, OAM 순서와 경계 검사를
유지한다. 오디오 서비스 지점도 원래 원본 객체 인덱스 0/8/16을 유지한다.
별도 프레임 캐시나 프레임 생략은 추가하지 않는다.

`2F/B24F..B258`은 전진 후 직업 그림과 양손 무기를 준비한 다음 연출을 시작한다.
`2F/A8EA..A962`가 두 손을 모두 로드하고, 그 그림은 행동 종료 때까지 상주한다.
이 수명과 순서는 그대로 유지한다. 두 128바이트 무기를 기존 작업 버퍼에 모아
한 전송 요청으로 보내는 대안도 비교했지만, 전체 시간과 최악 간격은 같고
준비 비용만 0.291ms 증가했다. 이 대안은 채택하지 않았으며 원래 ROM 직접 전송을
유지한다. 전송 묶음 수만 줄었다고 실제 처리 비용도 줄었다고 판단하지 않는다.

분리 투영만으로 전체 준비 비용은 719.235→655.823ms, 전체 행동은
2,244.289→2,177.116ms로 줄었다. 하지만 첫 칼질인 게시 9의 106.689ms 간격은
남았다. 같은 구간의 PR 79 대비 순수 준비/전송 대기는 35.869→36.207ms로
거의 같았고, 오디오 생산·표시 대기·IRQ의 겹침이 차이를 키웠다.
따라서 난수 표 접근이 느려서 생긴 회귀로 진단하지 않는다. 분리 투영은 반복
비용을 줄였다. 최악 간격은 최초 이동 프레임부터 자원 교체까지의 실제 실행 위상과
함께 검사해야 한다.

## 검증 구분

`verify-battle-strike.mjs --auto --action-only`는 개발 중 짧은 시간 비교용이다.
`probe/`에 따로 저장하고 `completeAudio:false`로 표시한다. 행동 완료 시점까지의
게시·요청·소비 해시·안전 검사를 하지만 전체 7,200틱 오디오나 모든 화면 검증을
대신하지 않는다. PR 80의 짧은 측정은 기존 전체 측정의 2,244.288921ms,
83게시와 10요청을 그대로 재현했다. 최종 승인은 짧은 옵션 없이 수행한다.

난수 표만 바꾼 빌드는 고정 WRAM 끝이 `CFF7→CEF8`, 여유가 `9→264`바이트로
개선됐지만, 검류의 시간은 정확히 2,244.288921ms로 같았다. 메모리 배치와
속도 회귀는 별개라는 실측 근거다. R2 0/8·제품 0/3은 그대로다.

## 채택한 빌드의 측정

이동 좌표 변환도 별도 함수로 분리하고 전진·복귀 시 사용하지 않는 공격 scratch
초기화를 제거했다. 원작 이동 출력과 숫자 진입 시의 scratch 초기화 책임은 유지한다.
모든 표시는 여전히 83번 게시하며, 59번 준비하고 같은 그림 24번을 재사용한다.
양손 요청/정리 10회도 유지한다.

화면 검증기는 임시 버퍼 첫 바이트가 240인지로 이동/공격을 추측하던 방식을
제거한다. 원래 동일 그림 재사용에 쓰던 유효 상태를 `strike_picture`로 공개해
그 값으로 구분하며, 새 런타임 상태는 추가하지 않는다. 이 상태가 공격일 때는
원작 160바이트 OAM 전체, 이동일 때는 원작 아군 OAM과 상주 화면 전체를 대조한다.
어느 경우에도 최종 GBC OAM·화면 픽셀 비교를 생략하지 않는다. 구형 기준 ROM만
종전의 버퍼 표식을 사용한다.

| 같은 검류 최대 양손 조건 | PR 79 | PR 80 | 이번 빌드 |
|---|---:|---:|---:|
| 전체 행동 ms | 2177.051 | 2244.289 | 2177.117 |
| 최초→최종 게시 ms | 2057.617 | 2155.762 | 2074.219 |
| 최대 게시 간격 ms | 83.984 | 106.689 | 106.689 |
| 화면 준비 CPU ms | 655.614 | 719.235 | 651.788 |
| 고정 WRAM 여유 바이트 | 271 | 9 | 264 |

간격은 기존 검증기의 게시 완료 카운터를 같은 방식으로 관측한 값이다. 대기 중
오디오 생산이 이어지면 실제 OAM DMA보다 완료 관측이 늦을 수 있으므로, 후속에서는
실제 표시 시점과 이 완료 시점을 분리해 측정해야 한다.

전체 행동은 PR 80보다 약 3.0%, 준비 CPU는 약 9.4% 줄었다. PR 79보다 전체가
빠르다고 주장하지 않으며, 최대 간격 회귀도 남아 있다. 첫 칼질 게시 9의 106.689ms는
준비/전송 대기 36.207ms, 오디오 생산 52.671ms, 표시 대기 7.843ms, IRQ 9.969ms다.
이 구간은 이후에도 별도 수치로 추적한다. 봉 계열의 같은 최대 양손 조건은
2177.077ms, 준비 CPU 614.599ms이고 최대 간격은 동일하다.

bank 52 사용량은 `0x721→0x92C`(+523바이트: 표 512와 접근 코드),
bank 55는 `0xCBF→0xCF1`(+50바이트)다. ROM 전체 크기는 늘지 않고,
추가 고정 RAM이나 WRAM 은행 전환은 없다. 단순 RAM 절약을 전체 성능 향상의
원인으로 설명하지 않는다.

이번 ROM SHA-256:
`1590386beba82c23986ff38c2edbb20bf6258a13a73f7f483f7b0f49f5b1f6e8`.
지원 범위는 기존 검류/봉 계열과 숫자 연계 그대로이며, 치명타·특수 상태·아군 피격·
다른 무기·마법·사망의 성공 처리를 추가하지 않았다. 다음은 남은 최초 칼질 지연의
자원 준비와 오디오 생산 겹침을 줄이고, 이후 미지원 원작 소비자를 연결하는 순서다.

## 최종 검증

- 호스트 `npm test`: 176/176 통과.
- GBC 원작 메타스프라이트·명중 생성기 2,016조건, 잘못된 variant의 무변경 거부,
  의도적 음성 대조 실패 감지 통과. 기존 기준 fixture 해시는 변하지 않았다.
- 봉 계열 부하 636장, 모든 적 위치/정면·백어택 688장, 무기→숫자 116장,
  검류 회귀 368장, 기존 밀집 숫자/공통 호출자 198장: 합계 2,006장.
  원작 OAM·패턴·팔레트와 실제 GBC OAM·화면 픽셀이 모두 일치했다.
- 위 5개와 자동 검류/봉 계열 2개의 총 7회는 각각 7,200틱을 끝까지 실행했다.
  동적 효과음 요청·원작/변환 소비 해시 일치, underrun·late·VRAM/OAM·메모리 가드
  오류 0. 짧은 `--action-only` 측정을 전체 오디오 승인으로 사용하지 않았다.
- 허용된 소스 588개만 별도 디렉터리에서 빌드해 ROM/보고서 등 9산출물이 동일했다.
  원본 ROM·번역·추출 자산·스크린샷·오디오·로그는 비공개 로컬 입력/증거로 유지한다.

음색 조정이나 실제 기기 청취 승인을 주장하지 않는다. 정상 게임 통합 관문도 별도다.

# 등장·인빈시블 포격의 V6 화면과 오디오 연결

기준: PR 47 병합 `d851b1606bb3354be7dc0d003f59541afab2bd5a`.
작업 브랜치 `ff3-opening-video`. 원본/생성 ROM, 추출 그림, 번역, 화면과 오디오 관측은 비공개다.

## 연결한 소비 경로

`ff3_opening_start/ack`의 요청이 실제 V6 전송·게시·숫자 자동 재생을 호출한다.
표시가 완료돼야 상태 확정, 적 소멸 집계, 결과 판정과 다음 선택으로 진행한다.
GBC에서 실행하는 것은 이식 C 호출자다. 원작 6502 실행은 빌드/검증 기준 도구다.
렌더링 입력은 현재 정면/백어택 × 포격 후 생존/전멸의 네 경로에 한정된 원작 관측 자산이다.
모든 편성·상태를 실시간으로 생성하는 전투 렌더러나 정상 게임 진행 완료를 뜻하지 않는다.

- 등장: `2F/B469`, 초기 사망·석화·개구리·정상 파티와 앞/뒷줄을 유지한다.
- 포격: `32/84C9..854A`. 포탄과 폭발 메타스프라이트를 묶음 단위로 평행 이동해
  V6 적 영역에 배치한다. 그룹 안 도트·타일 간격은 축소하지 않는다.
- 숫자: `33/AD2B..ADA5`. 첫 호출은 32회 표시한다. 두 번째 호출의 모든 값이 `FFFF`이면
  원작은 반환하므로, 이전 숫자 OAM을 임의로 삭제하지 않는다.
- 사망: `2F/BAEE` 등 실제 그래픽 본문과 종류 제거/보상 집계 완료를 연결한다.
- 메시지: `34/95C6`의 공유 문자열 기준 `0620` + `3D` → `065D`,
  제공된 번역의 `MSG_SYSTEM_023`을 수정 없이 연결한다. 바인딩은 비공개다.
- 메시지 속도 4의 원작 32회 대기와 창 닫기, 그래픽 `$25` 정리를 보존한다.
- 생존 경로는 다음 선택 준비 경계, 전멸 경로는 승리 호출자 경계에서 끝난다.
  승리 보상 지급/필드 복귀나 새 명령 입력까지 완료한 진단은 아니다.

HP는 같은 명시적 전투 입력을 원작 HP 문자 생성기에 전달한다. 사망 슬롯은 0,
나머지는 서로 다른 현재/최대 HP의 검사 입력이다. 자연 진행 세이브라고 주장하지 않는다.
행동 메시지창과 HP 4행은 기존 원작 프레임·팔레트·한글 7×7 경로를 재사용한다.

## 오디오와 메모리

초기화의 실제 원작 요청 곡 `$20`을 계속 재생한다. 화면 코드가 발생시킨 효과음 요청
`$80`(포격), `$B1`(적 소멸)을 오디오 엔진의 0, 49번 효과음으로 전달한다.
요청이 수락된 원작 논리 틱을 기록해, 독립 6502 오디오 참조와 GBC APU 쓰기를 비교한다.
임의 효과음 예약표가 포격 시점을 대신하지 않는다. 음색 변환 정책은 이번에 바꾸지 않는다.

전투 표시 동안 WRAM bank 1의 `$D000..D2C7`을 호출자 상태가 소유한다.
타이머/오디오 큐/스택, `$D2C8..D7EF`, 기존 창·전송 작업공간과 보호 바이트는 별도다.
이 수명은 진단 전투 전용이며, 탐색 실행기와의 모드 전환/필드 재구성은 아직 통합하지 않았다.
코드·초기 입력은 ROM bank 16을 예약하고 한글 자산은 bank 17부터 배치한다.

변경 블록 목록은 동일한 48바이트 행을 공유하는 사전으로 저장한다. 각 프레임은
모든 이전 화면에 대한 은행/주소 색인을 보유한다. 그림·색·프레임을 삭제하지 않는다.
숫자 표시에서는 불변 OAM 데이터와 은행을 먼저 고정하고, VBlank 게시 후 다음 그림의
비활성 OAM 버퍼를 준비한다. 오디오 디코더가 길어져도 숫자의 공급 시점을 미루지 않는다.
ROM 은행은 복원하고 WRAM 은행/스택은 이동하지 않는다.

OAM DMA는 계속 VBlank의 HRAM 루틴에서 인터럽트를 막고 실행한다. 다음 OAM의 CPU 복사는
그 DMA가 끝난 뒤 타이머 인터럽트를 허용한 상태에서 비활성 WRAM 버퍼에 수행한다.
근거: [Pan Docs OAM DMA](https://gbdev.io/pandocs/OAM_DMA_Transfer.html),
[VRAM/OAM 접근](https://gbdev.io/pandocs/Accessing_VRAM_and_OAM.html).
실기 합격은 별도이며 아래 실행 검증은 고정 MesenCore 기준이다.

## 검증 명령과 관측

```text
node --test tests/battle-opening-video.test.mjs
npm run build:battle-opening-video
npm run verify:battle-opening-video
```

실제 화면 캡처와 원작 도트의 V6 투영 결과를 픽셀 단위로 비교한다. 모든 요청의
705바이트 상태를 원작과 대조하고, 잘못된 VRAM/OAM 전송·활성 버퍼 덮어쓰기·오디오
타이머 지연·큐 고갈을 실패로 처리한다. 원작의 32회 숫자 프레임은 별도 게시 시계로 검사한다.

초기 실패 기록: 포격 처리 중 다음 숫자 OAM 공급이 늦어 `scene_error=13`이 발생했다.
다음 실행에서는 그 경계를 통과했지만 전멸 경로에서 오디오 큐 고갈 4회를 검출했다.
검사를 완화하지 않고 OAM 공급 책임과 오디오 선행 준비량을 수정했다.

전체 장면의 전송 준비 시간은 원작 대기 길이와 구분해서 보고한다. 숫자 구간의 속도 검증을
등장·포격 전체 속도 통과로 확대하지 않는다. R2 전체 통합 0/8, 제품 관문 0/3을 유지한다.

### 최종 결과

- 호스트 회귀 126/126, 별도 소스 복사본의 새 검증 1/1 통과.
- 공개 허용 소스 414개만 복사해 빌드한 ROM과 보고서가 일치했다.
- ROM SHA-256: `01f15b3f582ea06adaa4d8c60ac5a788aaa59f0968627cbfece008dba030606d`.
- 고정 MesenCore SHA-256: `1ba99d2c848e007c60cbd7fceca058440758eb44837a93a6724d29d72723c994`.
- 4경로 × 2회, 상태 경계 348건, 표시 단계 1,520건, 실제 캡처 1,784장
  (41,103,360픽셀) 일치. 생존 후 선택 준비 4회와 전멸 후 승리 호출자 4회다.
- 전체 최대 OBJ 40개, 한 줄 9개. 숫자 구간은 최대 32개/한 줄 6개다.
- 숫자 8회 × 32프레임, 공급 지연 0회, 원작 시간의 GBC 투영 오차 최대 3.207ms.
- 원작 오디오 21,600틱/64,783이벤트, 화면에서 발생한 효과음 12요청,
  APU 쓰기 144,407건 대조. 큐 고갈·출력 지연·잘못된 VRAM/DMA·활성 OAM 버퍼 덮어쓰기 0회.
- 타이머 누적 오차 -1.923ms, DMA 인터럽트 차단 최대 0.163ms, 스택 미사용 267바이트.

첫 전체 대조에서 1,000장 이상 캡처의 파일명을 문자순으로 정렬하는 검사기 버그를 발견했다.
숫자순으로 고쳐 같은 ROM/코어/실행 기록을 다시 대조했고 모든 캡처가 통과했다.
검사 기준을 낮추거나 기대 그림을 실행 결과로 대체하지 않았다.

**남은 속도 문제:** 등장부터 다음 경계까지 28.18~36.48초다. 원작 표시 대기 합계
241/297프레임에 화면 준비 시간이 추가되므로 전체 연출 속도 관문은 미통과다.

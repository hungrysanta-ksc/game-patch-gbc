# 일반 전투의 배경 자원 보존과 초기 준비

기준은 PR 91 병합 `f2bf848b224a8e0a757850e9098f8c915f005c31`의
[일반 마법 상주 자원](battle-magic-residency.md)이다. 기존 적→아군 보통 마법과
밀집 숫자의 준비/복구를 개선한다. 정상 전투, 새 마법 종류의 완료로 세지 않는다.

## 원작의 소유권과 GBC의 차이

원작 `2F/B15E → AF14 → 33/B68D`의 적 시전은 아군 시전 자세/전진을 건너뛴다.
`33/B589..B5B8`은 효과 자원 07/08을 적재하고 `B6DD`부터 대상을 순회한다.
`B711`은 A05E로 효과 OAM을 지우고 다음 그림/좌표를 생성한다. `2F/B175`는
숫자 자원 06을 복구한다. 이 경로에서 배경 지도를 매번 새로 만들거나 보존하지 않는다.

GBC는 숫자 32 OBJ 및 큰 마법과 원본 크기 아군을 함께 유지하기 위해, 정지한
아군의 일부만 임시 BG에 보존한다. signed BG 주소와 다른 지도 페이지를 빌리는
동작은 GBC 제약에 따른 추가 비용이다. 움직이는 아군을 일반적으로 BG로 바꾸거나
원작의 도트·숫자·대기 수를 생략하지 않는다.

이번 변경은 두 종류의 수명을 구별한다.

- **불변 패턴:** 현재 `--effects` 빌드는 돌/보스 변형을 제외한다. 상주 적 패턴
  bank1의 0..127번 타일은 입장 때 ROM에서 적재된 그대로다. 지형은 128번 이후에
  배치하며 빌드에서 범위를 검사한다. 마법만 이 앞부분을 일시적으로 빌렸다가 돌려준다.
  따라서 signed BG용 사본과 마법 뒤 복구는 같은 ROM 정본에서 직접 공급한다.
  VRAM→WRAM으로 정본을 다시 백업하지 않는다. 로드 비용을 입장 구간으로 옮기지도 않는다.
- **변하는 지도:** 적 점멸과 지형 때문에 활성/비활성 지도는 실제로 다를 수 있다.
  원래 비활성 지도를 같은 것으로 추정하지 않는다. 활성 지도+임시 아군을 실제
  비활성 지도와 비교하고, 바뀐 16바이트 구간을 포함하는 최대 128바이트 묶음을
  보존/전송한다. 짧은 미변경 간격도 묶으면 VBlank 인계 횟수를 줄일 수 있다.
  이 간격의 원래 바이트까지 저장하므로 복구는 여전히 정확하다.

전체 지도 작업 사본과 셀마다 작업 지도에 쓰던 은행 복사를 제거했다. 합성 팔레트는
이미 있는 셀 키의 상위 비트에 저장한다. 9바이트 변경 비트맵으로 복구 범위를
기록하며 새 WRAM 은행은 쓰지 않는다. 최대 80개 합성 타일과 기존 원본 OAM,
팔레트, 동적으로 바뀌는 UI 타일/아군 패턴의 실제 백업은 유지한다.

돌/보스가 패턴 앞부분을 수정하는 경로를 이 불변 정본 규칙에 합치면 안 된다.
조합은 빌드에서 거부하며, 앞으로 그 소비자를 통합할 때 자원 소유권부터 확장한다.

## 비용과 한계

같은 35게시 마법을 고정 MesenCore에서 측정했다. 원작 유지 프레임 수는 같다.

| 항목 | PR 91 | 이번 변경 |
| --- | ---: | ---: |
| 전체 행동 | 2,797.034ms | 2,612.753ms |
| 초기 준비 포함 최대 게시 간격 | 1,439.874ms | 1,221.980ms |
| 초기 준비 이후 최대 게시 간격 | 83.723ms | 100.470ms |

초기 최대 간격은 약 15.1%, 전체는 약 6.6% 줄었다. 연출 중 최장 간격은 한
VBlank 정도 늘었다. 준비 종료와 오디오 생산 구간의 정렬이 달라진 결과이며,
모든 게시 간격이 개선됐다고 주장하지 않는다. 오디오 명령/출력이나 도트를 건너뛰어
맞추지 않는다. 최초 셀 합성에 아직 약 442ms가 걸리고 원작 속도에는 미달한다.

16바이트 변경 구간만 따로 전송한 후보는 보존량을 560바이트로 줄였지만 전체
행동이 3,031.545ms로 느려졌다. 그래서 전송량 최소화 대신 인접 구간을 묶는
방식을 채택했다. 고정 WRAM 버퍼를 늘린 후보도 실효 개선이 없어 제거했다.
최종 고정 WRAM 끝은 `$CF7C`(경계까지 132바이트)이며 추가 은행은 없다.

다음은 같은 원작 상주 수명을 유지하면서 아군 셀 합성의 반복 읽기/변환을 줄이고,
이미 표시하는 유지 프레임 동안 다음 그림 준비를 분산할 수 있는지 검토한다.
이는 원작 대기 수와 소리 요청 시점을 보존한 별도 측정이 필요하다.

## 검증 범위

`battle-freeze-audit.mjs`는 고정 MesenCore의 물리 VRAM을 읽기만 한다.
동결 직전 원래 패턴과 ROM 정본, 동결 직후 signed 사본을 바이트로 대조한다.
호출자 종료 때 두 페이지·두 은행의 **4,096바이트 지도 전체**와 원래 패턴을
다시 비교한다. 화면 밖 열/행도 포함한다. 화면 픽셀만 같아서 숨은 지도 오류를
통과시키지 않으며, 보존 바이트와 준비/복구 전송량의 균형도 검사한다.

기존 원작 실행 기반 픽셀/OAM·창·숫자 대조, 음악/효과음 요청과 변환 출력,
VBlank/VRAM 접근 검사도 그대로 실행한다. 검증 모드의 입력 주입은 원작 호출자
연결의 증거이며 정상 메뉴·계산·전편 플레이의 증거로 확대하지 않는다.

최종 ROM `61ce7889f38aa961114ef1a38d46c1c60f4fc1e5a0f087f86148464e946fe175`에서
940개 화면, 11회 × 7,200 = 79,200 오디오 틱을 통과했다. 원작 명령/출력 해시와
효과음 요청을 대조했으며 오디오 부족·늦은 처리·불법 VRAM/OAM 접근은 0이다.
13회 임시 배경 사용에서 지도·정본 패턴·signed 사본 불일치가 모두 0이었다.
마법 상주 풀은 593회 중간 검사에서 프레임별 재전송이 없었다. 대표 행동은
지도 704바이트를 보존하고 준비/복구 합계 1,408바이트를 전송했다.

최대 30쌍 마법은 35게시/2,612.743ms, 아군 4명 대상은 142게시/5,744.728ms다.
양손 지팡이의 83게시/2,110.163ms와 최대 게시 간격 83.956ms는 유지됐다.
호스트 테스트 10/10과 독립 폴더의 공개 소스 624개 재빌드도 통과했고,
ROM 3개를 포함한 12개 산출물이 바이트 단위로 일치했다.
고정 MesenCore SHA-256은
`1ba99d2c848e007c60cbd7fceca058440758eb44837a93a6724d29d72723c994`다.

재현 명령:

```text
node tools/build-battle-party-oam.mjs --effects
node tools/verify-battle-magic.mjs
node tools/verify-battle-magic.mjs --back --status --skip-build
node tools/verify-battle-magic.mjs --flips --skip-build
node tools/verify-battle-magic.mjs --flips --back --status --skip-build
node tools/verify-battle-magic.mjs --auto --skip-build
node tools/verify-battle-magic.mjs --auto --case 1 --skip-build
node tools/verify-battle-magic.mjs --auto --case 2 --skip-build
node tools/verify-battle-effects.mjs
node tools/verify-battle-strike.mjs --numbers --skip-build
node tools/verify-battle-hit.mjs --numbers --back --skip-build
node tools/verify-battle-strike.mjs --auto --skip-build
```

R2 0/8·제품 0/3은 유지한다. 성능 검증을 원작 속도 도달이나 음질 승인으로
세지 않는다. 원본 ROM·번역·추출 자산·검증 화면은 공개 패키지에 넣지 않는다.

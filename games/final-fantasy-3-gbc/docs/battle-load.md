# 전투 초기 로딩: 팔레트 일괄 게시와 음악 틱 고정 비교

## 원작과 유지한 구조

원작 2F/B469..B479는 진입 상태를 초기화하고 AD53을 호출한 다음 아군을 이동시킨다.
2F/AD53..AD83은 배경 자산 256바이트를 읽고 적 진입을 초기화한 뒤 F8B0에서 OAM/색을 게시한다.
3F/F8B0..F8B9는 NMI 대기, OAM 복사, 전체 팔레트 복사, PPU 레지스터 갱신 순서다.
색 하나를 보낼 때마다 음악을 계산하고 별개의 다음 VBlank를 기다리는 구조가 아니다.
고정 원본 ROM과 기존 원작 상태 실행기를 기준으로 진입/게시 의무는 유지한다.

기존 GBC 경로는 팔레트 8바이트마다 전경에서 LY 144–146을 기다리고,
그 뒤 원작 오디오 생산자를 호출했다. 긴 오디오 처리로 그 짧은 구간을 놓치면
다음 VBlank까지 다시 기다렸다. 또한 주 루프가 작업 플래그를 읽은 뒤 요청이 들어오면
loader 초반에는 화면 준비용 보충 계약이 설정되지 않을 수 있었다.

이번 변경은 다음으로 한정한다.

- 기존 VBlank 전송 큐와 WRAM staging/descriptor를 재사용해 연속 팔레트를 게시한다.
  팔레트 1개(8바이트)마다 별도의 짧은 critical section을 사용하고 그 사이 타이머 IRQ를 허용한다.
  데이터/대상 범위를 검사하고, palette mode 5는 기존 타일·대사 팔레트·창 표시 mode와 구분한다.
- 같은 네 BG 팔레트와 네 색 보정 OBJ 팔레트를 각각 한 요청으로 보낸다.
  초기 검정 BG, 객체 숨김, 그래픽 교체, 아군 색, 첫 그림 게시의 의무는 유지한다.
  BG/OBJ의 중간 교차 쓰기 순서는 바뀌지만 객체는 숨겨져 있으며 실제 첫 그림과 팔레트 RAM을 검증한다.
- loader 진입 시 party_work를 설정한다. 이미 사용 중인 화면 준비의 두 틱 보충 계약을
  로딩 전체에 명시하며, 큐 크기·타이머·원작 음악/효과음/페이드 명령이나 변환 표는 바꾸지 않는다.

CPU가 색을 게시하는 대신 VBlank 소비자가 일을 맡는 것이 GBC의 변경점이다.
[Pan Docs Palettes](https://raw.githubusercontent.com/gbdev/pandocs/master/src/Palettes.md)의
CRAM 접근·자동 증가 규칙을 따른다. Mode 3에는 색 쓰기가 무시되므로 실제 모든 쓰기가
Mode 1/LY 144–150에 있는지 검사했다. 추가 상주 버퍼나 정적 WRAM 증가는 없다.
정적 끝 주소 0xCDD6, 0xD000 앞 여유 554바이트를 유지한다.

## 동일 음악 시점으로 비교

PR 64의 전체 순회는 준비 시간이 달라지면 다음 요청이 만나는 음악 시점도 달라진다.
새 검증은 프로필마다 ROM을 새로 부팅하고, 원작 오디오 소비 틱 96 또는 224의 실제 기록 시점에
프로필/로딩 요청만 넣는다. 오디오 상태·시계·큐·게임 자산은 변경하지 않는다.
첫 화면과 그 이후 최소 120틱을 검사한다. 이 개입은 로딩 함수의 검증이며 탐색에서 자연스럽게
전투를 시작하는 경로 완료를 뜻하지 않는다. 오디오 전체 종료는 별도의 10,800틱 실행으로 검증한다.

CPU가 요청을 처음 읽은 시점부터 요청 완료까지의 시간(ms):

| 원작 소비 틱 | 프로필 | PR 64 | 이번 | 감소 |
|---|---|---:|---:|---:|
| 96 | 0 | 1472.785 | 986.701 | 33.0% |
| 96 | 1 | 1472.785 | 986.701 | 33.0% |
| 96 | 2 | 1472.785 | 986.701 | 33.0% |
| 96 | 3 | 1472.785 | 986.701 | 33.0% |
| 224 | 0 | 1853.873 | 1022.574 | 44.8% |
| 224 | 1 | 1853.873 | 1036.979 | 44.1% |
| 224 | 2 | 1853.873 | 1022.574 | 44.8% |
| 224 | 3 | 1853.873 | 1036.979 | 44.1% |

틀이 다른 총 소요 시간을 섞지 않는다. 첫 두 단계의 팔레트 요청 결합과 작업 플래그 수정은
함께 적용했으므로 각각의 단독 효과로 분해해 주장하지 않는다. 같은 음악 시작 시점이어도
종료 시점은 달라진다. 로그의 audioMs는 해당 요청 동안 실제로 실행된 생산자 시간이다.

각 로딩은 팔레트 쓰기 128바이트, VRAM 전송 11392 또는 11584바이트로 기준과 같다.
BG 팔레트 32바이트와 OBJ 팔레트 64바이트는 투명색을 포함해 링크된 원작 변환 자산과 대조한다.
실제 첫 화면 픽셀, 원작 상태/OAM과 메모리 경계, 원작 APU/GBC 소비 해시, 타이머 오차도 검사한다.
잘못된 팔레트/DMA 쓰기, 오디오 지연/버퍼 부족은 0이다. 최악 타이머 오차 절댓값은 0.105ms 미만이다.

## 전체 경로와 회귀

후보 표시 ROM SHA-256: `877198b1a4316f4719f168d5f4290eec4ed62ea6ecb7240cbb09f69247c6fd6d`.
기준 PR 64 ROM: `776bac0d0e07fabd03aa005b813a067ddd4f9fe19cb749920ce2e3419d9e1499`.
668개 실제 화면과 원작 상태·패턴·맵·픽셀, 음악/효과음/페이드 10,800틱이 일치했다.
원래 순차 요청 검증의 초기 로딩은 987.841–1074.471ms다. 오디오 지연/버퍼 부족과 잘못된 DMA는 0이다.

**전투 중 present 최대 준비는 759.521→806.885ms로 측정됐다.** 초기 로딩 이후 음악 위상이 달라지고
상태 변경 시의 석화 합성 비용은 그대로 남아 있다. 초기 로딩 개선을 모든 프레임의 개선으로
확대하지 않으며, 이 측정 증가를 숨기거나 원작 속도 달성으로 세지 않는다. 자동 대기의 최대
게시 간격은 5프레임, 석화 패턴/맵 전송은 18240/13632바이트로 유지된다.

기존 혼란 회귀도 642화면/10,800틱 일치, 지연/버퍼 부족 0이다. 최대 present 준비는
234.619→229.980ms, 최대 게시 간격 5프레임이다. 회귀 ROM SHA-256:
`972e7e6a474b2571b469a2ff0f9eaa097ca88fdfb6cee64c9481ea3d454e81d8`.
공용 text-vblank 변경에 대한 한글 대사창 회귀는 원작 오디오 7200틱, 실제 캡처 82장과
한글 2350자 검증을 통과했다. 요청 314회, 표시 271페이지, 최대 응답 703.371ms,
p95 502.524ms, 잘못된 VRAM/DMA 쓰기와 오디오 지연/버퍼 부족 0이다.
대사 ROM: `e92088c6e2b3a66da43b54cd411aab4897a2497984d4576d086c6430c3da838c`.

호스트 154검사를 통과했다. 공개 허용 소스 506개만 별도 디렉터리에 복사해 표시/함수 대조/
오차 주입 ROM 세 개와 보고서가 바이트 단위로 재현됐다. 원본/번역 입력과 도구 경로는
비공개 local.json으로 공급했다.

## 남은 순서

약 500ms의 초기 준비 예산은 아직 미달성이다. 이번 음악 틱 고정 조건에서 남은 약 1초 중
오디오 생산자는 약 624–638ms, 전송/팔레트 함수의 비오디오 경과는 약 267–305ms다.
단순히 오디오를 멈추거나 데이터·숫자를 빼서 맞추지 않는다.

다음은 동일 음악 틱의 검증을 유지하면서 초기 그래픽 전송 요청을 묶어 대기를 줄이는 것이다.
현재 맵 초기화 4096바이트, 아군 패턴 4096바이트와 적 자산은 256바이트 단위로 전경에 복귀한다.
상주 자산을 한 번 올리는 원작 수명을 유지하면서 VBlank 큐에서 처리할 수 있는 범위를 비교한다.
ROM 직접 DMA를 검토한다면 원본 주소 정렬·은행 수명·타이머 중단 상한을 별도 증명해야 한다.
현재 구현이 다른 화면을 완전히 보존한 채 전투 자산을 로드한다고 주장하지 않는다. 로딩 중
기존 OBJ를 숨기고 BG를 초기화하는 현재 계약을, 탐색→전투 전환의 표시 수명과 함께 통합해야 한다.

변경 배우/석화 셀만 처리하는 고정 할당, 보스 상주 표시, 창·포격·숫자의 같은 자원 수명 통합은
로드맵의 후속으로 유지한다. 음질/CH4 타격음 충돌과 전체 게임·실기 검증도 완료되지 않았다.

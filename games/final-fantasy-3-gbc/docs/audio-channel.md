# 원작 채널 스크립트·엔벌로프 C 이식

기준일: 2026-11-22. 사용자 요청에 따라 음표·반복 명령과 음량/피치 엔벌로프를 옮겼다. 음색 조정은 [보류 상태](audio-backlog.md)를 유지하며 새 녹음을 만들지 않았다.

## 구현

`src/audio-channel.c/.h`는 원본 ROM bank `$36`의 `$81E6..$872C`를 C로 구현한다. 기존 `FF3AudioState`의 사운드 RAM 192바이트와 논리 APU 24바이트를 사용하고, 읽기 콜백으로 원본 악보·표를 받는다. ROM 데이터나 변환된 악보를 C 소스에 포함하지 않는다.

| 범위 | 옮긴 동작 |
|---|---|
| `$81E6..$820A` | 채널 활성 검사, 음표 길이와 16비트 감쇠 카운터 갱신 |
| `$820B..$8352` | 음표 12종 × 길이 16종, 쉼표, 타이, 옥타브/주파수/노이즈 표, DAC 쓰기 |
| `$8353..$84FE` | 템포 값 설정, 음량, 옥타브, 듀티/엔벌로프, 스윕, 프리셋, 반복 시작/종료/볼타와 점프 |
| `$84FF..$857C` | 채널 종료, 음악/효과음 소유권과 전체 종료 판정 |
| `$857D..$86D4` | key-off, attack/decay/release, 음량 변화와 표 기반 음량 합성 |
| `$86D5..$872C` | 피치 변화 주기, 상대 후방 점프, 주파수 하위 바이트의 포화 처리 |

원작의 8비트 처리 의미를 보존한다. 반복 깊이 `$FF`에서 시작하여 2개의 카운터 슬롯을 쓰고, 반복 횟수 0은 감소 시 255로 돌아가므로 256회 반복한다. 볼타는 반복 횟수의 홀짝을 검사한다. 스크립트는 기본 주소 + 8비트 Y 인덱스를 사용하며, 명령마다 RAM 포인터를 갱신하는 구조로 바꾸지 않는다. `$FF` 종료 후에도 해당 틱의 길이 카운터 감소는 실행된다.

음량 엔벌로프의 기본값 감소와 임시 출력 변조를 구분한다. 변조 결과를 기본값에 덮어쓰지 않는다. 일반 효과음 엔벌로프는 곡 음량을 무시하지만 특수 엔벌로프의 `$05` 문턱 검사는 곡 음량을 읽는 원작 동작을 유지한다. 피치 변화는 하위 바이트에서 0/255로 제한하며 상위 바이트를 바꾸지 않는다.

공개 함수는 채널 0..6, 스크립트 형식 0..4를 검사한다. 정상 원본 데이터가 전제이며 잘못된 포인터를 자동 복구하지 않는다. 종료하지 않는 명령 체인(호출당 1,024명령 초과)과 256바이트 전체가 타이인 lookahead는 0을 반환해 호출자가 실패 처리하도록 한다. 이 방어 한도는 원작 데이터의 새 음악 규칙이 아니다. ROM 읽기 콜백은 현재 원작 뱅크 매핑에 맞는 바이트를 제공해야 한다.

## 원본 대조

`tools/channel-fixtures.mjs`가 사용자가 가진 지원 ROM의 실제 `$81E6`/`$857D` 코드를 기존 `Driver6502`로 실행하여 기준을 만든다. 실제 음악/효과음 진행 중 진입 상태를 복제하고 복제본만 검사하므로 관측이 원래 진행을 변경하지 않는다. 실행된 읽기 주소/값을 사례별 사전으로 저장한다. C가 원본 실행에서 읽지 않았던 주소를 요구하면 실패한다. 명령 fetch와 C가 사용하지 않는 6502 임시 변수는 이식 대상 상태에서 제외한다.

동일한 검사기 `src/audio-channel-test.c`를 Windows 네이티브 C와 GBDK/SM83로 컴파일한다. C 함수가 계산한 RAM 192바이트, 논리 APU 24바이트, 쓰기 순서/값을 원본 결과와 비교한다. 기대 출력 상태를 C 상태에 복사하여 대신 실행하지 않는다. 연속 사례는 이전 C 결과가 다음 원본 입력과 같은지도 검사하고 상태를 초기화하지 않는다.

전체 4,336사례의 범위:

- 모든 음악 65슬롯을 1,200논리 틱, 효과음 97슬롯을 512논리 틱 진행하며 각각 5개 시점의 채널 진입 상태를 채취한다. 모든 틱이나 곡 끝까지의 전수 비교라는 의미는 아니다.
- 음표/쉼표/타이 `$00..$DF`와 제어 명령 `$E0..$FF`, 총 256바이트 종류를 실제 원본 루틴에 입력해 실행한다.
- 2단 반복, 횟수 0/1/2/3/255, 볼타 홀짝, 점프, Y 인덱스 순환, 16비트 타이 길이, 종료/채널 소유권, DAC 문턱을 합성 입력으로 보강한다.
- attack→decay 및 release→무음, 엔벌로프 후방 점프, 변조 카운터, 양/음수 변화와 상하한, key-off와 비활성을 검사한다. 합성 입력은 실제 게임 도달 상태라는 주장이 아니다.
- 367개 사례는 앞선 사례에서 상태를 이어받는다. 여기에는 256회 반복 전체와 엔벌로프 연속 실행이 포함된다.

기존 제어부의 2,360사례에서도 SCRIPT/ENVELOPE 콜백은 실제 C 실행으로 교체했다. 상위 음악 갱신 `$8925`만 명시적 원본 반환 상태 재생으로 남아 있다. 이 검사는 제어부와 새 채널 모듈의 연결을 검증하며, 아직 완성 음악 엔진이 아니다.

## 검증 기록

정상 채널 검사 ROM SHA-256: `4957e3d8d50e784ff3bbaffcb2f2646447e12630fc8fd0d01b80529c2eb56140`.

오류 검출용 ROM SHA-256: `d1290d8448c974c1f3f2b36bc31bc2c03a7b340e990dcf922fe7dfcf101a240f`.

통합 제어부 검사 ROM SHA-256: `666bddab5fa7265bdd6ed8b945aa63d40f1235b8d22b3b1984dfaabc15ec519c`.

기준 데이터 SHA-256: `90dbd99762ae26762a19b93ad9970e1b5be6f7ee4ca3ef612f5676bd41fff2e9` (2,060,396바이트). 원본 ROM과 GBDK 4.5.0 컴파일러의 허용 해시는 기존 `spec/`에서 확인한다. Mesen CE 버전/패치 식별은 [제어부 기록](audio-control.md)과 같다.

Windows MSVC 14.44.35207 검사에서 4,336/4,336 PASS, 의도적으로 첫 기대 RAM 바이트를 틀리면 첫 사례에서 오류 4 / 인덱스 0으로 FAIL한다. GBC 통합 제어부 검사에서는 2,360/2,360 PASS를 확인했다 (`gameboyMemory $C2A9`: `A5 01 00 38 09 00 00`, 관측 프레임 7,201).

GBC 채널 전용 검사도 4,336/4,336 PASS였다. `gameboyMemory $C8AD..$C8B3`은 `A5 01 00 F0 10 00 00`이며 7,201번째 에뮬레이터 프레임에서 완료 상태와 화면을 확인했다. 오류 검출용 ROM은 121번째 프레임에서 `A5 02 04 00 00 00 00`과 FAIL 화면을 보였다. 필드는 ready, 상태, 실패 코드, 사례 번호 u16, 실패 인덱스 u16 순서다. 관측 프레임 수는 게임의 논리 틱이나 엔진 성능 수치가 아니다.

공개 대상 소스만 별도 폴더로 복사하고 원본 ROM/GBDK 경로를 명시하여 재빌드했다. 채널/제어부의 정상·오류 검출용 ROM 4개, 기준 데이터 2개, 보고서 2개가 모두 바이트 단위로 일치했다. 기존 회귀 검사 13개도 통과했다. 검사 이미지, 호스트/GBDK 로그, 사례별 원본 상태와 재현 비교 결과는 로컬 `evidence/channel/` 및 `build/channel/`에 보존한다.

## 재현과 배포 경계

```powershell
node tools/build-channel.mjs --rom "D:/private/Final Fantasy III (Japan).nes" --gbdk "D:/tools/gbdk"
node tools/build-control.mjs --rom "D:/private/Final Fantasy III (Japan).nes" --gbdk "D:/tools/gbdk"
```

`build/channel/ff3-channel-test.gbc`를 GBC 에뮬레이터에서 실행하면 자동 비교 후 PASS/FAIL을 표시한다. `ff3-channel-negative.gbc`는 기대값 한 바이트를 의도적으로 틀렸으므로 FAIL이 정상이다. 화면은 개발용 검사 결과 표시이며 게임 UI가 아니다. 음원 출력은 끈다.

`--fixtures-only`는 컴파일 없이 로컬 기준 파일만 생성한다. 선택적 호스트 검사는 C 컴파일러로 `audio-channel.c`와 `audio-channel-test.c`를 `CHANNEL_HOST` 정의와 함께 컴파일하고, 실행 파일에 `build/channel/fixtures.bin 4336`을 전달한다. MSVC는 개발 중 빠른 대조용이며 GBC 패키지 빌드 의존성이 아니다. 검사 ROM 2 MiB는 기준 데이터 대부분을 담은 크기이며 음악 엔진의 ROM/실행 비용이 아니다.

원본 ROM, VGZ, 생성 ROM/기준 데이터/메모리, 번역 자료, 디스어셈블리는 공개 패키지에 넣지 않는다. VGZ나 디스어셈블리 파일 없이 원본 ROM과 공개 코드에서 검사를 재생성한다. 참고 디스어셈블리 출처는 [everything8215/ff3](https://github.com/everything8215/ff3), 고정 커밋 `1acef8117120ff891003de249b1a74bc8d94d674`이며 판단 기준은 ROM 실행 결과다.

다음은 음악 요청·템포 진행·페이드의 상위 처리 `$8925..`를 C로 옮겨 남은 상태 재생을 제거하는 단계다. 이후 GBC 출력 백엔드/시간 스케줄에 연결하고 BGM+임의 효과음의 연속 재생을 검증한다. 이번 결과는 논리적 동작 대조이며 음색 동일성, 실기, 전체 게임 통합이나 실시간 성능 검증을 뜻하지 않는다.

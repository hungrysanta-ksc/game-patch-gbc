# 등장·포격 준비 비용 분리와 완료 후 복귀

기준은 PR 50 병합 `8abf295c69f4cd33f62f6b6f435104e2c1e43dd7`, 작업 브랜치는
`ff3-opening-costs`다. 원작/번역/생성 ROM과 관측 파일은 로컬에만 보관한다.

## 무엇을 측정하는가

기존 `scene_phase=9`는 창의 C 계산뿐 아니라 오디오 보충과 VBlank 대기를 포함한다.
이를 CPU 계산 시간으로 해석하지 않는다. 같은 고정 MesenCore에서 ROM을 수정하지 않고
`native_busy`, `text_transfer_busy`, `scene_pending`, `scene_phase`, `scene_request`의
실제 변경 시각으로 호출 시간을 중복 없이 분류한다.

우선순위는 오디오 서비스 → 전송 완료 대기 → 게시 완료 대기 → 구성 단계 → 원작 대기
→ 숫자 → 기타 호출자다. 오디오 서비스에는 그 안에서 실행된 IRQ 시간이 포함되고,
오디오 외 전송 대기에는 DMA/IRQ 비용도 포함된다. 따라서 순수 명령별 CPU 프로파일이
아니며, 각 범주의 합이 관측한 호출 시간이다. 숫자 범주의 작은 값도 숫자 연출 전체 길이가
아니다. 숫자 표시 중 실행한 오디오는 오디오 범주에 속한다.

디버거의 요청 주입은 CPU 메모리 쓰기 콜백을 거치지 않는다. 첫 계측의 빈 결과를 성공으로
세지 않고, 첫 후속 경계에서 요청을 읽어 시작을 잡도록 수정했다. 각 요청의 비용 합은
호출 시간의 98% 이상이어야 하며, 누락/서로 다른 중복/불명확한 클록은 검증 실패다.
약 11~29ms의 시작·폴링 여백은 계측 범위 밖에 남는다.

기준 ROM의 첫 네 경로만 별도 계측했다. 이 실행은 5,500프레임에서 의도적으로 끝내므로
음악 전체 합격으로 세지 않는다. 네 경로 시간은 PR 50의 정식 8요청 실행과 정확히 같다.
후보의 최종 합격은 여전히 8요청·21,600 오디오 틱 전체 검사로 판정한다.

## 확인된 원인과 변경

기준 네 경로에서 오디오 서비스가 약 68%, 화면 구성·은행 읽기가 약 16%, 오디오를
제외한 전송/게시 대기가 약 11%였다. 창 단계에서만 세면 오디오 비중이 더 크다.
전송 IRQ가 완료 플래그를 내린 뒤에도 생산자가 세 번째 선행 틱을 계속 채우면,
화면 호출자는 완료된 작업에서 복귀하지 못한다.

- 창의 120칸은 세 포인터로 순서대로 처리한다. 칸마다 행×20·행×32를 재계산하지 않는다.
  투명 칸과 화면 밖 12열, 모든 원작 도트/문자/수량은 그대로 보존한다. 창 구성 전·중간의
  오디오 보충 경계도 유지한다.
- 오디오의 기본 205타이머 틱 선행 목표는 유지한다. 화면 요청 중 전송 또는 게시가
  **이미 완료**됐고, 미처리 명령이 없고, 마지막 완료 패킷이 현재보다 136틱 넘게 앞서
  있을 때만 생산자를 호출자에게 돌려준다. 패킷 중간에서 끊거나 원작 음악 틱을 생략하지 않는다.
- 전송을 기다리는 동안, 긴 C 구성에 들어가기 전, 원작 표시 대기, 숫자 전용 스케줄러에는
  그 조기 복귀 조건을 적용하지 않는다. DMA 크기·게시 시점·타이머 IRQ는 바꾸지 않는다.

변경은 `FF3_OPENING_VIDEO`에 한정한다. 전체 전투 편성이나 정상 게임 진행 완료가 아니다.

## 재검증

```text
npm test
npm run build:battle-opening-video
npm run verify:battle-opening-video
node tools/battle-opening-costs.mjs <PR50-baseline-folder>
```

기준 폴더는 PR 50의 `report.json`, `load.json`과 별도 계측 `profile.json`,
`profile.json.lua.log`를 포함한다. 비교 도구는 기준 ROM 해시, 같은 코어, 변하지 않은
251개 그림·원작 요청·대기·한글·오디오 계획, 모든 경로의 단축, 원작 대기/숫자/오디오
합격을 요구한다. 전체 원작 속도는 별도 관문으로 남긴다.

## 최종 결과

동일한 8요청은 PR 50의 15.805~21.565초에서 15.068~20.493초로 줄었다. 각 경로 단축률은
3.0~6.2%다. 창 포인터 계산만 바꾼 중간 후보는 15.437~20.845초였다.
중간 후보의 8경로·화면·오디오 검사도 완료한 뒤 최종 후보와 구분해 보존했다.

| 첫 네 경로 합계 | PR 50 | 최종 후보 |
|---|---:|---:|
| 오디오 서비스 | 50.356초 | 48.554초 |
| 화면 구성·은행 읽기 | 11.513초 | 9.974초 |
| 전송 대기(오디오 제외) | 5.831초 | 5.984초 |
| 게시 대기(오디오 제외) | 2.044초 | 1.799초 |
| 원작 대기(오디오 제외) | 1.548초 | 1.598초 |
| 숫자 실행(오디오 제외) | 0.482초 | 0.542초 |
| 기타 호출자 | 2.156초 | 2.179초 |

오디오 서비스 합계 감소는 짧아진 **화면 호출 구간 안의 점유 시간**이다. 오디오 VM 자체의
처리량이 그만큼 빨라졌다는 뜻이 아니며, 6분 전체 음악/효과음 틱과 출력은 생략하지 않았다.
전송 대기는 오디오와 서로 겹치지 않는 분류여서 분류 간 이동도 함께 해석해야 한다.

- 모든 원작 그림 251개·요청·대기·한글·오디오 계획 동일. 실제 캡처 1784장/41,103,360픽셀 일치.
- 원작 상태 경계 348건, 단계 1520건, 원작 최소 대기 전부 통과.
- 숫자 8회 × 32프레임, 공급 지연 0, 최대 표시 오차 3.207ms.
- 오디오 21600틱·효과음 12요청·APU 144444쓰기 대조. 큐 고갈·출력 지연·잘못된 VRAM/DMA·활성 버퍼 쓰기 0.
- 선행 준비 1496회 중 마감 초과 1158회, 최대 252.197ms. 전체 원작 속도 관문은 아직 미통과다.
- 호스트 회귀 126개 + 계측 검증 1개 통과. 공개 422파일 소스만으로 ROM/보고서 재현, 그 복사본에서 전체 런타임 검증.
- ROM SHA-256: `6372bb8522117bcd2ef8a0bc8a308a9fa7f0775e5f19fe6920a198031990206f`. MesenCore 고정 해시와 메모리/은행/IRQ 계약 유지.

다음은 오디오 서비스 내부의 VM·출력 변환·스냅샷을 계측해 남은 화면 구성 비용과 비교한다.
음색 변경은 후순위이고, R2 0/8·제품 관문 0/3은 유지한다.

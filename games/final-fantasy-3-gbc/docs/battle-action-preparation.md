# 행동 객체의 중복 준비 제거

기준은 PR 77 병합 `489d29add77bc91919bf7ec998309a761b988f71`이다.
원작 데이터/프레임/숫자/오디오를 줄이지 않고 무기 종류 1의 준비 경로를 바꾼다.
실제 연결 범위와 미지원 경계는 [칼질 연결](battle-native-strike.md)을 유지한다.

## 원작과의 구조 비교

원작 `33/A3DD..A3E8`은 공격자만 `32/90EA`로 그린다. 네 명 전체를 그리는
`32/90D8`와 별도 경로다. `33/A379..A3DA`는 손별 자원을 유지하고, 한 번의
칼질을 8장으로 진행한다. 앞의 4장은 같은 뒤로 든 자세이며 뒤의 4장은 각각
다른 슬래시 마스크다. 매 장 `A3C8/F8B0` 대기와 프레임 증가를 수행한다.

PR 77의 GBC 경로는 한 명을 그리기 위해 네 명의 원작 OAM을 만들고, 네 명의
좌표를 변환한 뒤 몸체 프레임에서 그 결과를 다시 지웠다. 고정된 나머지 객체를
다시 모으고 줄당 한도를 매 장 재계산한 것도 불필요했다. 하드웨어 차이가
요구하는 작업이 아니므로 제거한다.

- `ff3_party_actor_oam`: 같은 원작 테이블로 지정한 한 명의 6개 기록만 생성한다.
  기존 전체 생성기는 다른 소비자를 위해 유지한다.
- `ff3_action_oam_begin`: 행동 시작 시 변하지 않는 객체와 144줄 점유량을 한 번
  계산한다. `finish`는 변화한 객체만 검사하고 원작 우선순서로 합친다.
- 몸체는 사용할 좌표만 한 번 변환한다. 전진/복귀는 기존 화면에 해당 인물의
  6개 슬롯만 바꾼다. 대상 기준점도 행동 시작 때 한 번 읽는다.
- 동일한 자세·위치·손·무기 프레임·슬래시 상태는 현재의 불변 OAM 페이지를 다시
  게시한다. 다음 VBlank DMA와 원작 프레임 증가는 유지한다. 최대 반복의
  83개 게시 중 59개를 새로 준비하고 24개는 이미 만든 동일 화면을 재사용한다.
  컴파일 시 만든 프레임 영화나 화면 생략이 아니다.

GBC의 40개 OBJ/줄당 10개 한도, 원작 OAM 우선순위, 7:8 적의 실제 위치 보정은
여전히 검사한다. 초과하거나 범위를 벗어나면 화면을 게시하기 전에 실패한다.
현재 화면이 사용하는 OAM을 수정하지 않으며 변경 프레임은 반대편 버퍼에 쓴다.

## 공통 처리의 수명과 다른 이펙트

`begin`과 `finish` 사이에는 한 행동 소유자만 실행한다. 고정 객체 복사본은 최대
32개이며, 추가 기록과 합쳐 40개를 넘으면 실패한다. 기준 점유량과 작업 점유량은
기존 행동 전용 `$D740/$D7D0` 공간을 사용한다. 원작 상태/패턴은 캐시에 복제하지
않고 실제 원작 호출자의 상태를 계속 사용한다.

| 경계 | 적용 규칙 |
| --- | --- |
| 다음 손의 준비/정리 | 동일 화면 재사용을 무효화하고 손별 자원/팔레트 수명을 유지 |
| 다음 행동·숫자·상태/사망 확정 | 최신 기본 OAM을 잡은 뒤 새 소유자가 다시 `begin` |
| 이동·점멸·피격으로 다른 대상도 변화 | 변화하는 모든 슬롯을 고정 집합에서 제외하고 매 장 검사 |
| 패턴·팔레트·대상·후면 전환 | 이전 그림 재사용 금지; 해당 소유자가 자원과 기준점을 갱신 |
| 전체 대상/화면 마법 | 모든 동적 객체와 공유 배경 자원의 수명을 먼저 정의; 한 명 전용 캐시를 그대로 적용하지 않음 |

피해 숫자 소유자는 이미 최초 글리프/고정 점유량을 준비하고 후속 장에서는 숫자
그룹 Y만 갱신한다. 이 경로를 새 공통 함수로 억지로 바꾸지 않는다. 밀집 숫자의
최초 BG 전환 비용은 별개의 미해결 사항이다. 마법·기타 무기·사망 본체는 아직
연결되지 않았으므로 해당 실행 속도가 검증됐다고 주장하지 않는다. 앞으로 이
공통 처리로 연결하되 고정/동적 객체, 자원 교체, 원작 대기 경계를 먼저 선언한다.

정적 WRAM 끝은 `$CEF1`이며 bank 56의 공통 코드는 621바이트다. 이전 문서의
`$CE1D`는 초기화 영역을 제외한 값이었다. PR 77의 실제 `s__HEAP`는 `$CE48`이므로
이번 정적 WRAM 증가는 169바이트다. 빌드에서 `$D000` 경계를 검사한다.

## 측정과 검증 방법

동일한 편성/장비/양손 명중 카운터 `[99,99]`(각각 4회로 제한), 오디오 일정을 사용한다.
99는 직업 레벨이 아니라 명중 횟수 상한 진단값이다. 캡처용 게이트 검증과 게이트
없는 자동 속도 검증을 분리한다. 속도 검증도 83장 게시와 원작 효과음 10개,
7,200 오디오 소비 틱의 출력 해시 및 VRAM/OAM 접근을 확인한다.

읽기 전용 Lua 훅으로 행동 활성 구간의 에뮬레이션 시간을 배타적으로 나눈다.
IRQ → 오디오 생산/보충 → 전송 플래그 → 게시 대기 → 나머지 준비/호출자 순으로
분류한다. 준비에는 해당 플래그로 감싸지 않은 자원 처리도 포함되므로 순수 OAM
CPU 시간이라고 부르지 않는다. 오디오 범주는 서비스 내부 대기도 포함한다.
전체 합이 관측 행동 시간의 98% 이상인지 검사하며 로그 누락을 통과시키지 않는다.
게시 간격은 foreground의 완료 확인 시각이지 실제 LCD 프레임 간격은 아니다.

```powershell
npm run build:battle-effects
node tools/verify-battle-select.mjs --action-oam
node tools/verify-battle-select.mjs --action-oam --negative
npm run verify:battle-strike
npm run verify:battle-strike-positions
npm run verify:battle-strike-numbers
npm run verify:battle-strike-auto
npm run verify:battle-effects
npm test
```

기준 ROM/NOI/보고서/변환표가 보존된 비공개 디렉터리는
`verify-battle-strike.mjs --auto --baseline --build-dir <absolute-directory>`로 같은
계측기를 실행한다. 병렬 캡처 시 검증기를 한 번 빌드한 후 `--skip-build`를 사용해
실행 중인 Windows DLL을 덮어쓰지 않는다. 원작 파일·생성 ROM·캡처·로그는 공개하지 않는다.

## 측정 결과와 남은 성능 경계

최종 효과 ROM SHA-256:
`24b1ceefcf97b8dd3fafd09b61906469734b602a34a288e05187d444d4a284eb`.

| 동일한 양손 최대 반복 | PR 77 | 변경 후 |
| --- | ---: | ---: |
| 요청부터 정리까지 | 5,392.833ms | 2,311.208ms |
| 최초부터 최종 게시 완료까지 | 5,251.901ms | 2,204.132ms |
| 최대 게시 완료 간격 | 166.992ms | 120.361ms |
| 준비/호출자 등 | 2,655.552ms | 673.582ms |
| 오디오 생산/보충 | 2,014.216ms | 1,219.177ms |
| IRQ | 503.303ms | 216.983ms |
| 게시 대기 | 210.091ms | 192.580ms |

전체 지연 **57.14% 감소**. 게시 83장·원작 사운드 요청 10개는 동일하다.
오디오 엔진 자체는 변경하지 않았다. 행동 소요 시간이 줄면서 그 구간에 들어오는
IRQ/보충량도 바뀌므로 오디오 엔진이 위 표의 비율만큼 빨라졌다는 뜻이 아니다.
전송 플래그에 별도 귀속된 시간은 없고, 플래그 밖 자원 처리는 준비 항목에 포함된다.

- 컴파일된 960개 원작 상태에서 단일 캐릭터 생성 4명분을 전체 생성의 원작 정답과
  대조했다. 별도 예산 경계·캐시 갱신·범위 실패 검사도 같은 GBC에서 통과했다.
  오류 주입 ROM은 첫 원작 OAM 불일치를 검출했다.
- 양손 368장, 위치 544장, 칼질→숫자 116장, 숫자 회귀 198장의 원작 OAM/실제 OAM/
  전체 픽셀이 모두 일치했다. 각각 7,200틱 소비 오디오와 원작 출력 해시가 일치하고,
  오디오 부족/지연·잘못된 VRAM 읽기/쓰기·OAM DMA는 모두 0이었다.
- 호스트 173검사 통과. 기본 `--windows` ROM은 기존
  `43e7794f03574db82e6759480b1a0fa355364e9e40f34510c529e4345f6cfa1c`와 바이트 동일하다.
- 원작 리소스 추출 결과/오디오 변환표는 PR 77과 동일하다. 공개 소스 584파일로
  효과 ROM·단위/오류 주입 ROM·보고서·추출 결과 6산출물을 별도 디렉터리에서 바이트 단위로 재현했다.

화면 전체 재구성은 제거했지만 원작 속도 도달을 선언하지 않는다. 남은 오디오
서비스 시간은 요청 인계/보충/출력 변환으로 더 나눠야 한다. 요청을 늦추거나
효과음을 생략하는 최적화는 허용하지 않는다. 새 이펙트는 같은 자원 수명 규칙과
전체 픽셀/숫자/소비 오디오 검증을 사용하며, 정상 전투 입력/계산 연결은 별도 관문이다.

# 양파검사 직업 숙련도와 검 공격 길이

2026-11-25. 기준은 PR 43 병합 `8e775b76af83a8b2a078f934eb7b69d508c43257`.
사용자 정정에 따라 **캐릭터 레벨을 쌍 안에서 고정하고 직업 숙련도 1/99를 비교**했다.
원본 NES 실행에서 칼질·타격 이펙트·효과음 요청 반복 수와 길이 차이를 확인했다.
GBC 연출 연결 완료나 자연 성장 플레이 검증은 아니다.

## 고정 조건과 실측

양파검사인 4번째 아군, 오른손 검 `0x1E`, 빈 왼손, 기본 능력치 5와 같은 적/진열/상태를 유지했다.
직업 숙련도만 변경한 뒤 원작 장비 능력치 루틴으로 파생 값을 다시 계산했다.
캐릭터 레벨은 1·33·99의 세 조건으로 나누었지만 **각 비교 쌍 안에서는 같다**.
이 능력치는 자연 성장한 레벨 33/99를 재현하지 않는다. 캐릭터/직업 레벨 모두 화면의 1/99는
내부 0/98이다. `3C/8ACC..8ADB`의 읽기와 표시 전 +1로 확인했다.

각 조건에서 시작 난수 카운터 256위치를 원작 물리 효과로 검사하고 연출 차이가 가장 큰 첫 위치를
대표로 골랐다. 차이가 난 위치는 각각 0/256, 6/256, 52/256이다. 이는 해당 고정 상태의
카운터 전수 검사이며 게임 전체의 발생 확률이 아니다. 양쪽은 같은 난수 표와 같은 시작 카운터를 쓴다.

| 고정 캐릭터 레벨 | 직업 숙련도 | 시작 카운터 | 실제 명중 수 | 칼질/타격 효과 주기/효과음 요청 | 무기 연출 프레임 |
|---|---:|---:|---:|---:|---:|
| 1 | 1 | 0 | 1 | 1 | 10 |
| 1 | 99 | 0 | 1 | 1 | 10 |
| 33 | 1 | 174 | 2 | 2 | 18 |
| 33 | 99 | 174 | 3 | 3 | 26 |
| 99 | 1 | 73 | 3 | 3 | 26 |
| 99 | 99 | 73 | 6 | 4 | 34 |

Mesen NES 실제 실행에서 `33/A0C0` 시작부터 `2F/B25B` 복귀까지 측정했다.
FPS는 60.0988118623484, 18/26프레임은 약 0.300/0.433초다. 접근·메시지 등 전체 행동 길이와
혼동하지 않는다. `32/991F`는 주기당 4번의 프레임 갱신이며 이를 독립 타격 효과 4개로 세지 않는다.
`$7F49=$B6` 요청은 칼질마다 1회이고 APU 소비 확인 `$40`·정지 요청은 별도다.
원본 WAV 6개는 모두 비무음·클리핑 0, PNG 338장과 실행 로그를 함께 보존했다.
원본 BGM도 함께 녹음되므로 WAV 진폭을 타격 수로 환산하지 않는다.

## 원작 소비 경로와 이식 계약

주소는 기존 `ff3j.asm`의 은행 표기다. 실제 MMC3 관측에서는 8 KiB 은행쌍의 하위 은행
`$30/$32`를 확인하므로 문서의 `$31/$33` 표기와 구분한다.

| 근거 | 확인한 역할 |
|---|---|
| `3C/8ACE,8AD4..8ADB` (39853행 부근) | 숙련도 `$6110+slot*64`, 캐릭터 레벨 `$6101+slot*64`, 표시 +1 |
| `31/ABCD..ABF2,AC25..AC53` (9857~9920행) | 캐릭터 레벨/민첩은 공격 시도 수, 숙련도/민첩은 검 명중률에 기여; 원작 정수 연산 유지 |
| `33/A077,A094` (16908/16928행) | 무기 종류별 표시 상한; 검은 5 이상을 4로 제한 |
| `33/A365..A3D8` (17281행 부근) | 검 반복 카운터, 8프레임 주기, 주기마다 `$B6` 효과음 |
| `32/97B2,991F` (15676/15884행) | 명중 없으면 타격 효과 생략; 첫 크리티컬 섬광 2프레임; 검 타격 프레임 갱신 |
| `33/A2F2..A2FA` | 다른 손에 무기가 있으면 빈 손의 맨손 연출을 추가하지 않음 |

직업 숙련도를 연출 길이에 직접 곱하지 않는다. **장비/숙련도 계산 → 명중 판정 → 손별 실제 명중 수
→ 무기 종류별 연출 반복**이라는 원작 인계를 유지한다. 피해·명중 메시지용 값과 표시 상한 적용 후
카운터를 분리해야 한다. 6명중을 4회 연출했다고 피해 계산까지 4명중으로 줄이면 안 된다.
양손은 별도 반복이고, 빗나가도 검을 한 번 휘두르지만 타격 효과는 없다. 혼란도 별도 분기다.
이 검의 상한/길이를 활·맨손·다른 직업기 전체에 일반화하지 않는다.

다음 GBC 연결의 합격 조건에 같은 입력의 손별 반복·이펙트 프레임·효과음 시점·전체 수명 일치를
추가한다. V6의 원본 아군 도트, 적 점멸/아군 피격, 숫자·창 복원과 같은 실행기에 연결하고
긴 반복 중에도 음악/효과음 생산과 VBlank 예산을 검증한다. R2 통합 0/8, 제품 관문 0/3은 그대로다.

## 재현과 증거 경계

`battle-weapon-duration.mjs`는 원본 `2F/B24F`와 무기/그래픽 본문을 실행한다.
하드웨어 대기는 기존 참조 실행기의 대기 수로 관측한다. 호스트 테스트는 검 명중 0~상한 초과,
크리티컬, 양손, 빈 손, 혼란의 25조건을 검사한다. 실제 PPU/APU 측정은 별도 캡처와 대조했다.

실제 캡처는 기존 원본 진단 전투에서 버튼 입력으로 공격을 선택하고 물리 공격 진입에서 멈췄다.
보존 상태의 정확한 PC는 `31/A2BA`, 하위 매퍼 은행 `$30`, 공격자 포인터 `$6E=$7635`다.
원본 코드는 수정하지 않았다. 그 상태에서 승인된 RAM 개입으로 레벨/숙련도·파생 능력치·난수 시작값을
바꿨다. 진단 이름·능력치가 포함되므로 정상 게임의 획득·성장·선택 경로를 증명하지 않는다.

- ROM SHA256: `262a98737975df25fff80ad91090c3da039d2828035c6253140d2c5f3b176ea2`
- MesenCore SHA256: `1ba99d2c848e007c60cbd7fceca058440758eb44837a93a6724d29d72723c994`
- 비공개 MST SHA256: `55faa0141c1ad2218c458e957bae27c514d94feaffde86003a2fde7fad0a61c9`
- IRAM SHA256: `028ae484f5b9d4f71ea06ea54724b6be4793ccd030dfeb39af207d1e31eb8c86`
- PRG RAM SHA256: `0192c3e4d5a2ec32498fe976eef1e02684859f35b2e01744fbc7dd93bdfd06ac`

로컬 재현 (`local.json`의 원본 ROM·MesenCore와 .NET 8 사용):

```powershell
node tools/prepare-battle-weapon-duration.mjs --state .local/duration-before-fight.mst --dump .local/duration-before-fight --out evidence/battle-weapon-duration
dotnet build tools/ObserveBattleWeapon/DurationCapture.csproj -c Release --configfile tools/Capture/NuGet.Config
foreach($charLevel in @(1,33,99)) { foreach($jobLevel in @(1,99)) {
  dotnet tools/ObserveBattleWeapon/bin/Release/net8.0/DurationCapture.dll "evidence/battle-weapon-duration/L$charLevel-J$jobLevel/config.json"
} }
node tools/verify-battle-weapon-duration.mjs --out evidence/battle-weapon-duration
```

관측 도구는 위 비공개 상태/덤프 해시가 맞지 않으면 중단한다. 이를 소스 배포에 포함하거나
제품 빌더 의존성으로 만들지 않는다. 새 상태는 호출자/파생 값/은행을 다시 검증한 별도 실험이다.
재실행은 새 출력 디렉터리를 사용한다. 캡처는 PNG·WAV·원시 로그와 조건을 저장하며,
검증기는 원작 참조의 각 칼질/타격/SFX 프레임까지 대조하고 `verified.json` 및 `index.html`을 만든다.
HTML은 동시 화면 프레임 탐색과 개별 원본 WAV 청취용이며 오디오 자동 동기 재생은 하지 않는다.
ROM·덤프·세이브·PNG·WAV·조건/결과 데이터는 Git에 올리지 않는다.

전체 호스트 회귀 **109/109**, 새 원작 본문 테스트 **2시험/25조건**을 통과했다.
효과음 요청 한 개를 변조한 관측 로그도 검증기가 `sound count/timing mismatch`로 거부했다.
공개 허용 소스 **388파일**만 별도 디렉터리에 복사해 빌드·새 테스트·6개 실제 캡처를 재실행했다.
양쪽의 원시 이벤트 로그, 명중 수, 반복 수와 시점, 캡처 길이가 같았다.
PNG는 각 캡처의 첫 장을 제외한 **332장**이 바이트까지 일치했다. 첫 장은 세이브 불러오기 직후
화면 위쪽이 서로 다른 색/미완성 상태였고, 그 뒤 프레임 및 무기 연출 구간은 일치했다.
WAV는 5개가 바이트 일치했지만 캐릭터 33/숙련도 1의 한 파일은 샘플이 달랐다.
그 파일도 길이·비무음·클리핑 0은 같고 원시 SFX 요청 로그도 같다. 파형 차이는 녹음 전반에 걸쳐
있어 단순한 시작 지연으로 단정하지 않는다. **전체 미디어의 바이트 재현성은 확보하지 못했다.**
원본 효과음 요청 횟수/시점 확인과 캡처 파형의 결정성을 구분하며, 이 비교를 음질 승인이나
GBC 오디오 연속성 검증으로 사용하지 않는다. 원시 실패 로그와 두 캡처는 모두 로컬에 보존한다.

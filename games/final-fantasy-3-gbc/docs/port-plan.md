# 원작 기반 한글 GBC 이식 및 배포 빌더 계획

기준일: 2026-11-22. 이번 사용자 결정이 이전 샘플 확장 계획보다 우선한다.

이 문서는 사운드 착수 전 정한 전체 계획을 보존한다. 이후 `games/final-fantasy-3-gbc`에서 진행한 현재 구현·검증은 [프로젝트 안내](../README.md), [현재 사운드 엔진 검증](audio-native.md), [원작 필드 이벤트 통합 검증](field-audio.md)을 기준으로 확인한다. 아래의 기존 시제품 자산/감사 기록은 별도 로컬 시제품의 이력이며 이 공개 폴더에 모두 포함되어 있다는 뜻이 아니다.

## 1. 목표와 방향 수정

목표는 NES판 Final Fantasy III를 한국어로 즐길 수 있는 GBC 이식이다. 게임 규칙과 이벤트·메뉴의 기능·정보·상호작용은 원작을 기준으로 한다. GBC 화면과 음원에 맞는 표현 변경은 필요하지만 새 게임 규칙이나 새 대사를 만들지 않는다.

최종 배포물은 **원본 NES ROM을 사용자가 입력하면 분석 → 추출 → 변환 → 컴파일 → 링크 → 검증을 수행해 GBC ROM을 생성하는 오프라인 패키지**다. 지금부터의 개발도 이 생산 경로를 사용한다. 마지막에 별도 배포 도구를 덧붙이는 방식으로 진행하지 않는다.

이번에 추가했던 고정 피해 3, 적당 피해 2의 반격, 순차 행동, 시험용 전멸 회복, 임의 보상/경험치 창, 작성한 샘플 대사와 고정 파티 이름은 제품 구현으로 채택하지 않는다. 기존 ROM과 코드는 그래픽/메모리/입력 실험 기록으로 보존하고 확장을 중단한다. 포션 등 임의 게임플레이 샘플을 다음 작업으로 삼지 않는다.

## 2. 현재 자산의 재사용 판단

| 현재 결과 | 판단 | 제품에 가져갈 조건 |
|---|---|---|
| 입력 ROM 식별, 원본 불변, GBDK 빌드와 해시 검사 | 재사용 | 배포 빌더의 입력 계약으로 통합 |
| 22개 테이블 원시 추출, 그래픽 포맷 변환 | 재사용 | 원시 바이트 추출과 필드 의미 해석을 구분; 각 소비 루틴과 연결 |
| 223개 몬스터 이미지, 22개 직업 기본 자세 | 재사용 가능한 분석 결과 | 남은 특수 보스/팔레트 연결과 전체 자세·연출은 추가 분석 |
| 아군 원본 16×24, 일반 적 28×28, 배경 11px | 승인된 표현 기준 | 모든 적/행동/마법/상태 표시가 들어가는지 전체 자산에서 검증 |
| 던전 160×128 시야, 원본 지형/주인공, 스크롤 | 렌더러의 기반 | 이동·지형·차량·이벤트 로직은 원작 의미로 다시 연결 |
| 해리포터 7×7 폰트와 글자 렌더러 | 재사용 후보 | 원작 문자열·이름·치환 코드·창 명세에 맞춰 연결; 전체 문맥 검증 |
| 작성한 3줄 대사, START 경험치/상태 창, 임의 전투 상태기계 | 제품 채택 제외 | 동적 글자/숫자 렌더링 검증만 인정 |
| 기존 테스트와 에뮬레이터 캡처 | 해당 실험의 증거로 보존 | 샘플 규칙의 테스트 통과를 원작 동등성으로 계산하지 않음 |

현 프로젝트는 표현 가능성을 확인한 시제품이다. 전체 게임의 이식률은 산출하지 않는다. 장비·아이템·마법 테이블이 추출되어 있다는 사실은 해당 시스템이 이식되었다는 뜻이 아니다.

## 3. 확인한 원작 분석 자료

주 자료는 [everything8215/ff3](https://github.com/everything8215/ff3), 고정 커밋 `1acef8117120ff891003de249b1a74bc8d94d674`다.

| 파일 | 사용할 정보 |
|---|---|
| `ff3j.asm` | 주소/명령 바이트/주석이 있는 디스어셈블리. 전투 계산, 화면, 메뉴, 이벤트, 사운드 등 |
| `rom-map.txt` | 데이터·코드 영역, 포인터 표, 레코드 수와 배치 |
| `field-ram.txt`, `battle-ram.txt` | 필드/전투 상태, 저장 영역, 능력치·장비·마법·직업 경험치 구조 |
| `ff3j-event.txt` | NPC 조건과 이벤트 명령의 분석. 설명의 영문 대사는 번역 원문으로 사용하지 않음 |
| `ff3j-text.txt` | 일본어 문자열 목록. 실제 ROM의 제어 코드와 참조 위치를 보존해 다시 추출 |

보조 자료인 [FF6Tools](https://github.com/everything8215/ff6tools)는 NES FF3 일본판을 지원한다. 현재 확보한 `ff3j-nes.json`의 정의는 맵·NPC·텍스트·월드맵 중심이다. 다른 게임에 있는 편집 기능이 FF3에도 모두 있다고 가정하지 않는다. 게임 실행 엔진이나 완성된 GBC 이식 소스가 아니다.

이번 감사에서 `ff3j.asm` 56,017줄의 명시적 바이트를 원본 ROM과 비교했다. 명령어 형식으로 분류된 45,231개 행은 모두 일치했다. 데이터 행에는 주소/바이트 불일치 10곳이 있다. 예: `4C/955F`는 ROM 범위를 벗어난 은행 표기이고, `3A/8890`은 인접 데이터와 주소가 겹친다. 원인 확인 전 자동 보정하거나 원본 ROM을 수정하지 않는다. 감사는 표기된 바이트만 다루며 전체 데이터·주석 의미·실행 완전성을 보증하지 않는다.

당시 별도 로컬 시제품의 `tools/audit-source.mjs`와 `build/analysis/source-audit.json`으로 감사했다. 이 전체 감사 도구·원본 분석 자료는 이번 공개 오디오 폴더의 의존성이 아니다. 현재 오디오 빌드는 입력 ROM에서 직접 추출하며, 원작 드라이버와의 실행 대조는 공개 `tools/capture-audio.mjs`로 수행한다.

## 4. 가져오는 방식

### 원작 의미를 유지하는 부분

- 캐릭터·장비·인벤토리·마법·직업·이벤트·세이브 상태의 필드와 의미를 먼저 명세한다. 예를 들어 원작 캐릭터 경험치는 3바이트다. 샘플의 16비트 경험치·임의 포화 규칙은 그대로 쓸 수 없다.
- 원작 계산 루틴을 작은 함수 단위로 C/SM83에 옮기고 원본 주소, 읽고 쓰는 필드, 호출 관계를 기록한다. 캐리, 정수 폭, 반올림/버림, 오버플로, RNG 소비 순서를 보존한다. 코드 모양의 일치보다 결과와 부작용의 일치를 검증한다.
- 원작 이벤트·NPC·전투 행동·음악 스크립트는 가능한 한 원래 명령 의미와 데이터 순서를 유지하는 인터프리터를 사용한다. 특정 좌표/이벤트를 C 코드에 하드코딩해 재현하지 않는다.
- 포인터/은행을 재배치하면 원본 주소→생성 주소 대응표와 모든 참조 갱신을 빌드가 관리한다. 알 수 없는 명령을 건너뛰거나 임의 기본값으로 대체하지 않는다.
- 원작에 존재하는 이름 입력과 사용자 이름의 저장/치환을 이식한다. 샘플의 고정 이름을 원작 기본 이름으로 채택하지 않는다.

### GBC용으로 작성하는 부분

- PPU/OAM/패턴·팔레트 업로드 대신 GBC 타일/속성/VRAM/OAM을 사용하는 렌더러.
- MMC3 주소 접근 대신 ROM 데이터 핸들과 GBC 은행 전환. 인터럽트 도중 데이터 은행 변경/복원 규약 포함.
- NES APU 출력을 GBC 음원으로 변환하는 출력 계층.
- 조작을 원작 메뉴 상태에 전달하는 입력 계층, 한글 글자·문자열 레이아웃, 배터리 RAM 저장 계층.

권장 구조는 `source/`(해석과 주소 대응), `core/`(원작 규칙), `platform/gbc/`(표시·음원·입력·저장), `localization/ko/`, `tools/`(추출/변환/빌드), `tests/reference/`(원작 비교)다. 현재 파일을 즉시 옮기지는 않는다. 제품 빌드 경로를 추가할 때 샘플 빌드와 분리한다.

완성 패키지는 원작 루틴에 대응하는 이식 구현을 컴파일하고 입력 ROM에서 추출한 데이터를 함께 링크한다. 6502 기계어 전체를 자동으로 SM83 기계어로 번역하는 범용 컴파일러가 이미 있다는 뜻의 “리컴파일”은 아니다. 자동 변환이 유리한 데이터·스크립트는 자동화하고, 하드웨어 의존 코드는 검증된 이식 구현으로 교체한다. 전체 NES 에뮬레이터를 GBC에서 실행하는 방식은 기본 경로로 삼지 않는다.

## 5. 다음 구현: 원작 사운드 검증

단순 비프음이나 새로 입력한 악보 대신 원본 ROM의 음악/효과음 데이터로 시작한다. 현재 소리는 아직 재생·청취 검증하지 않았으며 아래는 정적 분석에 근거한 작업 범위다.

확인한 진입점:

- `36/8003`: 사운드 갱신, `36/820B`: 명령 해석.
- `36/822F`: E0~FF 명령 분기표. 템포·음량·옥타브·엔벌로프·스윕·반복·분기·종료 포함.
- `36/8925`: 음악, `36/8B9D`: 효과음 갱신.
- `36/8C29`: 효과음에 의한 음악 채널 사용 조정. 이 우선순위와 종료 후 복원을 가져온다.
- 00~40의 곡 ID 슬롯 65개를 헤더 수준에서 확인했다. 모든 곡의 재생/루프가 검증된 것은 아니다.
- 07, 20, 28, 2A(16진수) 곡 헤더에는 다섯 번째 DMC 경로가 살아 있다. `36/8310`은 `$4011` 직접 DAC 값으로 짧은 팝 소리를 만들고 `36/81AC` 쪽에서 0으로 되돌린다. 일반적인 DPCM 샘플 재생으로 단정하거나 이 채널을 조용히 삭제하면 안 된다.

GBC 출력 후보는 NES pulse 1/2 → GBC CH1/CH2, triangle → CH3 삼각 파형, noise → CH4다. GBC의 4채널·파형·주파수·엔벌로프 특성이 NES와 다르므로 그대로 레지스터를 복사하지 않는다. 특히 두 pulse의 스윕, triangle 음량, noise 주기, DMC 타격음과 기존 음악의 동시 재생은 측정해서 변환 규칙을 정한다. [Pan Docs Audio](https://gbdev.io/pandocs/Audio.html)

검증 순서:

1. 전 곡/효과음의 포인터, 명령, 점프·반복, 채널 사용을 조사하고 원본 바이트와 연결한 목록을 만든다. 명령 길이를 모르면 해석을 중단하고 보고한다.
2. 원작 사운드 명령의 템포·음표·엔벌로프·우선순위를 재현하는 플레이어를 만들고, 원작과 같은 논리 틱의 이벤트 로그를 비교한다. 음악 시간은 화면 프레임률 차이와 분리한다.
3. 던전/전투/승리 곡과 커서/공격/마법 효과음, DMC 사용 곡을 추출 데이터 그대로 GBC에서 재생한다. 실제 곡 ID와 호출 장면의 연결은 원작에서 확인해 고른다.
4. 원작과 GBC의 오디오를 같은 구간으로 녹음해 음정·템포·루프·BGM+효과음 복원·팝/끊김을 비교한다. 전투/스크롤/한글 렌더링 부하를 동시에 걸어 CPU·은행 전환·인터럽트 영향을 측정한다.
5. 결과를 원작 유지 가능 / 음원 특성상 근사 / 해결되지 않음으로 기록한다. DMC 근사를 포함한 들리는 변경은 비교 음원을 제시해 판단받는다. 취향으로 편곡하지 않는다.

이 단계의 산출물도 `원본 ROM → 오디오 데이터 변환 → GBC 빌드`로 생성한다. 제품에 재사용할 사운드 계층이며 새로운 시험용 게임플레이는 추가하지 않는다.

## 6. 전체 작업 순서와 완료 조건

| 단계 | 작업 | 완료 판단 |
|---|---|---|
| 0. 기준 고정과 배포 경로 | 이번 방향 반영, 자료/ROM 대응, 제품 입력·산출물 계약, 전체 시스템 목록 | 원작 동작과 샘플 동작 구분, 모든 작업의 원본 주소·검증 방법 명시 |
| 1. 사운드와 메모리 위험 확인 | 위 사운드 검증, ROM/WRAM/VRAM/저장 RAM/프레임 예산, 배포 빌더 골격 | 원작 데이터 기반 BGM+효과음 동시 재생, 알려진 손실과 CPU 비용 제시, 깨끗한 폴더에서 ROM 입력 빌드 |
| 2. 원작 상태와 데이터 모델 | 캐릭터·장비·마법·직업·가방·세계/이벤트 플래그·세이브 구조, 전체 추출 명세, RNG | 필드 폭과 원작 초기값/저장 round-trip; 원본 참조가 끊기지 않는 데이터 패키지 |
| 3. 원작 실행 계층 | 맵/NPC/이벤트 VM, 메뉴 상태기계, 전투 명령/공식/효과/AI/성장·직업 처리를 의존 순서로 이식 | 각 루틴이 같은 입력 상태와 RNG 조건에서 원작과 같은 결과·부작용을 냄 |
| 4. 원작 첫 구간 통합 | 새 게임/이름 입력 → 낙하/초기 이벤트 → 제단 동굴 → 보스 → 크리스털/직업 해금 → 원작이 허용하는 저장/재개 | 원작과 같은 이벤트 순서·보상·상태 전이. 임의 대사·수동 전투 버튼·전멸 회복 없이 플레이 |
| 5. 전체 콘텐츠 확장과 한글화 | 나머지 지역/NPC/상점·숙박/차량/월드 상태/특수 전투/연출/후반부/엔딩; 원문 기반 번역과 전체 창 검증 | 도달 가능한 데이터·스크립트·효과를 분모로 누락 0, 이름·아이템 치환·제어 토큰 유지, 원작 진행과 대조 |
| 6. 최종 배포 검증 | 오프라인 패키지, 전체 플레이, 저장/로드, 새 설치 환경 재현 | 사용자가 원본 ROM 하나를 제공해 동일 결과 생성, 엔딩까지 진행, 미확인 기능을 완성으로 표시하지 않음 |

단계 2~3은 한 기능씩 즉흥적으로 붙이는 작업이 아니다. 의존 관계는 공통 상태/정수 연산/RNG → 장비·직업 기반 능력치 → 아이템·마법·행동 의미 → 명령 선택·라운드·적 AI → 승패·경험치/레벨·직업 성장 → 탐색 반영이다. 원작 메뉴는 이 상태와 기능을 그대로 노출하도록 구현한다. 번역 데이터 추출은 단계 2부터, 실제 번역과 화면 검증은 해당 실행 경로가 준비되는 대로 진행한다.

원작 비교는 전체 프레임 입력이 우연히 같다고 가정하지 않는다. NES와 GBC의 시간/화면 처리 차이를 고려해 함수/행동/이벤트 경계에서 상태를 비교하고, RNG 값뿐 아니라 소비 횟수와 순서를 통제한다. 원작에 명시적인 버그가 있어도 임의로 수정하지 않고 근거와 영향을 기록한다.

## 7. 최종 배포 패키지의 계약

```text
사용자가 제공한 NES ROM (불변)
    → 해시/헤더/리비전/핵심 코드 서명 확인
    → 영역·포인터·명령·문자열·자산 분석 및 추출
    → 데이터/그래픽/음악 변환 + 원문에 연결된 한글 자료 적용
    → 원작 대응 GBC 코드 컴파일 + 데이터 은행 배치/링크
    → ROM 헤더/체크섬/메모리 예산/참조/누락 검사
    → 사용자 로컬의 GBC ROM + 출처 대응표 + 빌드 보고서
```

패키지에 넣을 것은 이식 구현, 분석/추출/변환 규칙, 한글 번역·인코딩 자료, 재배포 가능한 폰트/도구 의존성, 검증 코드다. 원본 ROM·원본에서 미리 추출한 대량 자산·생성 GBC ROM을 패키지의 필수 동봉물로 삼지 않는다. 폰트/도구를 동봉할 수 없다면 명시적인 외부 입력으로 처리하며 개발 PC의 `.cache`, `assets/private`, `local.json`에 몰래 의존하지 않는다.

- 최초 지원 입력은 현재 사용자가 제공한 일본판 ROM의 정확한 해시다. 다른 덤프/번역판은 별도 검증된 프로필을 추가한 경우에만 허용한다.
- 사용자가 실행하는 최종 빌드에는 분석자의 인터넷 접속·에뮬레이터 세션·개인 경로가 필요하지 않아야 한다. 개발 검증과 사용자 빌드를 분리한다.
- 원작 루틴에 대응한 포트 소스와 코드 서명/주소 대응 규칙을 버전 관리한다. 알려지지 않은 코드나 데이터 차이가 있으면 생성을 중단한다.
- 그래픽 팔레트/배치, 문자열 길이·누락, 알 수 없는 VM 명령, 데이터 포인터/은행 넘침도 빌드 실패 사유다. 샘플 구현으로 대체하고 성공 처리하지 않는다.
- 중간 결과는 매니페스트와 해시로 추적하고 출력에는 입력 ROM/도구/변환 정책/번역 버전을 기록한다. 타임스탬프·로컬 경로가 최종 ROM 해시를 흔들지 않게 한다.
- 제품 카트리지 구성은 영속 저장을 지원하도록 정한다. 현재 시제품의 MBC5 ROM-only 설정과 종료 시 상태 소실은 제품의 저장 명세가 아니다. SRAM 용량과 배치는 원작 저장 구조 분석 후 결정한다.
- 깨끗한 폴더에서 패키지+정상 입력만으로 빌드, 두 번 빌드한 결과 일치, 입력 불변, 잘못된 입력 거절, 필요한 외부 파일 누락의 명확한 오류를 배포 검사에 포함한다.

## 8. 앞으로의 작업 보고 기준

“창이 나옴”, “적 HP가 줄어듦” 대신 다음을 보고한다: 원작 어느 루틴/데이터를 옮겼는지, 원작과 비교한 상태/입력은 무엇인지, 아직 옮기지 않은 범위는 무엇인지, 최종 배포 빌드에서 같은 결과가 생성되는지. 화면 차이는 승인된 GBC 표현 변경 범위로 설명하고, 게임 규칙 변경으로 대신하지 않는다.

계획 수립 당시 완료한 것은 자료 재조사·ROM 바이트 감사·사운드 정적 조사·배포 방향 명세였다. 이후 유한 구간 사운드 재생과 ROM 입력 빌드 경로를 추가했다. 현재 검증 범위는 별도 기록을 따르며 전체 게임 실행 계층 이식 완료로 계산하지 않는다.

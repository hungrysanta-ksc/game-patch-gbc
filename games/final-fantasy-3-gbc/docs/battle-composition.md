# 원작 전투 그림의 합성과 상주 타일 전송

2026-11-24. 기준: PR 24 병합 `0591fd17122235164f2804bcdcce6fc0719c606f`.
원작 적·아군·큰 마법을 함께 표시하고 7×7 한글 창과 기존 원작 음악/효과음 부하를 겹치는
R2 진단이다. 전투 명령/계산/보상/정상 진행을 구현한 것이 아니다.

```powershell
npm run build:battle-composition
npm run verify:battle-composition
```

`local.json`의 지원 원본 ROM·기존 비공개 번역 대응표·7×7 글꼴·고정 GBDK/MesenCore/.NET을 사용한다.
기존 캐시와 비교하려면 같은 도구에 `--battle --legacy-cache`를 전달한다. 결과와 화면/ROM은
`build/battle-composition`, 원시 관측은 `evidence/battle-composition`에 생성하며 공개하지 않는다.

## 원작 공급과 이전 조사의 정정

적 6/팔레트 143·152는 원작 편성 슬롯 47의 참조에서 가져왔다. 직업 0/1/2/3의 아군은
`2F/A9ED`로 CHR을 적재하고 `2E/9E01`로 팔레트를 선택한다. `2F/B4AC`의 정상 자세 초기화와
`32/90D8`의 OAM을 실행해 그림을 얻는다. 원본 16×24 픽셀은 줄이지 않는다.

PR 24의 슬롯 조사에서는 자세 초기화를 생략해 빈 자세 0이 선택되어 있었다. 그 검사는
아군의 24개/16개 슬롯 예약과 마법 픽셀을 검사했으나, 실제 서 있는 아군 그림까지 검증한 것은
아니었다. 이번에는 원작이 선택하는 자세 2를 실행하고 24조각 모두에 불투명 픽셀이 있음을 검사한다.
GBC 배치의 y도 정확히 10/34/58/82로 맞췄다. 원작 1,740조건 재검사에서 이전 최대 슬롯 수와
색 보존 보조 OBJ의 168조합 초과 결과는 변하지 않았다. 수정된 보고서 해시는
`1bc9d791914cb54ab5df6bd1a0ce3921fe1c96bf3042fb19e0f038fd4a6630cb`이다.

마법 스크립트 29의 원작 순서 `13,13,14,14,15,15`를 유지한다. 마지막 프레임은 36조각이다.
`AF6F/B589/B696/B711/B7B5`의 선택·CHR 적재·복사·위치·순서를 실행하고, `AB08`로 원작 효과
팔레트도 읽는다. 원작 프레임당 대기는 4 NES 프레임, 약 66.557ms다.

적 위치 `(0,24)`·마법 중심 `(56,56)`·아군 위치는 화면 예산용 변환이다. 해당 직업과 마법/적의
조합이 실제 스토리에서 도달한다는 검증은 아니다. 적 48×48→42×42는 최근접 축소의 색 보존 후보이며
전 적에 승인된 최종 미술 규칙이 아니다. 지형·전투 메뉴·상태 연출은 이 표본에 포함하지 않는다.

## 같은 픽셀로 비교한 후보

| 후보 | BG 팔레트 | 최대 OBJ | 최대 한 줄 | 범위 |
|---|---:|---:|---:|---|
| 적·마법 합성 + 원본 크기 아군 OBJ 예약 | 4 | 32 | 5 | 호스트 색 분할/위치 예산. 아군용 OBJ 팔레트/전송 통합은 미실행 |
| 아군까지 BG와 잔여 OBJ로 합성 | 7 | 11 | 3 | 이번 GBC 진단 경로 |

전체 합성도 모든 RGB555 픽셀과 얼굴·실루엣을 유지한다. 타일별 색을 BG 4색과 원작 팔레트의
투명 OBJ 마스크로 나누며, 남는 BG 팔레트 7은 한글 창이 사용한다. 네 OBJ 팔레트는 두 적 팔레트,
마법 팔레트, 원작 아군 팔레트 1이다. 사전 선택한 BG 팔레트는 여섯 엔트리 사이에서 바뀌지 않는다.
합성 뒤 160×144 화면과 원작 소비자에서 계산한 화면을 대조한다.

이 진단은 호스트에서 합성한 세 그림/여섯 엔트리의 유한 타일 모음이다. 기존 SM83 실시간 합성기의
속도가 빨라졌다는 결과가 아니다. 적×마법×직업×자세×대상 위치의 조합을 전부 사전 생성하는 방식을
제품 설계로 채택하지 않는다. 실제 실행에서는 상주 원작 자산과 변경 셀 공급의 범위를 따로 결정해야 한다.

## 전송과 소유권

`battle-atlas.c`는 BG 타일 80개(1,280바이트)를 먼저 상주시킨다. 실제 화면별 BG 패턴은 최대 71개이며,
모든 원본 엔트리는 유지하되 같은 그림으로 이어지는 요청에는 새 전송이 필요 없다.
두 지도 중 비활성 지도와 비활성 OBJ 영역을 준비한 뒤 기존 VBlank 게시 함수로 함께 전환한다.

지도 차이의 연속 범위를 변환 시점에 계산한다. 단순히 같은 행을 생략하는 것뿐 아니라,
중간의 미변경 바이트까지 포함한 짧은 연속 전송으로 DMA 설정 횟수를 줄인다.
모든 이전 그림/다음 그림과 초기화 상태에 대해 이 범위를 적용하면 전체 목표 지도가 복원되는지 검사한다.
32개 고정 WRAM 전송 기록은 ROM 은행·소스·목적지·VRAM 은행·길이를 보유한다. 소스는 16바이트 정렬을
링크 결과에서 확인하며 한 DMA는 128바이트 이하, 시작은 VBlank의 LY 144–149로 제한한다.
ROM 은행과 VBK를 전송 완료 후 복원하고 작은 전송 사이에는 타이머 IRQ를 허용한다.

사양 근거는 Pan Docs [VRAM DMA](https://raw.githubusercontent.com/gbdev/pandocs/master/src/VDMA.md)다.
ROM 소스와 16바이트 정렬, GDMA 중 CPU 정지 및 은행 유지 조건을 확인했다. 사이트 403/curl DNS 실패 후
같은 문서의 GitHub 원문을 사용했다. 실제 버스 검사에서는 최대 128바이트·VBlank·활성 영역 보호를
동시에 확인한다. 이 결과는 고정 MesenCore의 CGB 실행이며 실기/독립 에뮬레이터 검증은 남아 있다.

이 경로는 탐색의 WRAM 3/4/5 합성 캐시 10,240바이트와 1,856바이트 메타데이터를 사용하지 않는다.
은행 6의 256바이트는 한글 창에 빌려준 임시 키 영역을 보존하는 용도다. 맵/필드 RAM과 GameState,
음원 큐는 유지한다. 이는 모드별 메모리 재사용의 가능성을 보인 것으로, 정상 필드→전투→필드 전환을
구현하거나 필드의 보존 상태를 확정한 것은 아니다.

한글 창은 검수된 원작 본문 7의 두 페이지를 부하 입력으로 사용한다. 이 문장을 전투 대사로 지정한
것이 아니다. 음악/효과음도 기존 원작 필드 음악 요청과 효과음·페이드 일정의 회귀 부하다.
마법과 정확한 효과음 호출의 동기화나 전투 BGM 호출자 통합은 이번 범위에 포함하지 않는다.

## 실제 GBC 결과

고정 MesenCore에서 원작 오디오 7,200틱 동안 733요청을 처리했다. 실제 20장·460,800픽셀과
한글 셀 배치가 기대값과 일치했다. 원작 이벤트 21,366개·실제 APU 쓰기 30,938개를 대조했고,
오디오 지연/큐 부족, 잘못된 VRAM/DMA 접근, 활성 그림 덮어쓰기, 메모리 가드는 모두 0건이다.
타이머 편차는 -0.088ms다. 고정 WRAM 끝은 `$CDF4`(여유 524바이트), 관측된 스택 미사용은
284바이트다. 이 실행의 버스 검사에서 DMA 3,172회를 확인했다.

| 측정 | 기존 캐시 | 상주 타일·연속 ROM DMA |
|---|---:|---:|
| 스크립트 내부 그림 변경 관측 수 | 54 | 147 |
| 해당 요청 중앙값 | 552.621ms | 66.995ms |
| 해당 요청 최대 | 653.398ms | 117.336ms |
| 최초 준비 | 2,043.593ms | 200.912ms |

같은 여섯 원작 엔트리·동일 픽셀·오디오 일정을 사용한다. 두 실행의 처리 속도가 달라 관측 수는
다르다. 같은 그림의 별칭 요청, 창을 닫은 뒤 마지막→첫 그림 복귀, 검증기의 스크린샷 대기는
위 내부 전환 통계에서 제외했다. 기존 경로의 셀 검색/합성 대신 상주 패턴과 미리 계산한 변경 범위를
쓰고 연속 전송으로 DMA 설정 비용을 줄였다. 동적 SM83 합성 자체의 성능 개선 수치는 아니다.

**원작 시간 관문은 미통과다.** 4 NES 프레임(66.557ms) 기준 147전환 중 146회가 넘었으며
`timingGatePassed=false`로 기록한다. 픽셀/오디오 검증의 성공과 이 성능 실패를 분리한다.
요청마다 완료를 기다리는 함수 경계 진단이고 원작 시계에 맞춘 자동 재생기는 아직 아니다.
스크립트 29는 같은 그림을 두 엔트리씩 유지하지만, 그 시간을 이용한 다음 그림 선행 준비는
이번에 구현하지 않았다. 원작 간격을 느리게 바꾸거나 별칭을 버려 통과시키지 않는다.

한글 창 열기 중앙값/최대는 435.445/619.778ms, 다음 페이지는 318.174/402.020ms,
닫기는 16.743/33.597ms다. 창 표시 응답 개선도 남아 있으며 전투 UI의 완료 수치가 아니다.

호스트 47테스트가 통과했다. 자세 초기화, 그림 순서/픽셀/팔레트/OBJ 예산과 모든 이전·다음
지도 조합의 부분 전송 복원을 검사했다. 기존 탐색·한글 창 ROM은 재빌드 시 이전 산출물과 같다.
공개 허용 소스 270개를 새 디렉터리에 복사하고 원본 ROM·고정 GBDK·비공개 번역/대응표·글꼴을
외부 경로로 참조한 별도 빌드에서도 전투 ROM/보고서와 기존 탐색·창 ROM 해시가 같았다.
별도 복사본에서 전투 관련 5테스트와 공개 목록 검사도 통과했다. 이는 같은 도구체인의 소스 재현
검사이며, 원본 ROM만 사용하는 최종 배포 계약이나 독립 에뮬레이터 재검증은 아니다.

## 다음 관문

R2는 아직 열려 있다. 이번 표본의 색/OBJ 수 성공을 큰 보스·여러 적·모든 자세·소환·지형/메뉴의
공존 성공으로 확대하지 않는다. 다음에는 측정된 전환 시간과 원작 4프레임 간격을 기준으로
준비 시점/게시 시점과 표시 시계를 연결한다. 이어 보스 210 등 기존 초과 표본의 실제 편성 배치와
메모리/팔레트/전송 상한을 검사하고, 전편 조합을 미리 저장하지 않는 공급 방식을 정한다.
탐색의 실시간 입력·월드 링·전체 응답 문제도 남아 있다. 이 경계를 정한 뒤 R3 공유 규칙으로 진행한다.
음질 개선은 후순위를 유지한다.

# 원작 필드 이벤트와 사운드의 통합 검증

기준일: 2026-11-23. 첫 통합 구간은 제단 동굴 맵 `$16`의 바위 통로 이벤트 `$71`이다. 원본 ROM에서 맵·지형 그래픽·팔레트·이벤트·악보를 읽어 GBC에서 실행한다. 임의 피해량·보상·대사·전투 전환은 이 경로의 입력이 아니다. 음색 정책은 이전 단계와 같다.

## 원작 범위

| 원작 위치 | 연결한 동작 |
|---|---|
| `3A/934B`, `3F/E8CE..E8DA` | 맵 속성 byte 10의 BGM. 이 맵은 곡 `$02`. 로딩 완료 후 요청 |
| `3F/E201`, `3F/E226`, `3F/E374` | 맵 프레임의 사운드 갱신 후 이벤트 실행 순서 |
| NPC 스크립트 `$02`, `2C/9947` | `FF 71`이 이벤트 `$71`을 선택 |
| 이벤트 포인터 `2C/8600 + $71×2` | 원본 포인터 `$B257`, 파일 위치 `0x5B267` |
| `3E/D219..D277` | 이벤트 명령 길이와 다음 명령 위치 |
| `3B/B58F`, `B938..B980` | D0: 효과음 `$38` 요청, 17회 VBlank 경계에서 X 스크롤 XOR 2, 연출 중 사운드 갱신 |
| `3B/B71C..B74F` | F8 음악/효과음 요청. 이 이벤트의 인자는 `$83`, 효과음 `$03` |
| `3B/B5AD..B5B4`, `B8A6..B8EF` | D6/D7: 맵에서 첫 `$5B/$5C`를 찾아 +2. 없으면 변경 없음 |
| `3B/B7A3` | FF 종료. 현재 소비자는 완료 상태를 외부에 전달 |

원작 이벤트를 해석하면 `D0 D0 F8 83 D6 D7 D6 D7 FF`다. 42논리 프레임 동안 효과음 세 번, 흔들림 두 번, 맵 변경 세 번이 발생한다. 네 번째 통로 검색은 일치하는 타일이 없으므로 변경하지 않는다. 변경 위치는 원본 맵 검색으로 얻으며 좌표를 이벤트 실행 코드에 하드코딩하지 않는다.

검증 진입점은 **맵 로딩과 이미 선택된 이벤트의 함수 경계**다. 개발용 카메라는 변경되는 통로를 보도록 원본 타일 위치에서 계산한다. 전체 새 게임·플레이어 이동·NPC 충돌/조건·메뉴·전투를 실행한 플레이스루가 아니다. 이 장면에는 NPC/파티 렌더러를 합치지 않았다. 기존 시제품의 가상 전투나 가상 대사는 가져오지 않는다.

## 추출과 표시

`tools/field-source.mjs`가 지원 ROM 해시를 검사한 빌드의 입력을 받아 다음을 생성한다.

- 원작 RLE 맵 1,024바이트. 실제 `3E/CBFA` 실행 결과와 대조한다.
- 지형 112타일: NES 두 비트플레인을 GBC 교차 행 순서로 바꾼다. 픽셀 인덱스는 그대로다.
- 메타타일·팔레트 속성. 팔레트 인덱스는 실제 `3A/9091` 소비 결과에서 얻고 기존 RGB555 근사표를 사용한다. NES의 공통 배경색을 각 CGB 팔레트의 0번 색에 적용한다.
- 원본 이벤트 포인터/바이트, 맵 BGM과 출처 보고서. 지원하지 않는 명령이나 데이터 구성이면 빌드/실행 오류로 종료한다.

160×128 지형 시야와 아래 16픽셀의 빈 영역을 사용한다. 새로운 안내 대사나 게임 규칙은 없다. 화면 타일은 VRAM `$9000`, BG 맵은 `$9800`, 속성은 CGB VRAM bank 1을 사용한다. 타이머 인터럽트는 사운드 출력과 함께 해당 논리 프레임의 흔들림/맵 변경 번호를 전달한다. 렌더러는 준비 중인 미래의 맵 상태를 바로 표시하지 않고 소비된 상태를 표시한다.

개발용 부하 검사는 3,600논리 틱 동안 같은 원본 장면에 여섯 번 재진입한다. 재진입 간격 600틱은 검증 장치의 입력이며 원작 게임 이벤트라고 주장하지 않는다. 첫 로딩 후 BGM을 시작하고, 이후 재로딩 중에는 기존 BGM이 계속 진행한다. 매 재진입에서 원본 그래픽·타일맵·팔레트를 실제 VRAM에 다시 쓰고, 로딩을 끝낸 뒤 원작 맵 BGM 요청과 이벤트를 실행한다.

## 부하와 오류 수정

이전 사운드 전용 ROM은 4096 Hz 타이머의 짧은 직접 인터럽트를 사용한다. 기본 GBDK 그래픽 쓰기 함수와 함께 쓰자, 인터럽트가 LCD mode 3으로 복귀하는 경우 일부 VRAM 쓰기가 무시되는 것을 바이트 대조로 확인했다. 렌더러는 접근 가능 상태를 기다린 뒤 **짧은 임계 구간에서 STAT를 다시 확인하고 한 바이트를 쓰도록** 변경했다. 접근 가능 상태를 기다리는 동안에는 인터럽트를 막지 않는다. 팔레트 데이터 쓰기도 같은 규칙을 쓴다.

일치하지 않는 타일을 찾는 1,024바이트 검색에서 컴파일러가 반복마다 스택에 포인터를 저장해 화면 갱신이 늦어졌다. GBC에서는 고정 SM83 ABI에 맞는 짧은 검색 루프를 사용한다. 호스트 C 버전과 GBC 실행 모두 첫 일치/없음과 실제 맵 변경을 대조한다.

그래픽 업로드는 32바이트 또는 타일맵 한 행 단위로 나눈다. 팔레트 복원은 마지막 행 쓰기와 별도 프레임으로 분리한다. 오디오 선행 큐를 모두 채우느라 화면 갱신이 늦어지지 않도록, 표시 프레임이 대기 중이고 오디오 한 논리 틱 이상이 준비되면 화면 작업에 실행 시간을 넘긴다.

## 검증 방법

원작 6502 이벤트를 직접 실행하는 기준 도구는 `$FF00`을 VBlank 경계로, `$C009`를 별도 검증된 사운드 갱신 경계로 취급한다. PPU나 게임 전체를 이 CPU 도구로 에뮬레이트한다는 뜻은 아니다. 원작 이벤트의 요청 바이트·순서·프레임과 스크롤·맵 변경을 기록하고 C 이벤트 실행 결과와 대조한다. 기대 맵 상태를 C 엔진에 복사하는 방식으로 검사를 통과시키지 않는다.

통합 ROM 검사는 원본 사운드 엔진과 같은 음악/효과음 요청을 적용하여 RAM/APU 상태와 출력 기록을 대조한다. GBC 에뮬레이터에서는 실제 VRAM 그래픽 1,792바이트, 보이는 21×16타일 및 속성, 팔레트 32바이트와 SCX/SCY/WY를 대조한다. 오디오 지연·큐 고갈·타이머 드리프트, 렌더 작업 최대 시간과 표시 사이의 논리 틱 간격을 함께 검사한다.

검사 기준에는 원작 소비 결과를 쓰며, 게임 진입점과 카메라·반복 재진입 같은 개발용 조건은 별도 기록한다. 최종 게임 전체나 실기 성능의 완료 판단으로 확대하지 않는다.

## 결과

MesenCore에서 3,600논리 틱(약 59.9초), 10,682출력 이벤트, 1,188관측을 대조했다.

| 항목 | 결과 |
|---|---|
| 장면 로딩 / 원작 이벤트 완료 | 6 / 6 |
| 이벤트 시작 논리 틱 | 76, 673, 1273, 1873, 2474, 3073 |
| 오디오 출력 시한 초과 / 큐 고갈 | 0 / 0 |
| 종료 시 타이머 드리프트 | +0.200 ms |
| 지형/타일맵/속성 업로드 | 14,928바이트; 팔레트 쓰기는 별도 |
| 렌더 호출 / 최대 작업 시간 | 3,579회 / 32타이머 틱 = 7.8125 ms |
| 로딩 완료 상태의 최대 렌더 간격 | 원작 논리 틱 2개; NES/GBC 주사율 차이 포함 |
| 고정 코드 끝 / 정적 WRAM 끝 | `$393D` / `$CC3D` (정적 WRAM 3,133바이트) |

최대 작업 시간은 4096 Hz 타이머로 계측한 값이며 전체 게임 CPU 사용률이 아니다. 정적 메모리 검사는 스택 최대 사용량을 측정한 것이 아니다. 고정 뱅크 끝 `$4000`까지 1,731바이트가 남아 있으므로 기능 확장 때 코드 뱅킹 예산을 별도로 잡아야 한다.

호스트 C 이벤트 검사는 원작 42프레임의 모든 맵 바이트·요청·흔들림·종료를 통과했다. 기대 맵 한 바이트를 바꾼 음성 대조군은 맵 비교 오류(exit 8)로 검출했다. 사운드 전용 ROM의 기존 3,600틱 검사도 지연/큐 고갈 0으로 통과했다.

별도 관리형 Mesen 실행에서 통로 변경 전후 화면과 완료 상태를 확인했다. START 입력으로 완료 카운터가 1→0으로 초기화된 뒤 다시 1이 되고 변경 번호가 3이 되는 것을 확인했으며 엔진 오류·출력 지연·큐 고갈은 0이었다. 캡처는 로컬 `evidence/native/field-final-before.png`, `field-final-after.png`에 보관한다.

공개 허용 목록의 소스 81개만 빈 폴더에 복사하고 원본 ROM/GBDK 경로만 지정해 다시 빌드했다. 생성 ROM·지형 블록·원작 비교 기준·변환표가 개발 폴더 결과와 바이트 단위로 일치했다. 기존 CPU/사운드/VGZ 회귀 검사 13개도 통과했고 사운드 전용 ROM 해시는 이전 단계와 동일하다.

통합 ROM SHA-256: `65a7503642547ddcd64e4c0fbf42b715dab0359beba75b7784ae36a566bda00c`.

지형 입력 블록 SHA-256: `9b7fdebbd496c009bef27383836dd4f5accebd201688a9614e2bc48d41b6cc64`.

GBDK/원본 ROM/MesenCore의 고정 버전은 [네이티브 사운드 검증](audio-native.md)과 같다. 원시 결과는 로컬 `build/scene/`과 `evidence/native/ff3-field-audio*.json`에 보존한다.

## 실행과 재현

```powershell
node tools/build-native.mjs --scene --rom "D:/private/Final Fantasy III (Japan).nes" --gbdk "D:/tools/gbdk"
node tools/build-native-verifier.mjs
node tools/verify-native.mjs --scene
```

출력은 `build/scene/ff3-field-audio.gbc`다. 자동으로 로딩·원작 이벤트·재진입을 실행한다. START는 검사 시작점으로 다시 초기화한다. 원본 게임의 START 메뉴 기능을 이식했다는 뜻이 아니다.

검증은 `local.json`의 고정 MesenCore와 .NET 경로를 사용한다. `--reuse`는 해당 ROM/코어 해시와 일치하는 기존 원시 관측을 재대조할 때만 사용한다. 새 실행을 수행했다는 뜻은 아니다. 녹음 API는 사용하지 않는다.

호스트 이벤트 검사는 별도의 C 컴파일러로 실행한다. 예를 들어 MSVC 개발자 셸에서는 다음과 같다. 음성 대조군은 생성된 fixture의 기대 맵 바이트 하나(offset 1041)를 XOR 1 한 별도 파일로 검사해 exit 8을 확인한다. 원본 fixture는 수정하지 않는다.

```powershell
cl /nologo /W4 /D_CRT_SECURE_NO_WARNINGS /Febuild/scene/field-host.exe /Fobuild/scene/ src/field-event.c src/field-event-test.c
./build/scene/field-host.exe build/scene/field-fixtures.bin
```

원본/생성 ROM, 추출 그래픽·맵·이벤트·비교 기준·관측·번역 데이터는 공개 대상에서 제외한다. 배포 소스는 원본 ROM에서 필요한 자료를 다시 생성한다. 다음 게임 실행 계층 작업은 원작의 NPC 조건/이벤트 선택과 이동·충돌을 이 소비자에 연결하는 것이다. 한글 문장·전투/마법·다른 맵과 전체 CPU 예산은 각각 해당 경로를 합쳐 검증해야 한다.

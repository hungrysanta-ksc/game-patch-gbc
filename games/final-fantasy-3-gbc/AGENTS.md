# FF3 GBC project workflow

- Work on a feature branch. Never push changes directly to `main`.
- Publish through a pull request into `main`. Inspect the exact PR head, changed files and checks before merging. The user requested this workflow, including merging the current work through a PR. Do not bypass protection, failed checks or unresolved merge conflicts.
- Current implementation order and acceptance gates: `docs/implementation-roadmap.md`. `docs/port-plan.md` preserves the original scope and older planning history.
- Party names are fixed by user decision: 루네스, 아르크, 레피아, 잉구스. The supplied Korean NES reference shows these names during new-game confirmation. Do not implement custom name entry or treat Japanese name-byte conversion as an outstanding product requirement. Keep the reference ROM private; the supported Japanese original remains the build input.
- Build from the user's supported original ROM. Keep original/generated ROMs, extracted assets, reference disassembly, observations and the supplied Japanese/Korean translation files outside Git. Publish only the explicit `tools/export-source.mjs` allowlist; update and verify `export-manifest.json`.
- Use the existing `create-kr-patch` skill plus the applicable installed `nes-reverse-engineering` and `gb-hardware-research` guidance. See `docs/development-skills.md` for pinned sources, local setup and FF3-specific limits. These skills are development aids, not product build dependencies.
- Preserve original mechanics and data. Unsupported consumers fail explicitly; do not turn them into successful no-ops. Inventory slot counts, syntactic decoding, original-code comparison and normal-play validation are separate claims.
- For every implementation or optimization (including audio, UI, gameplay, graphics, loading and tooling that defines runtime behavior), inspect the original ROM consumer and its callers before choosing the design. Record source bank/addresses, actual execution order, update cadence, shared-state ownership and resource lifetime. Reference assets or decoded scripts alone are not sufficient when runtime behavior or screen composition is involved: use original execution observations as needed. Retain the original efficient structure where applicable; when GBC hardware requires a different structure, explain the constraint, compare alternatives and verify preserved behavior and total cost. Never substitute an imagined implementation merely because it is easier to build. Carry these rules into each subsequent task and PR, not only the current performance work.
- For every ported consumer, record the original state/update/resource-lifetime structure, which parts the GBC implementation retains, why any part must change, and whether an alternative reduces total CPU/transfer/memory cost without changing behavior. Asset reuse or pixel equality alone is not structural fidelity. Keep precomposed frame fixtures as reference oracles, not the default runtime architecture. Measure proposed improvements against the same original work and include worst-case coexistence; do not claim superiority from an isolated metric.
- Treat field/battle/return as one resource lifecycle. Before sharing or retaining a RAM/VRAM region, reconcile every mode's allocation, pending transfer, callback, cache invalidation and persistent-state owner. Separate executable diagnostics do not prove coexistence or safe re-entry. Follow the current roadmap's single-ROM roundtrip gate before resuming isolated battle micro-optimization; keep existing diagnostics as regression tools.
